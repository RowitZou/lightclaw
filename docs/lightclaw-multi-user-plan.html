1. main dev-plan 的最新基线

当前三件套是“用户配置自治 + 目录可移植化”。它把多用户问题拆成一个更稳的第一阶段：用户可以拥有自己的配置、模型、密钥引用、skill、memory、workspace 和 sessions，但 daemon 的系统级配置、runtime backend、cluster 参数和审计仍由管理员掌控。

统一 daemon

仍然是一套后台进程服务多个 canonical user。全局 config.json 是 admin baseline，不被普通用户覆盖。

用户自治目录

每个用户有一棵 users/<canonical>/ 树；如果管理员配置了 dataRoot，整棵树可被重定向到共享存储上的独立位置。

runtime 先不开放

本阶段不让用户修改 runtime backend、driver、docker、cluster、network、hooks、mcp 和系统级 path。这些继续是 admin-only。

这意味着当前方案要从“直接做每用户 runtime pool / 真实执行身份”回收为“先做目录和配置边界”。真实集群身份是后续扩展，不是 PR1-PR7 的第一承诺。

2. v0.4 Phase 1 目标布局

新布局按“用户优先”组织数据：顶层保留 admin 注册表、运行日志、审计和全局 auth；用户可迁移内容集中在 users/<canonical>/ 下。dataRoot 存在顶层 identities.json，因为它决定用户树的位置，不能反过来写进用户树内部。

默认路径

userHome(canonical) 默认解析为 <home>/users/<canonical>。workspace 默认在 userHome/workspace，跟随用户树整体迁移。

可重定向路径

管理员可在 identities.json 给用户设置 dataRoot。cluster backend 下它必须是 daemon 可见目录，并且落在 gpfsMounts.hostPrefix 映射规则内。

3. Session-scoped 配置解析

main dev-plan 的关键点是：启动级、全局级逻辑仍可读 getConfig()；但会话内的 provider、tools、permission、render 和 runtime 参数读取，应切到 getSessionConfig()，拿本轮 session 创建时固定下来的配置快照。

1

消息进入

channel runner 得到 Feishu sender、chat、tenant 和 session metadata。

2

身份映射

平台身份映射到 canonical user，并读取 identity ceiling 与 dataRoot。

3

受限合并

resolveUserConfig() 合并 admin baseline 与用户 override。

4

快照注入

SessionContext 持有不可变快照，ALS 暴露 getSessionConfig()。

5

审计记录

记录 actor、canonical user、权限模式、资源路径和关键配置来源。

type UserConfigOverride = {
  defaultModel?: string
  lang?: "cn" | "en"
  permissionMode?: PermissionMode
  endpoints?: Record<string, UserEndpoint>  // PR4, additive only
  models?: Record<string, ModelEntry>       // PR4, additive only
}

type UserEndpoint = {
  baseUrl: string
  schema: "anthropic" | "openai" | "openai-auth"
  apiKeyRef: string
}

// dataRoot is intentionally not here.
// It lives in identity/identities.json, because it decides where this file is.
安全边界靠 schema，而不是靠“运行时发现危险字段再拦”。用户 override 是 strict schema：未知字段解析即拒；admin-only 字段在物理结构上无法表达。

4. 用户级资源边界

模型与 endpoint

PR4 允许用户加自己的 endpoint/model，但只能加法合并，不能覆盖或删除 admin 定义。密钥通过 apiKeyRef 指向 users/<u>/secrets.json。

Workspace 与 mount

默认 workspace 在用户树内。/mount 继续改当前用户的 rlaunch-mounts.json，所有路径需要通过 daemon 可见性与 GPFS 前缀校验。

Memory、skill、session

用户记忆、技能、会话、taskrun 都沉到同一棵用户树。这样 /export 可以打包用户数据，同时排除 secret。

权限模式

用户可以设置 permissionMode，但最终值要被 identity ceiling 截断。ceiling 仍由 admin 控制。

审计和 api logs

audit/ 和 api-logs/ 留在顶层。它们是部署级取证与观测数据，不随用户树迁移。

runtime 配置

runtime backend、clusterSettings、docker、hooks、mcp、network、系统 path 等保持 admin-only。本阶段不把它们放进用户 override。

5. Codex Auth 与 Brain++ 身份：作为后续 addendum

之前方案把 Codex per-user auth 和 Brain++ 动态身份放得太靠前。按 main dev-plan，它们应该标成 v0.4 Phase 1 之后的扩展：先不阻塞 PR1-PR7，但现在要把接口边界想清楚，避免目录和 secret 设计返工。

Codex OAuth

当前 dev-plan 的 PR4 只定义了 apiKeyRef，这对普通 API key 合适，但不能完整表达 Codex OAuth token bundle、refresh、logout 和过期状态。

可选扩展是新增结构化 per-user auth store，例如 users/<u>/auth/codex.json，或让 secrets.json 支持 typed secret。导入源只能是 daemon 可读路径，不能直接读取用户本机的 .codex。

Brain++ / rjob 身份

main dev-plan 明确 runtime 配置仍是 admin-only。因此 Brain++ token、kubeconfig、impersonation 和 rjob 真实提交身份不应混入 PR1-PR7。

后续可以做 BrainppAuthResolver：按 canonical user 解析 token/kubeconfig/impersonation，再扩展 rlaunch/brainctl 参数；rjob 需要额外确认 CLI 是否支持动态凭证，或改成 daemon 侧提交封装。

能力 Phase 1 状态 推荐后续形态 为什么不提前做
Codex Auth addendum 结构化 per-user auth store，refresh/logout/list 都按 canonical user 操作。 OAuth token 不是普通 API key，直接塞进 PR4 的 apiKeyRef 会污染 schema。
Brain++ 动态身份 addendum 用户级 auth resolver + rlaunch/brainctl 参数拼接 + rjob 身份路径确认。 runtime 仍是 admin-only，贸然开放会扩大安全面和调试复杂度。
每用户 worker pool addendum 等 dataRoot、workspace、mount、session config 快照稳定后，再把 pool key 扩展到 user/auth hash。 目录和配置边界未稳定前做 worker 切分，容易得到错误的复用粒度。

6. 现有存储的迁移方案

main dev-plan 里“本期无生产迁移”是为了避免在小范围删档测试阶段引入脚本复杂度。但架构方案需要预留真实数据迁移路径：如果当前 <LIGHTCLAW_HOME> 已经有会话、记忆、skill、workspace 或用户密钥，就用一次性离线迁移，而不是运行时兼容两套布局。

迁移原则：维护窗口内停 daemon，完整备份旧 home，把 by-type-then-user 复制成 by-user-then-type；顶层 admin 注册表、audit、api-logs 不下沉；迁移完成后只启动新布局，不保留旧布局 fallback。
旧路径 新路径 处理规则
identity/per-user/<u>/permissions.json users/<u>/permissions.json 原样复制，权限规则继续归属该 canonical user。
identity/per-user/<u>/secrets.json users/<u>/secrets.json 原样复制并强制 0600；不得进入 export 包或日志。
identity/per-user/<u>/skills/ users/<u>/skills/ 原样复制；bundled skills 仍由系统目录提供，不复制进用户树。
identity/per-user/<u>/taskruns/ users/<u>/taskruns/ 原样复制；导入到新部署时可按需标记为历史，不自动恢复后台调度。
identity/per-user/<u>/bg-tasks.json users/<u>/bg-tasks.json 同部署迁移可保留；跨部署导入建议重置，避免旧调度自动复活。
identity/per-user/<u>/feishu-workspace.json users/<u>/feishu-workspace.json 同飞书 app/租户可保留；换 app 或租户时重建飞书文件夹绑定。
identity/per-user/<u>/rlaunch-mounts.json users/<u>/rlaunch-mounts.json 同集群可保留；换集群或 GPFS 前缀时逐条重校验。
sessions/<u>/ users/<u>/sessions/ 原样复制；迁移后抽样打开 transcript 和 meta。
memory/<u>/ users/<u>/memory/ 原样复制，包括 _shared 和 role memory 子目录。
workspaces/<u>/ users/<u>/workspace/ 或 paths.workspace/<u> 默认搬入用户树；如果 admin 配了全局 paths.workspace 大盘，则保留 escape-hatch 位置。
audit/、api-logs/、logs/ 仍在顶层 不迁入用户树。audit 是部署级 append-only 取证，api-logs 是后台观测。

离线迁移流程

  1. 停 daemon、停 rlaunch worker，确认没有 in-flight tool call。
  2. 备份完整 <LIGHTCLAW_HOME>，记录当前 commit、config hash 和 identities hash。
  3. 枚举 canonical users：以 identities.json 为准，补充扫描旧的 per-user/sessions/memory/workspaces。
  4. 为每个用户创建目标 userHome；如果要外置数据根，先由 admin 写入并校验 dataRoot。
  5. 按映射表复制数据，保持文件权限，secrets 强制 0600。
  6. 启动新代码，只启新布局；旧目录移动到 archive 或只读备份，不参与运行时 fallback。

校验与回滚

  1. 路径校验：每个用户的 permissions、secrets、skills、sessions、memory、workspace 都能从 userHome 解析。
  2. 权限校验：用户 A 无法读到用户 B 的 workspace、skill、secret 和 session。
  3. 运行校验：抽样对话、读写 workspace、列 skill、读 memory、启动 sandbox。
  4. dataRoot 校验：cluster 下必须命中 gpfsMounts 映射，失败就拒绝启动该用户工作区。
  5. 回滚：停新 daemon，恢复备份 home 和旧 commit；不要在失败状态下双写两套目录。
迁移脚本可以以后作为独立 admin 工具补上，但不建议做运行时自动迁移。自动迁移最危险的点是半成功：用户树、identity 注册表、workspace mount 和 rlaunch worker 的状态可能互相不一致。

7. 按 main dev-plan 的落地路线

下面直接按 dev-log/main 的 PR1-PR7 重排。第一阶段交付标准是：用户数据可独立、可迁移、可配置；admin-only 边界清楚；session 内不再被全局配置污染。

PR 目标 关键改动 验收信号
PR1 目录倒置 + userHome() 新增用户目录锚点；per-user path 全部从 userHome 派生；workspace 默认进入用户树；audit/api-logs 留顶层。 路径重定向零行为变更，全测绿。
PR2 per-user dataRoot identities.json 增加 dataRoot；admin-only /user set-home；复用 mount 的 daemon 可见和 GPFS 前缀校验。 合法 dataRoot 后用户树整体迁移；非法路径清晰拒绝；提示重启 worker 或 reset sandbox。
PR3 受限配置合并层 UserConfigOverride strict schema；resolveUserConfig()；SessionContext 快照；/model 和 /mode 写用户 override。 不同用户 defaultModel/lang/mode 不串；in-flight session 配置不漂移。
PR4 BYO endpoint + model 用户添加 endpoint/model；命名冲突拒绝；apiKeyRef 指向 secrets.json；provider cache key 加 canonical user。 用户自带模型可用，key 不进 transcript，provider 不跨用户复用。

PR7 Prompt + 文档契约 更新 CLAUDE.md、wiki、env.md；model-facing prompt 如需改动单独 review；明确 dataRoot、daemon 可见、安全边界。 开发者和模型都按同一套目录、配置和权限契约工作。

8. 修正后的结论

当前最稳的多用户路径是：先完成“用户树 + 受限配置 + session 快照 + BYO endpoint + 自助 UX + 导出”的 v0.4 Phase 1；再把 Codex OAuth 和 Brain++ 真实执行身份作为清晰边界的扩展接上。

近期可交付

一个 daemon 支持多个用户自治配置；每个用户的数据集中在自己的目录树；admin-only 字段不能被用户表达；session 内配置不被下一次修改影响。

后续再扩展

Codex per-user OAuth 需要结构化 auth store；Brain++ 动态身份需要先确定 rlaunch/brainctl/rjob 的凭证传递模型，再接入 worker pool 和审计。
