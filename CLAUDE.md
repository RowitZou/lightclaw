# LightClaw Runtime Safety Notes

- LocalRuntime is admin-only. When `runtime.backend = "local"`, paired non-admin users must not acquire a runtime; multi-user service must use DockerRuntime or RjobRuntime.
- Do not add path-string workspace guards to tools or permission policy. Runtime safety comes from the LocalRuntime admin-only gate, Docker/Rjob isolation, read-only mounts, and the Phase 5 permission system.
- RlaunchRuntime never uses `brainctl exec -i`. The cluster's brainctl exec drops stdin payloads silently (the `9cafbdc` writeFile incident: ~16% silent corruption) and also suppresses stdout when `-i` is opened with no real stdin. Every `ExecInput.stdin` is folded into the bash command body via `composeExecScript` (base64 inline + brace group so the pipe feeds the whole `&&` chain). Per-call cap is 32 KB raw — empirically the brainctl ws frame fails above ~57 KB total script. `fs.writeFile` chunks transparently above the cap; new tools that hand large payloads to a helper should chunk via `fs.writeFile` + read-from-disk rather than growing the cap.

# LightClaw Cwd Layout Notes (Phase 24)

- `<cwd>/.lightclaw/` is a data write area, never a code discovery root. The only LightClaw write inside this namespace is `inbox/<chatId>/<fileName>` for incoming channel media, written through `runtime.fs.writeFile` rather than host fs.
- Hook / MCP / Skill discovery is admin-side only: `<lightclawHome>/hooks/`, `<lightclawHome>/mcp.json`, and `<lightclawHome>/skills/`. Do not reintroduce a project-layer scan path under `<cwd>/.lightclaw/` even if Claude Code does.
- Channel attachments sink in two phases: Feishu `onMessage` attaches `pendingAttachment` metadata to `NormalizedChannelMessage`; `ChannelRunner` materializes it after pairing and runtime acquire via `ChannelRunnerStrategy.materializeAttachment`. New channel adapters should follow the same shape: channel code does not touch identity or runtime pools directly.

# LightClaw Pairing Card Notes (Phase 25)

- Unknown Feishu senders take the card path only when the canonical admin already has a Feishu binding. Otherwise `ChannelRunner.resolveMessageUser()` must keep the old text fallback, because an application card with no admin target is worse than a visible pairing code.
- The card path does not create `pending.json` entries until the user clicks `[确认申请]`. Cancel stays silent and does not consume the pairing rate-limit slot. If a pending code already exists, repeated user messages render the waiting card instead of sending another review card.
- `fetchFeishuUserInfo()` is cosmetic and best-effort: it uses `contact.v3.user.get` with `user_id_type=open_id`, returns `{ name, email, userId }`, and falls back to open_id on any failure. Do not make pairing depend on this API being healthy.
- `/user approve` is single-argument now: `/user approve <code>`. Both terminal approval and admin card approval call `deriveCanonicalName({ name, email, openId, userId })`, so canonical names are deterministic (`<base>_<user_id>` when Feishu user_id is available).
- Pairing card tokens are in-memory only. After a daemon restart, old card clicks resolve as expired or already handled; users can resend a message and `pending.json` remains the durable source of truth.
- Admin review card clicks must validate the operator through `lookupBySender(feishu:<open_id>)` + `isAdmin()`. Never trust the card payload alone for approval authority.

# LightClaw Feishu Session Isolation Notes (Phase 26)

- Feishu sessionId formula is now `feishu:dm:<chatId>` for p2p/private chats, and `feishu:group:<chatId>[:<threadId>]:<senderOpenId>` for group/topic-group/unknown chat types. `threadId` comes from Feishu `message.thread_id` and is a topic-group sub-channel; `rootId` comes from `message.root_id` and is only reply-chain metadata. Do not merge them back into `parentId`, and do not make `rootId` influence sessionId.
- Same Feishu user in DM, each group, and each topic thread runs an independent transcript, `session-memory.md`, channel lock, and permission FIFO queue. Canonical identity, identity preferences, permission rules, and auto-memory stay per canonical user so long-term facts and user-level rules still cross sessions.
- Group mention gating is enforced in application code before pairing/session routing. With `channels.feishu.requireMention` (default `true`), group messages pass only when `mentions[]` contains the bot open_id or the parsed text contains `@<botName>`. The Feishu open-platform "only messages that mention bot" backend toggle is not enough; keep this gate as the safety net. `requireMention: false` is the explicit admin escape hatch.
- Bot self identity is probed once at startup via `/open-apis/bot/v3/info`. If it cannot be fetched, the gate falls back to "pass" with a stderr warning instead of killing the daemon, because a bot-info outage should not make the channel unusable.
- Group user messages are prefixed before the LLM sees them: `[<senderName>] <text>`. Sender name is best-effort contact lookup, then mention sidecar name, then open_id suffix. DM messages do not get this prefix. The Feishu system prompt tells the model that the prefix is sender metadata, not user words.
- Permission approval cards from group-triggered tool calls are pushed to the sender's DM via `sendInteractiveCardToOpenId(senderOpenId)`. The card button value carries `originSessionId`; callbacks validate it before resolving the pending ask. If DM push fails, fall back to the original chat and log stderr so the turn never hangs silently.
- Permission `ownerKey` is the sessionId. Same user in DM and group can have independent pending approval queues. Do not restore `chatId:senderOpenId`; that collapses unrelated session decisions back together.

# LightClaw Permission System Notes

- `Tool.suggestPermissionRules(input)` returns a *set of rules to install as a group* — not a precise→broad menu. For a chained Bash command the suggester emits one `Bash(<head>:*)` rule per subcommand (split on `;`/`&&`/`||`/`|`, max 5); for path tools a single `Tool(<dir>/**)` rule; for WebFetch a single `WebFetch(<hostname>)` rule; for MCP a single `MCP(<server>:<tool>)` rule. New tools should follow the same shape — return an empty array when no precise scope is derivable, and the approver will fall back to a single tool-wide allow rule.
- Approvers render a fixed three-option UX (Allow once / Allow <merged label> / Deny). The middle option installs every rule in the suggester's array in one go, and the merged label is built by `formatSuggestionLabel` (degrades to `N 类 …` past 50 chars). Faithful port of Claude Code's `bashToolUseOptions.tsx` + `generateShellSuggestionsLabel`. Do not add per-rule buttons or tier-selection UX back.
- `ask` outranks `allow` in `evaluatePermission`. Rules in `permissions.json`'s `ask: [...]` array force the ASK flow even under `bypassPermissions`; only `deny` outranks them. Use this to keep critical operations (`Bash(rm:*)`, `Edit(/etc/**)`) confirmable while running otherwise-permissive sessions.
- The "以后都允许" / `[a]` button writes a persisted rule to `<lightclawHome>/identity/per-user/<canonical>/permissions.json`, not to in-memory state. Rules survive daemon restarts and are reloaded via `loadIdentityRules` on every initializeState / resetSessionContext. There is no "session-scoped" tier — `once / always / deny` collapses to a 3-option UX where `always` is unconditionally persisted.
- Subagents share the parent's permission UX. The channel runner sets `state.permissionApprover` before each query() entry; the permission router prefers `ctx.permissionApprover` but falls back to `state.permissionApprover`, so AgentTool-spawned forks reach the same Feishu card / readline prompt as the main agent. Do NOT reintroduce the "isSubagent → auto-deny on ask" short-circuit; terminal forks without an approver still deny via the final fallback branch, which preserves the original safety property.
- Concurrent same-kind permission asks (e.g. parallel subagents both asking `Bash(curl:*)`) coalesce via the FIFO queue + reevaluate sweep: only the head renders a card; when the user picks "以后都允许", `FeishuPermissionCoordinator.reevaluateOwnerQueue` resolves every queued tail under the new rule set and silently allows / denies anything that now matches. Never render multiple cards for what is effectively one decision.
- High-risk permission asks (anything that contains a `Bash(rm/dd/sudo/su/sh/bash/zsh/eval/mkfs.*:*)` rule, OR an Edit/Write/Read on `/etc`, `/usr`, `/boot`, `/sys`, `/proc`, `**/.ssh`, `**/.gnupg`, `**/.aws`, `**/.kube`) hide the "以后都允许" button — channel users have no shoulder-surfing safety net and `rm -rf /` permanently allowed is unrecoverable. The classifier is `permission/high-risk.ts:isHighRiskAsk`; chained Bash commands trigger as soon as any subcommand is high-risk (`cd /tmp && rm -rf foo` → high-risk via the `rm` segment). Stale-card clicks or text replies that ask for "以后都允许" on a high-risk pending are silently downgraded to allow-once; never persist a rule that the current UX would not have offered.

# LightClaw Slash UX Notes (Phase 18)

- `/help` is a pure command list, role-rendered (admin sees an extra block). Do not put whoami / state info in `/help`; that goes to `/status`. State and operation surfaces are split: `/help` answers "what can I do", `/status` answers "who am I, where am I, what's running".
- Admin-only commands (`/user`, `/ceiling`, `/cost`, `/sandbox`) and user-only commands (`/feedback`) are gated in both `BUILTIN_COMMANDS.visibleTo` and `dispatchChannelSlash`. The role gate must reject with a clear message ("admin only" / "user-only"), not silent allow. `/sandbox` in particular is admin-only because its `status` subcommand leaks deployment internals (image / container / worker names), `prefetch` triggers a multi-GB pull, and `reset` rebuilds a per-user worker — none of which should be a user-facing button. Sandbox health surfaces to admin via channel notices, not via slash commands.
- Renamed commands (`/identity` → `/user`, `/permissions` → `/rules`) are intentionally NOT kept as compat aliases. The `RENAMED_COMMANDS` table in `src/commands/builtin.ts` only emits a hint ("Renamed to /user. See /help.") so the user can self-correct. New code must not register the old names.
- `/fresh <prompt>` runs an ephemeral one-shot session: new sessionId (`fresh-<uuid>`), no memory recall, no transcript persistence, mode forced to `default`. The output is prefixed with `[fresh] `. Do not couple `/fresh` to the forked-agent runner — it goes through the main `query()` path with `persistTranscript: false / includeMemory: false / forcedMode: 'default'` flags.
- `/stop` aborts the in-flight turn for the calling user only. The state tracks abort controllers per-canonical (`abortControllerByUser`); never abort the global controller from a channel handler — that would also kill an admin's terminal session running concurrently.
- `/stop` and a curated read-only slash whitelist take a **pre-lock fast path** in `ChannelRunner.handleMessage` via `parseFastPathSlash`. The channel lock is held for an entire LLM turn, so without this short-circuit `/stop` would queue behind the very query it is trying to abort and never fire mid-turn. Read fast-path runs the slash inside a fresh `SessionContext` populated from disk: preferences (mode / model), identity rules, and the persisted main-session transcript (so `ctx.messages.length` reflects the real message count). Live in-flight per-turn counters like `totalInputTokens` read 0, which is honest "between turns" semantics. Whitelist (`parseFastPathSlash` returns `'read'`): `/help`, `/status`, `/cost`, `/rules` (no args / `list`), `/mode` / `/model` (no args), `/auth list`, `/user` (no args / `list` / `pending` / `feedback`), `/sandbox` (no args / `status`), `/feedback`. `/sandbox status` is special — its handler needs a live `Runtime`, so the fast path acquires one from the per-canonical pool just for that slash (Map lookup if cached). `/feedback` writes `feedback.jsonl` on a path entirely separate from the channel session transcript, so no main-lock contention applies. Write variants (`/mode <m>` / `/model <m>` / `/rules allow ...` / `/auth import ...` / `/user approve ...` / `/sandbox prefetch` / `/sandbox reset`) intentionally fall through to the lock so they serialize with any in-flight turn. When adding a new slash, default to in-lock; only opt into the whitelist after confirming the handler doesn't read live in-memory turn state (or, for runtime-touching slashes like /sandbox, after confirming a pool acquire is acceptable).
- `/branch`'s spawn-pair write to the main transcript is fire-and-forget at the runner level. `appendBranchSpawnPair` itself still acquires `channelSessionLock(mainSessionId)` (because lining up the (user, placeholder) pair at a between-turn boundary is what keeps the API contract — interleaving the placeholder mid-turn would split a tool_use from its tool_result), but the runner does NOT `await` it before kicking off the branch query. The merge-back path awaits the deferred promise before its own `rewriteTranscript`, and FIFO on `channelSessionLock(mainSessionId)` keeps spawn-pair-write strictly before merge-back. Net effect: `/b X` typed during a long main turn starts running immediately; the spawn placeholder lands in the main transcript at the next safe boundary (when the main turn finishes); merge-back replaces that placeholder with the branch's final text. Do not "fix" this by re-awaiting `appendBranchSpawnPair` at spawn time — that defeats `/branch` entirely (the symptom: branch starts only after the main turn it was meant to side-step finishes).
- `/branch` snapshots the main transcript via `trimToLastCompletedTurn(loadTranscript(mainSessionId))`, NOT raw `loadTranscript`. The trim walks back from the end and stops at the last `assistant` message with no `tool_use` block (or the last `system` compact_boundary). This is the fix for the 2026-05-07 `feishu-zouyicheng` / `branch-zouyicheng-5fce2af1` incident: when `/b` fires during an in-flight main turn, the main user message is already on disk but the assistant response is not, so a raw load returns a transcript ending in a dangling user message. Without trim, the branch then appends its own user query and the LLM sees two consecutive user messages — gpt-5-codex tolerates this by treating it as a batch and answering BOTH (branch ends up solving the main session's question alongside its own). Trim also keeps the inherited transcript small, which keeps the branch's auto-memory extraction (which blocks `awaitBackgroundTasks` at the end of the branch's runner block) fast — on a 60-message inherited transcript extraction can outlast the next main turn, producing the visible "branch done last in tmux" symptom from the same incident. Wake mode and other consumers of `loadTranscript(mainSessionId)` do NOT need trim because they acquire `channelSessionLock(mainSessionId)` first and therefore by definition see a between-turn snapshot.
- `mergeBranchResultBack` returns `MergeBranchResult` (`'replaced' | 'fallback-appended' | 'skipped'`). The fallback path handles the compact-erased-placeholder edge case: if a long-running branch finishes after main turns have triggered auto-compact (which collapses the prefix into a `system` summary message that no longer carries `branchPlaceholder` metadata), the placeholder cannot be located by branchId. Without the fallback, the branch result would be silently dropped from the main transcript. With the fallback (passed as `input.fallback = { userQuery, branchSessionId, startedAt }` from the channel runner), merge-back appends a synthetic (user, assistant) pair at the end of the transcript carrying the same `branchSpawn` / `branchPlaceholder` metadata an in-place replacement would have used. The transcript stays user/assistant-alternating, so the next main turn sees the branch outcome as a normal Q+A pair. Both replace and fallback paths log to stderr so admin can grep `branch <id> merge-back ...`. Do not remove the fallback — it is the only path that keeps long branches recoverable across compact boundaries.

# LightClaw i18n Notes (Phase 19)

- All user-facing strings (slash output, banners, feishu cards, system notices, error notices visible to users) go through `t(key, args?)` from `src/i18n/index.js`. Never hardcode user-visible CN/EN strings inline.
- Two locales: `cn` (default) and `en`, defined in `src/i18n/locales.ts`. Adding a key requires adding it to BOTH; the `_shapeCheck` block at the bottom of locales.ts is a typescript-level guard that fails the build if a key exists in only one locale.
- **Stderr logging stays English** regardless of locale (admin greps logs, locale drift hurts). Only user-visible output goes through `t()`. Code comments / CLAUDE.md / git commits / test files / api-logs JSON content also stay English.
- `setLang(config.lang)` is called once at the start of `initializeApp()` (init.ts) so any subsequent t() call resolves to the configured locale. `BUILTIN_COMMANDS` is rebuilt inside `createBuiltinReplRegistry()` at call time so command descriptions/usage strings pick up the active locale (cannot be at module-top — t() would evaluate before setLang).
- Permission card text-reply normalization (`approve` / `批准` / `1` / `yes` / `y` etc) accepts BOTH languages in any locale — input parsing should never block a user just because they typed in the other language.
- Runtime error tables (`runtime/rlaunch-errors.ts`, `runtime/image-readiness.ts`, `runtime/docker.ts`, `runtime/rlaunch.ts`) currently still hardcode CN strings — they're stderr-dominant + low-frequency surfaces, deferred to a follow-up phase. New runtime errors SHOULD use `t()` so the deferred work doesn't grow.

# LightClaw Memory Extraction Notes

- Auto-memory extraction goes through the forked-agent runner (`src/agents/forked-agent.ts`) and uses tool-use (`MemoryWrite`). Do not restore the old "emit JSON text -> JSON.parse" path; long sessions with quoted or nested content can corrupt JSON text and silently lose memories.
- The extraction subagent's tool gate is `createAutoMemCanUseTool`: `MemoryWrite`, `MemoryRead`, `Read`, `Grep`, `Glob`, and read-only `Bash` are allowed; everything else, including `Write`, `Edit`, `AgentTool`, and MCP tools, is denied.
- `inProgressByDir + pendingContextByDir` coalescing (keyed by `memoryDir`) prevents high-frequency turns from spawning many extraction forks for the same user, while still allowing concurrent extractions for different users. Do not bypass it by calling the extraction inner loop directly, and do not collapse it back to a single global flag.
- `drainPendingExtraction(60_000)` must run from process exit paths. New daemon or shutdown paths need to wire the same drain.

# LightClaw autoDream Notes

- autoDream is dark-launched: `config.autoDream.enabled` defaults to `false`. Do not add a `/dream` slash or turn it on by default without a separate dogfood decision.
- The runner lives in `src/memory/dream/` and reuses `runForkedAgent`, `getLastCacheSafeParams`, and `createAutoMemCanUseTool`. Do not add a broader dream-only tool gate unless a concrete memory workflow proves the current read-only + MemoryWrite set is insufficient.
- Triggering is per canonical user: time gate, scan throttle, session-count gate, and `.consolidate-lock` all operate under that user's memory directory. The runner also defers when `isExtractionInProgressFor(memoryDir)` is true so dream and extract never write the same user's `MEMORY.md` concurrently. Never introduce a global dream lock that makes one user's consolidation block another user's.
- Dream forks run as `mode: 'subagent'` with `subagentLabel: 'auto_dream'`, so api-logs should show `kind: 'subagent'` rather than a new top-level ApiLogKind. Keep this label stable for admin grep.
- `drainPendingDream(60_000)` must stay next to `drainPendingExtraction(60_000)` in process exit paths. `/stop` must not abort dream forks; they use their own signal and are not registered in `abortControllerByUser`.

# LightClaw BackgroundTask Notes

- BackgroundTask vs AgentTool: AgentTool is immediate and returns a tool_result to the current turn; BackgroundTask is scheduled future work that returns immediately and runs later in an isolated `bg-<canonical>-<task>-<fire>` session. Do not add `schedule: now` to BackgroundTask, because that blurs the tool-choice boundary and can make the user wait for a result that will never enter the current turn.
- Schedule shapes accepted at the tool boundary: `oneshot { at: ISO8601 }`, `after { afterMinutes }` (one-time, normalized to oneshot at spawn / update time — never persisted as `'after'`), `recurring { daysOfWeek, hour, minute }`, `interval { everyMinutes, anchorAt? }`. The `'after'` shorthand exists specifically because LLMs reliably mishandle "1 minute test" / "remind me in 5 minutes" — they tend to either miscompute an ISO8601 timestamp for `oneshot` or, worse, silently fall through to `interval { everyMinutes: 1 }` and create a recurring task. Both `BackgroundTask.call` and `UpdateBackgroundTask.call` rewrite `'after'` into `'oneshot'` with `at = now + afterMinutes * 60_000` before storage; `schedule-calc.computeNextRunAt` also has a defensive `'after'` branch but stored entries should never carry that kind.
- Phase 22 surface (Iter 0–5 wired): `src/background-task/{types,store,schedule-calc,runner,scheduler,wake}.ts`, `src/agents/main-agent-can-use-tool.ts`, `src/session/branch-merge.ts`, `src/channels/feishu/bg-{completion-card,card-coordinator}.ts`, the four main-agent tools `BackgroundTask`/`ListBackgroundTasks`/`CancelBackgroundTask`/`UpdateBackgroundTask`, the wake-only tools `notify_user`/`stay_silent` (only injected via wake.ts; not in `builtinTools`), and `/branch` (alias `/b`) at the channel runner level.
- The cron/background agent is intentionally stateless. `runBackgroundTaskFire()` builds a fresh SessionContext, writes its own transcript, runs `query()` as `mode: 'subagent'` with `subagentLabel: 'background_task'`, and does not inherit parent cacheSafeParams or inject fireHistory into the prompt.
- BLOCK matrix:
  - AgentTool subagents are blocked from `BackgroundTask`, `notify_user`, and `stay_silent` (`BLOCKED_SUBAGENT_TOOLS`).
  - BackgroundTask isolated agents are blocked from recursive `BackgroundTask` and from wake-only tools (`createBackgroundTaskCanUseTool`).
  - Main agent in normal mode is blocked from `notify_user` / `stay_silent` (`createMainAgentCanUseTool('normal')`); wake mode (only path that enters via `wakeMainAgent`) flips them on.
  - AgentTool is allowed inside a BackgroundTask fire so a scheduled job can fork subagents while it runs.
- Store shape is per canonical user at `<lightclawHome>/identity/per-user/<canonical>/bg-tasks.json`, versioned as `{ version: 2, tasks: [...] }`. Each task can carry `allowedTools?: string[]`, using the same pattern syntax as `/rules allow` (`Bash(rsync:*)`, `WebFetch(api.example.com)`, `Edit(/tmp/**)`, `MCP(server:tool)`). Version 1 files lazy-migrate on read by treating missing `allowedTools` as undefined. Successful oneshot tasks are removed after completion; failed oneshots stay in the store with `lastFiredAt` so approval paths can update `allowedTools` and retry immediately. Recurring and interval tasks keep `lastFiredAt`, `consecutiveFailures`, and FIFO `fireHistory` capped to 20.
- The scheduler's resource cap is per canonical user (`backgroundTask.maxConcurrentRunsPerUser`, default 3), not global. One user filling their three fire slots must not block another user's three slots. Overflow fires queue FIFO under that user.
- Startup catchup compensates missed oneshot tasks with stagger; recurring catchup is intentionally not retroactive (next run computed forward from now). Init also calls `recoverOrphanedBranchPlaceholders(sessionsDir)` so any `/branch` placeholders left in `running` after a crash flip to `interrupted` content + status.
- Fire delivery path (`scheduler.deliverCompletion`) reads the user's `identity.channels.feishu[0]` open_id; with no Feishu binding the fire still runs but completion is logged to stderr only. `notifyTo: 'user'` pushes a card via `BackgroundTaskCardCoordinator` (success card has no buttons; ordinary failure card has `[Retry now]`; permission failure card has `[Approve & Retry]`, which merges the suggested rules into this task's `allowedTools` only, never identity-global `/rules`, and immediately queues a new fire). `notifyTo: 'agent'` instead acquires the main session's `channelSessionLock`, runs a wake `query()` with `notify_user`/`stay_silent` injected, and pushes `🔔 ${label}\n\n${text}` only when the model picks `notify_user`. Permission-denied wake prompts include denial details and tell the main agent to either `UpdateBackgroundTask({allowed_tools:[...]})` then `stay_silent`, `notify_user`, or cancel the task.
- `/branch` and `/fresh` get separate lock keys: `branch-<canonical>-<uuid>` and `fresh-<uuid>`. Both share the singleton `channelSessionLock`, so neither blocks the main session, but `appendBranchSpawnPair` and `mergeBranchResultBack` re-acquire the main `feishu-<canonical>` lock to keep main-transcript writes serialized with any in-flight main turn. Branch result text is merged back full (no truncation) — `sessionMemory.md` absorbs it as a structured finding next turn and survives compact.
- Shutdown paths must drain in this order: memory extraction, autoDream, then BackgroundTask. The CLI already calls `drainPendingBackgroundTasks(60_000)` and stops the scheduler; new daemon exits should keep that drain.
- All BackgroundTask completion-card and `/branch` placeholder strings go through `t()` (`bg.card.*`, `branch.placeholder.*`). Wake `buildWakePrompt` stays English on purpose — it's an LLM system instruction, not user-facing display.
- Cron fires and wake-mode turns construct `SessionContext` with `permissionApprover: null` ON PURPOSE. Do not attach the channel runner's Feishu approver to fire / wake contexts; a 03:00 cron fire must not hang on an orphaned approval card. Phase 23 adds the unattended fallback instead: when `requestPermission()` reaches verdict `'ask'` with no approver and `ctx.isBackgroundTask`, it allows only `BG_BUILTIN_SAFE_TOOLS` (`Read`, `Glob`, `Grep`, `TodoWrite`, `MemoryRead`, `ListBackgroundTasks`) plus `ctx.taskAllowedTools`. Everything else denies with `background-task-not-in-allowlist` and is collected into `FireOutcome.permissionDenials` with `Tool.suggestPermissionRules()`.
- High-risk permission denial rules (`Bash(rm/dd/sudo/su/sh/bash/zsh/fish/eval/mkfs.*:*)`, sensitive Edit/Write/Read paths) never go to wake mode. `scheduler.deliverCompletion()` forces them to the user permission-failure card even when `task.notifyTo === 'agent'`. The card button remains enabled because it writes only this task's `allowedTools`; it shows a warning and does not modify global `/rules`.
- `matchBashCommand` is chain-aware: it splits top-level `;` / `&&` / `||` / `|` / `&` and any segment can match a `Bash(<head>:*)` pattern. This closes the old `cd /tmp && rm -rf foo` gap for deny rules and also keeps allow behavior consistent for pipelines such as `grep foo | wc`.
