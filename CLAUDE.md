# LightClaw Runtime Safety Notes

- **Stream idle abort (Phase 38, 2026-05-24).** `query.ts` wraps every
  `streamChat()` call with a dual-threshold watchdog: TTFB
  `config.streamIdle.ttfbMs` defaults to 90s, inter-event
  `config.streamIdle.interEventMs` defaults to 30s. When either budget is
  exceeded, it aborts the upstream request with `IdleStreamError`, writes a
  `[stream-idle-abort] ... kind=<ttfb|inter-event>` stderr line, and reuses
  the per-turn transient retry path. The existing `[ttfb]` line remains the
  first-event observability marker; undici's transport timeout is only the
  backstop now.
- **Provider keepalive contract (Phase 38).** `StreamEvent { type:
  'keepalive' }` is framework-internal only: `query.ts` refreshes the stream
  idle clock and then continues, so keepalives must never become assistant
  text, tool dispatch, transcript content, or channel output. Providers emit
  keepalives from three sources, all yielded as the same framework event:
  - **reasoning-derived (`reason:'reasoning'`)** — `openai-auth` Responses
    `response.reasoning_summary*`, OpenAI-compatible Chat Completions
    `reasoning_content` / string `reasoning`, and Anthropic
    `thinking_delta`. These mark non-visible reasoning activity.
  - **transport-derived (`reason:'transport'`)** — wire-level heartbeats the
    upstream server emits when no business event flows: `openai-auth`
    `event:keepalive` (probed 2026-05-25 at ~30s cadence; `data` carries
    `{type:'keepalive', sequence_number:N}`, SDK passes through with
    `event.type === 'keepalive'`), and Anthropic `ping`. Forwarding these
    keeps the idle clock anchored to wire activity rather than business
    events — without it, long legal hidden reasoning trips the inter-event
    watchdog as false hung, exactly the 2026-05-25 dogfood false-positive.
  - **tool-args-derived (`reason:'tool-args'`)** — provider deltas that
    accumulate a tool call's JSON arguments without otherwise yielding to
    the consumer: `openai-auth` `response.function_call_arguments.delta`,
    OpenAI Chat Completions `delta.tool_calls[*].function.arguments`, and
    Anthropic `input_json_delta.partial_json`. Pre-Phase-38-followup these
    were silently consumed into provider-internal accumulator slots,
    leaving `query.ts`'s watchdog blind from `output_item.added`(function_call)
    / `content_block_start`(tool_use) through `output_item.done` /
    `content_block_stop`. A long-args streaming response — typical for
    `Dispatch` calls with 3-5 KB structured prompts — would falsely trip
    the inter-event abort even though codex / openai / anthropic were
    actively emitting deltas every 20-200ms. 2026-05-26 dogfood: 4/4
    Dispatch JSON truncations with `kind=inter-event ms=35001-39501ms`
    followed by `function_call args invalid JSON ... position 2740-4686`.
    Every provider now emits `{type:'keepalive', reason:'tool-args'}` on
    each non-empty tool-args wire chunk so the watchdog clock resets on
    wire activity, mirroring the reasoning_summary forwarding. The empty
    `partial_json: ''` / `delta: ''` defensive case does not yield —
    matching the `output_text.delta` / `thinking_delta` empty-string guard
    convention. Per-chunk yield for `openai`'s Chat Completions path is
    deduped to one event per chunk even when several parallel
    `tool_calls[]` entries fire in the same chunk: one keepalive per wire
    chunk is sufficient to anchor the clock, and emitting one per parallel
    tool call would flood the event stream with redundant resets.
  `openai-auth` overrides `Provider.idleTimeouts` to `35s/35s`: ~30s keepalive
  cadence + ~5s grace, tight enough that a real proxy/TCP stall (no
  heartbeat received) trips abort fast. Other providers fall through to
  `config.streamIdle` global defaults (90s/30s). Do not prompt-engineer
  around any of this — it is provider plumbing.
  When adding a new provider, **audit every accumulator path** (tool args
  JSON, structured output deltas, embedded function-call streams) and
  ensure the corresponding wire delta yields a framework keepalive. The
  pattern is: if your provider has an `acc += delta` line in the stream
  loop without a `yield` on the same wire event, the watchdog will go
  blind for as long as that accumulator stays open.
- **A provider must throw on an empty / dead stream, never synthesize a vacuous `end_turn` (2026-06-23).** When the upstream SSE connection closes with zero business events — or emits only heartbeats and never reaches a terminal frame (`response.completed` / `response.failed` / `response.incomplete` for Responses, a `finish_reason` for Chat Completions, `message_stop` for Anthropic) — the post-loop `stopReason ?? 'end_turn'` fallback would otherwise persist a `content: [], stopReason: 'end_turn', usage: {}` stop event. `query.ts` accepts that as a finished turn; main with no `in_progress` todo then ends silently and the user sees "no reply" (0.3.4 dogfood: gpt-codex-high / codex-default, an upstream/proxy link that also threw TTFB idle aborts on the same window). All three providers now track a `sawAnyEvent` / `sawAnyChunk` flag and throw `"… stream returned no events …"` when the stream is empty OR `(content empty && stopReason null && usage empty)`. The message substring is matched by `transient-error.ts`'s `TRANSIENT_FAILURE_PATTERN`, so the failure routes into `query.ts`'s per-turn transient retry + `recycleConnections` — the SAME recovery path a TTFB idle abort uses (an idle abort throws `IdleStreamError` and never yields a stop event, so it can NOT itself produce the vacuous record; the two are distinct upstream-failure signatures). A genuine empty completion (a real terminal frame → `stopReason` AND `usage` both set) is deliberately NOT caught and stays a legitimate empty `end_turn`. When adding a new provider, mirror this guard alongside the keepalive audit above — an `acc`-then-synthesize stream loop with no empty-stream throw silently reintroduces the no-reply bug.
- LocalRuntime is admin-only. When `runtime.backend = "local"`, paired non-admin users must not acquire a runtime; multi-user service must use DockerRuntime or RlaunchRuntime.
- Do not add path-string workspace guards to tools, permission policy, OR runtime backends. Runtime safety comes from the LocalRuntime admin-only gate, Docker/Rlaunch isolation, read-only mounts, and the Phase 5 permission system. `toContainerPath` in docker.ts / rlaunch.ts accepts any absolute path post-normalize: workspace + mountTable hits get translated, everything else (`/tmp`, `/etc`, `/proc`, …) passes through as the container-local path so LayeredDataPlane's `exec-relay` layer runs the command inside the worker pod where it sees the image's own filesystem (e.g. container `/etc/passwd` is the image's, not the host's). Relative paths still throw — backends only legitimately see absolute paths. **Do not re-add the "Path is not within {RuntimeKind}Runtime workspace: …" guard**; that was leftover technical debt from 18ff987's sweep that this runtime-fs-cleanup phase completed.
- **RlaunchRuntime never puts bulk bytes on the brainctl exec channel — in either direction.** brainctl exec is a control channel only; its websocket exec stream silently drops bytes on large payloads (the `9cafbdc` stdin incident: ~16% writeFile corruption; the 6 MB PDF stdout byte-mismatch dogfood bug). brainctl exec stdout therefore carries only control-shape data, never tool output:
  - `ExecInput.stdin` is unsupported — `runBrainctlExec` throws if it is set. Callers stage payloads via `fs.writeFile` instead. The base64-inline-stdin path, the 32 KB inline cap, and the chunked writeFile are all deleted.
  - Every non-privileged (agent-dispatched) exec runs in **capture mode**: `composeExecScript` redirects the command's stdout/stderr to per-call files under `<workspaceRoot>/.lightclaw/exec/` — `{ <cmd>; } 2> <err> | head -c <maxBytes> > <out>` — and brainctl stdout carries only a `LIGHTCLAW_EXIT:<n>` marker. `collectExecOutput` parses the marker, reads the two files host-side via the gpfs mount (`shared-cluster-fs`), and deletes them. `head -c` is a real pipeline stage (not process substitution): a runaway stdout takes SIGPIPE and dies so it cannot fill the mount, and the wrapped bash does not exit until head drains so there is no read-before-flush race. stderr goes straight to a file (host-capped on read; a stderr-only runaway is bounded by the exec timeout). When the marker is **absent** the wrapped script never ran (a brainctl-level failure) — the raw brainctl result is returned so `exec()`'s `isWorkerLostError` still sees the real control-plane envelope.
  - Privileged bootstrap execs (`chownWorkspaceOnce`, `stageHelpersOnce`) keep brainctl's own stdout: they run as root, so capture files would be root-owned and unreadable by the non-root daemon, and their output is small / log-only. Capture mode is therefore always setpriv-wrapped — `composeExecScript` throws if `capture` is set without `dropPrivileges`.
  - Per-call scratch basenames are `<canonicalUser>-<uuid>.{out,err,read,write}`. The rlaunch worker (and its single `.lightclaw/exec/` dir) is shared by every session and dispatched worker of one canonical user, so `randomUUID` is what prevents concurrent execs from colliding; the canonical-user prefix is a human-readable marker. Normal execs delete their scratch files inline; `inbox-aging` sweeps `.lightclaw/exec/` on a 6h TTL (vs. the 7d inbox/downloads TTL) purely as a backstop for daemon-crash-mid-exec stragglers.
- **Three-plane runtime model (Phase 33)**. Every backend composes `ControlPlane` (exec + lifecycle), `DataPlane` (read/write/stat/readdir), and `PathPolicy` (worker↔host translation + path gate). Compatibility shims remain: existing tools still call `runtime.exec(...)` / `runtime.fs.*`, where `runtime.fs === runtime.data` and `runtime.exec` routes through `runtime.control.exec`. (Phase 35 retired `DataPlane.glob` along with the sandbox `glob.py` helper — Glob tool now runs `rg --files --glob ... --sort=modified` exclusively and falls back to a `Bash`-with-`find` hint when rg is missing.)
- **`runtime.scratchRoot` is fast local disk; `runtime.workspaceRoot` is the persistent (often GPFS-backed) workspace.** Every backend exposes both. On cluster deployments the workspace mount is GPFS, whose small-file metadata ops run ~50x slower than local disk — a `git clone` that writes thousands of small objects/files pathologically slows down there. `scratchRoot` always points at genuine node-local / container-local disk for IO-heavy throwaway work: DockerRuntime → `/scratch` on the container's writable rootfs layer (overlay2 on the daemon host's local disk, bounded by the existing `storageOptSize` cap); RlaunchRuntime → `/scratch` on the worker pod's own node-local filesystem (NOT a gpfs mount); LocalRuntime → an OS temp dir. It is **ephemeral** — wiped on `/sandbox reset`, container removal, or worker restart — so anything that must persist has to be copied into `workspaceRoot` explicitly. Provisioning is best-effort and memoized per container/worker lifecycle: DockerRuntime's `ensureScratchDir` runs a privileged (`-u 0`) `mkdir -p /scratch && chmod 1777` (root, because the fs root is not writable by the image's unprivileged user; `1777` then lets unprivileged execs write); RlaunchRuntime's `ensureScratchDir` does the same as a privileged brainctl exec, ordered right after `ensureWorkspaceChowned` and re-run on respawn. Failures are loud (stderr) but non-fatal — git-heavy work just falls back to the slower workspace mount. `/scratch` is intentionally NOT in the mount table: harness file IO to it goes through `exec-relay`, while git itself runs inside the sandbox via `Bash` at local-disk speed.
- **An exec timeout / abort / maxBuffer kill takes down the whole process tree, not just the direct child (Bug 4).** Two layers, because the orphan lives in a different place per backend:
  - **`runProcess` (daemon side, all backends).** Children are `spawn`ed `detached` so the pid is also a process-group leader; `signalProcessGroup(child, sig)` signals `-pid` (the group). The timeout / abort / maxBuffer paths SIGTERM the group, and `finish()` does one synchronous SIGKILL sweep of the group when a kill was initiated so a descendant that ignored SIGTERM (or outlived the parent) is reaped instead of leaking. This fully covers **LocalRuntime** (the spawned `bash` tree is local). For DockerRuntime / RlaunchRuntime it only reaps the local `docker` / `brainctl` CLI client — the in-container / in-worker process is owned by the container runtime and is NOT a child of that client.
  - **`wrapSandboxCommandWithTimeout` (`exec-wrap.ts`, Docker + Rlaunch).** `DockerRuntime.exec` / `RlaunchRuntime.exec` wrap the agent command so the sandbox enforces its own timeout: the command runs via `setsid` in a fresh process group with an in-sandbox watchdog that SIGTERMs then SIGKILLs that group after the budget. Because the watchdog runs *inside* the sandbox it still fires when the control-plane client is killed and the wrapper shell is orphaned — the in-sandbox tree self-terminates within `budget + grace` instead of leaking until the container / worker lifecycle reaps it. The daemon-side `runProcess` timeout is bumped to `sandboxBackstopTimeoutMs(budget)` so the in-sandbox watchdog always resolves first and the daemon timeout is a pure backstop for a wedged control plane. Docker skips the wrap when `input.stdin` is set (harness-internal `execRelayFs.writeFile` — fast, spawns no tree, and its stdin should not detour through the wrapper's setsid child); Rlaunch wraps every `exec()` call (privileged bootstrap execs call `runBrainctlExec` directly and stay unwrapped). Depends on `setsid` (util-linux), same dependency posture as `setpriv`. A command that finishes on its own is unaffected — the wrapper forwards its stdout / stderr / exit code; a timed-out one exits 143/137 with a `lightclaw: command exceeded the <n>s sandbox time limit` stderr line (it does NOT start with `error:` so the worker-lost detector ignores it).
- **Runtime data transport is a backend decision, not the sandbox boundary.** The boundary is layered: each backend's `toContainerPath` does only one job — translate input paths to a container-shape absolute path. Workspace + mountTable hits get mapped to their container prefix; other absolute paths (`/tmp`, `/etc`, `/proc`, …) pass through unchanged so the LayeredDataPlane's `exec-relay` layer can run the command inside the container. `path.posix.normalize` folds `..` segments before the absolute-path check, so traversal-shaped inputs land at a normalized absolute path the container resolves naturally. `PathPolicy.isAllowed(p, op)` adds one gate on top: it rejects writes to mounts declared `mode: 'ro'` BEFORE any layer runs, because daemon-side `bind-mount` / `shared-cluster-fs` layers have host write permission and would otherwise bypass the worker-visible read-only flag. `PathPolicy.toHostPath(p)` returns `null` outside the mount table so host-fs layers fall through to `exec-relay`. DataPlane layers choose the byte path: Local uses `host-direct`; Docker uses `[bind-mount, exec-relay]`; Rlaunch uses `[shared-cluster-fs, exec-relay]`. Read/Write/Edit on `/tmp/foo` therefore Just Works — shared-cluster-fs self-filters via `isShared`, exec-relay reads `/tmp/foo` in the worker pod via brainctl. Pre-runtime-fs-cleanup the toContainerPath workspace guard rejected these paths string-side and forced agents to fall back to `Bash + python` heredocs; that guard is gone.
- **Rlaunch file IO never traverses the brainctl channel.** In-mount paths (`/workspace/...`) read/write through the host-visible gpfs path via `shared-cluster-fs` (zero-copy). Container-local paths (`/tmp`, `/etc`, …) go through `exec-relay`, which `cp`s the file between the target and a `.lightclaw/exec/` scratch file and does the actual byte read/write host-side over the gpfs mount — `readFileViaExec` (the old `base64 -w 0` over brainctl stdout) and the chunked base64 writeFile are deleted, so there is no byte-mismatch surface left to verify against. `stdoutByteReliability = 'unreliable-large'` still describes the brainctl transport accurately; we simply never put bulk bytes on it anymore.
- **Rlaunch worker uid alignment (chown bootstrap + setpriv exec wrap).** The kubebrain ml-base image starts worker PID 1 as root. The daemon process runs as the operator's non-root uid (typically uid 10250 in the cluster's dev VPS). Pre-uid-alignment this mismatch made `shared-cluster-fs` write paths (the Phase 33 primary byte path for in-workspace Read/Write/Edit) hit EACCES whenever the worker had previously created root-owned files in the shared gpfs mount — the most visible symptom was `Edit` failing on a `git worktree add`-spawned source tree the agent itself had just created. Fix is two coordinated moves:
  - **One-time chown on worker start.** `RlaunchRuntime.ensureRunning()` calls `chownWorkspaceOnce()` BEFORE `stageHelpersOnce()`, which runs `mkdir -p <workspaceRoot> && chown -R <daemonUid>:<daemonGid> <workspaceRoot> || true` inside the worker (privileged exec, no setpriv wrap because worker PID 1 is the only entity with `CAP_CHOWN` over the gpfs mount). Idempotent — already-correct entries are no-ops. Memoized per `workerName`; worker respawn re-runs. Failures are loud (stderr) but non-fatal: layered fall-through still works through exec-relay.
  - **setpriv-wrapped exec for unprivileged calls.** `composeExecScript` accepts a `dropPrivileges: { uid, gid }` option. `wrapCommand` populates it from `cfg.daemonUid / daemonGid` (defaulting to `process.getuid() / getgid()` at `buildRlaunchRuntimeConfig` time) UNLESS the caller sets `ExecInput.privileged = true`. Every agent-dispatched tool call lands inside the container as the daemon uid; files it creates (`git worktree add`, `pnpm install`, `cat > foo` from Bash, …) are daemon-owned, so shared-cluster-fs subsequent reads/writes have no EACCES surface. Privileged no-capture shape: `<env> cd <cwd> && setpriv --reuid=<uid> --regid=<gid> --clear-groups --inh-caps=-all -- bash -c <quoted body>`. The unprivileged tool path additionally runs in capture mode (output redirected to `.lightclaw/exec/` files, `cd` applied inside the wrapped bash) — see the brainctl-exec-channel bullet above. `--clear-groups` drops supplementary groups; `--inh-caps=-all` drops inheritable capabilities so children can't re-acquire privilege. **Only bootstrap callers** (`chownWorkspaceOnce`, `stageHelpersOnce` apt + pip, future NetworkBridge iptables) set `privileged: true` to keep root. Tool code must NEVER set `privileged: true`. The image is required to ship `setpriv` (Ubuntu 22.04 ml-base does, it's in util-linux).
  - **Order**: chown → stage-helpers → tool exec (with setpriv). Re-doing chown on respawn keeps freshly-spawned workers self-healing without operator intervention.
- **`RlaunchRuntime.exec` retries once before respawning on `isWorkerLostError`.** The 5-substring keyword set (`not found` / `connection refused` / `unable to upgrade connection` / `unavailable process` / `cannot exec into a container`) matches both legitimate worker death and brainctl control-plane / kubelet websocket transients. **Exit 127 short-circuit (2026-05-13)**: POSIX shell "command not found" returns exit 127 and would otherwise trip the broad 'not found' substring (`bash: line 1: rg: command not found` once per Glob/Grep when the rlaunch ml-base image lacked ripgrep — pre-fix the runtime respawned the worker on every Glob/Grep call). brainctl / kubelet faults surface as non-127 exits (typically 1, or 137 on SIGKILL), so the guard is safe — never weaken it without auditing for a real-worker-death path that exits 127 (none observed to date). Companion fix on the trigger side: `stageHelpersOnce` now installs `ripgrep` + `jq` alongside `poppler-utils` (~5–6 s extra apt time, well under the 240 s budget) and the probe checks `command -v rg` + `command -v jq` so a partial-staged worker re-runs the apt step. **Envelope-line anchor (2026-05-15)**: the substring scan is now restricted to stderr lines beginning with `error:` or `Error from server` — the two envelopes brainctl / kubectl use for every real failure (Stopped worker: `error: cannot exec into a container in an unavailable process: Stopped`; deleted worker: `Error from server (NotFound): processes.workspace.brainpp.cn "ws-..." not found`; websocket / kubelet faults: `Error from server: unable to upgrade connection: ...`). Pre-fix the scan covered stderr+stdout in full and tripped on any user-program output that happened to print one of the 5 substrings — a Python heredoc `raise SystemExit('runner query block start not found')` then `&&`-falling through to `pnpm typecheck` (exit 2) was enough to respawn a healthy worker mid-task. The exit-127 short-circuit only protected the shell-emitted `command not found` case; the line anchor closes the general user-output surface without weakening real death detection. Do NOT remove the anchor without an enumeration of brainctl / kubectl error shapes that lack both prefixes — none observed to date. 2026-05-12 dogfood confirmed a separate false-positive class: brainctl returned one of these patterns while the original worker was still alive on the cluster, runtime respawned a fresh worker, and the old worker leaked until the cluster GC window kicked in (default 1h). Mitigation: log the original brainctl stderr (otherwise lost — `runBrainctlExec` writes nothing to daemon stderr on failure) and retry once after a 1s pause (`workerLostRetryDelayMs`, exported test override). Real worker death survives the retry; transient blips usually clear within a second. Three diagnostic stderr lines now flank the decision: "worker-lost-like error … (retry in 1s before respawn)", then either "retry recovered … first error was a transient" (preserve worker) or "retry still failed … respawning" (real death). Caller-side abort during the retry sleep is honored — the original failed result is returned and the runtime does NOT respawn behind the caller's back. Do NOT remove the retry layer without first checking dogfood stderr for "retry recovered" lines; they directly indicate dirt the broad keyword set would otherwise have eaten.
- **Harness-internal fast IO (`writeFileViaHostMount` / `readFileViaHostMount`)** remains available for channel encoders and media materialization. These optional methods preserve the old `null` fallback contract and existing `[rlaunch] host-mount fast ... disabled` stderr lines; they are now compatibility helpers beside the primary DataPlane path, not the only safe host-mount route.
- **Startup mount probe (Phase 33 follow-up).** `DockerRuntime.start()` and `RlaunchRuntime._startOnce()` call `assertMountsAccessible(this.paths, kind)` before any docker/brainctl action. The probe runs `fsp.access(mount.host, R_OK | (mode==='rw' ? W_OK : 0))` for every entry in `policy.mountTable` and throws a `[<kind>] runtime mount <worker> (host=<host>, mode=<mode>) is not accessible from daemon (<errno>): <msg>. Fix the host path / permissions, or remove the entry from runtime.<kind>.mounts.` on first failure. Rationale: without this, a misconfigured bind-mount / shared-cluster-fs entry (wrong host path, EACCES on the host prefix, gpfs not mounted on daemon node) only surfaces as a `[runtime] ...-fs disabled ... falling back to control-plane relay` stderr line on the first tool call, silently re-routing reads through `docker exec` / `brainctl exec` stdout — the exact failure mode that re-creates the Bug 1 byte-mismatch risk for large reads. Hard-fail at start is the right tradeoff: admin's "run lightclaw" attempt already checks host paths, so a transient delayed mount is not in scope; sticky-disabled mid-run blips stay handled by the per-layer guard. LocalRuntime has an empty mount table and is a probe no-op. Do NOT add `mkdir -p` to the probe — the workspace path is auto-mkdir'd by `RuntimePool.acquire` (`pool.ts:334`) before the runtime constructor runs, and extra mounts are admin-controlled territory.
- **`RuntimeAvailability.retryable` separates soft backoff from fatal unavailability.** Every `ok:false` branch in `rlaunch.ts:isAvailable` / `docker.ts:isAvailable` must set `retryable: boolean`. `worker-scheduling`, `image-pulling`, `image-not-attempted` are `retryable: true` (the next agent turn or a short wait can recover); `worker-failed`, `image-failed`, `worker-quota-denied`, `autopull-disabled` are `retryable: false`. `query.ts`' environment-domain gate maps `retryable:true` to `is_error:false` on the synthesized `tool_result` (Bug 12 from 2026-05-12 dogfood: a `worker-scheduling` body with `is_error:true` reads to the model as "tool call failed" → apology + don't-retry; the right semantics is "service unavailable, try again next turn" which `is_error:false` carries). Retryable bodies also get a trailing `[runtime: <reason>, retryable]` marker so the model can pattern-match on it. When adding a new `RuntimeAvailability` reason, classify it explicitly — if you're not sure whether the next turn can recover unaided, the default is `retryable:false` (admin must intervene), never omit the field.
- **Provider content drop reporting via static probe**. Each provider exposes `detectStaticDropKinds()` for top-level user-message attachments and `detectStaticDropKindsInToolResult()` for blocks nested under `tool_result.content`. Both probes run the provider's real message-shape translator (`convertMessages*`) with synthetic empty-base64 blocks and report the `AttachmentKind`s that cannot be represented on the wire. `getProviderFor()` runs the probes ONCE per `(endpoint, upstreamModel)` on first lookup and reconciles the v2 on-disk cache at `(kind, position)` where `position` is `inUserMessage` or `inToolResult`. Single source of truth — `streamChat` and static probes must not drift because the probes literally run the converter. New provider authors must add both probes when the two positions differ.
- **The capability cache is a converter/position cache with runtime counters, not an API capability oracle**. `capabilities-cache.json` records `{enabled, failures}` per `(endpoint, upstreamModel, kind, position)`. Static converter drops precharge `enabled:false`; converter-emitted kinds precharge/retain `enabled:true` unless a previous runtime-disabled entry already exists. Runtime 4xx capability signals do not permanently flip on the first failure anymore: the current request may retry with a forced text/path fallback, but only the fifth consecutive failure for that exact key persists `enabled:false`. Any successful wire call resets failure counters for that model. `/model --clear-cache` deletes the selected model's cache entry and clears the in-process precharge memo so the next lookup re-probes from code. Never present this file as "the API supports X"; it is "this converter/model/path is currently safe to emit X here".
- **Adding a new `AttachmentKind` requires three coordinated edits.** The static probe is single-source-of-truth ONLY when these stay in sync — otherwise the new kind silently bypasses precharge and you pay first-turn waste forever (the runtime `content_dropped` event was retired 2026-05-10, no other backstop precedes the wire). When extending `AttachmentKind` in `provider/types.ts` to add e.g. `'archive'` / `'mesh'` / whatever future modality:
  1. Add a probe block of that kind to **every** provider's `detectStaticDropKinds()` synthetic message (`anthropic.ts` / `openai.ts` / `openai-auth.ts` and any future provider). Empty base64 is fine — the probe doesn't care about content.
  2. Add a corresponding case in **every** provider's local `classifyUnsupportedBlock(blockType)` mapping (e.g. `if (blockType === 'archive') return 'archive'`). Forgetting this means the probe sees the block, but the classifier returns `null`, and the kind never enters the dropped Set even when the wire schema doesn't accept it.
  3. Update encoder/finalizer paths in `channels/attachment-encoding.ts`, `provider/multimodal-finalization.ts`, and any tool that emits `ToolResultContentBlock` so both positions either emit the new block or intentionally fall back.

  The reactive 4xx catch in `channels/runner.ts` still records runtime failures when a wire error names the kind (`isCapabilityMissingError` pattern-matches common provider messages), but it is counter-based and position-aware. Static probe is the path that prevents first-turn waste; #1 + #2 must stay in sync to preserve that property.

# LightClaw Cwd Layout Notes (Phase 24)

- `<cwd>/.lightclaw/` is a data write area, never a code discovery root. LightClaw writes inside this namespace fall into two categories:
  - **Persistent, agent-readable**: `inbox/<chatId>/<fileName>` for incoming channel media (`runtime.fs.writeFile`); `downloads/<fileName>` for WebFetch binary responses (PDF / images / archives / office docs — written daemon-side by `src/tools/web-fetch-*.ts` and pushed into the workspace via `runtime.fs.writeFile`, no chat-namespace because WebFetch has no natural namespace key). The agent can `Read` / `AnalyzeVisuals` / `Bash` these via `<workspaceRoot>/.lightclaw/<inbox|downloads>/...`. Both are aged out by the per-canonical-user `inbox-aging` sweep (Hermes-style hourly mtime scan, default ttl 7 days, configurable via `channels.feishu.inboxAging`); `inbox/` is two-deep and `downloads/` is flat, but they share the same TTL since they are the same class of cache. WebFetch always appends a 6-char random suffix to the URL-derived basename so repeated fetches of the same URL never silently overwrite, and the mime-derived extension is authoritative (URL paths like `arxiv.org/pdf/2509.25721` would otherwise confuse `os.path.splitext` into treating `.25721` as an extension).
  - **Ephemeral, tool-internal**: `tmp/pdf-pages/<uuid>/page-N.jpg` (PDF visual fallback), `tmp/pdf-slices/<uuid>/selected-pages.pdf` (Read inline-PDF page slices via `pdfseparate`/`pdfunite`), and `tmp/resize/<uuid>.jpg` (vision resize subroutine output). These are deleted by the producing tool's `finally` block; inbox-aging will pick up stragglers only on a process crash mid-tool-call. Never agent-readable as artifacts — they exist for the duration of a single tool call.
- Hook / MCP discovery is admin-side only: `<lightclawHome>/hooks/` and `<lightclawHome>/mcp.json`. Skill discovery is bundled skills plus per-canonical-user skills under `<lightclawHome>/users/<canonical>/skills/`; `<lightclawHome>/skills/` is no longer scanned. Do not reintroduce a project-layer scan path under `<cwd>/.lightclaw/` even if Claude Code does.
- Channel attachments sink in two phases: Feishu `onMessage` attaches `pendingAttachment` metadata to `NormalizedChannelMessage`; `ChannelRunner` materializes it after pairing and runtime acquire via `ChannelRunnerStrategy.materializeAttachment`. New channel adapters should follow the same shape: channel code does not touch identity or runtime pools directly.
- LightClaw deliberately does NOT register persistent attachments in any sidecar registry / index. Path-as-handle is sufficient for local files; cloud documents (PR4 Feishu collab) will pass tokens directly as tool arguments. This matches Claude Code / OpenClaw / Hermes — none ship an artifact registry. If a future feature genuinely needs cross-session lookup or token-as-handle, scope the abstraction narrowly to that feature instead of resurrecting a global registry.

# Secret Injection Model (Phase 18)

- **Per-user runtime secrets** are stored at `<lightclawHome>/users/<canonical>/state/secrets.json` (0o600, alongside `permissions.json` and `rlaunch-mounts.json`). Each entry has `{value, enabled, updatedAt}`. Values never leave this file / daemon memory / a single `ExecInput.env` injection — they never appear in transcripts, api logs, fork transcripts, memory, or signal payloads.
- **Injection point** is `src/tools/bash.ts` only. The agent references enabled secrets as `$NAME` in Bash commands; shell expansion happens inside the sandbox, so the model-written command string only ever contains the literal `$NAME`. All three runtime backends (LocalRuntime / DockerRuntime / RlaunchRuntime) pipe `ExecInput.env` through their existing env paths — no backend-specific code lives in the secret store.
- **Secrets reach only top-level main-dispatched fires — every deeper / internal dispatch is stripped (2026-06-14, was main-only 2026-05-31).** The gate is `resolveDispatchedFireSecrets(chainState, role, canonicalUser)` in `src/agents/dispatch-secrets.ts`: eligible iff the dispatcher node `chainState.path.at(-2)` is the orchestrator (`getAgent(role).kind === 'orchestrator'`, i.e. a depth-1 fire main dispatched directly) AND the callee is not `kind:'internal'` — then it returns the owner's `loadEnabledSecrets(canonicalUser)` from disk, else `undefined`. **Two call sites feed it the SAME `chainState` so the grant can never drift between a fire's first shift and a resumed one:** (1) `runDispatchedAgent` (initial fire) reads `params.chainState`; (2) `resumeRunWithBlock` reloads the chainState from the backing bg entry (`loadBackgroundTasks().find(e => e.taskRunId === run.id)?.chainState`) — a `TaskRunMeta` carries no chainState, and the entry's is exactly what the fire was dispatched with. Both sites set `childCtx.enabledSecrets` explicitly (overriding the `{ ...currentCtx }` spread) AND pass the same map into `buildPromptForRole({ enabledSecrets })`, so the worker's `## Available Secrets` section (the existing `formatAvailableSecretsSection` helper, byte-identical to main's) renders from the same source as the env injection. Rationale: a scheduled/background fire dispatched by main is the owner's manager running the owner's own work unattended (authenticated git clone/push) — there is no main "in the loop" to funnel through, unlike a mid-chain sub-worker. A grandchild dispatched by a sub-worker (dispatcher is a worker, not main) and all internal maintenance roles run with no secrets in `bash.ts`'s `getCurrentEnabledSecrets()`, so a secret never propagates further down a chain than the single fire main authorized. Do NOT widen this to all dispatched workers, remove the dispatcher-kind gate, or `loadEnabledSecrets` unconditionally on resume (that would leak to resumed sub-worker shifts). The 2026-05-31 dead-weight load on `background-task/runner.ts`'s parent ctx stays removed — the load lives only behind this gate.
- **Lifecycle**: `set` writes to disk; `enable` flips a flag; the channel runner loads enabled secrets per inbound turn (so admin `enable` / `disable` are next-turn-effective); `remove` deletes the entry.
- **Entry points**: `/secret set <NAME> <VALUE>` only. The agent supplies its own value, stored in its own per-user library — no cross-boundary resource access. The earlier `import-env` / `import-file` subcommands were removed (2026-05-28): `/secret` is open to every paired user (not admin-gated), but `import-env` read the daemon's shared `process.env` and `import-file` read any absolute path's first line, so a non-admin user could enumerate daemon env vars or exfiltrate arbitrary host files (`/etc/passwd`, `~/.ssh/id_rsa`) into their own secret store and `echo` them in Bash. The reserved-name denylist only covered a handful of env names and could not bound arbitrary file reads. `set` carries the chat-history-leak caveat (value lands in Feishu history — recommend throwaway tokens); an admin avoiding that can edit `secrets.json` directly (they have host access). If a no-chat-leak admin path is ever needed again, gate it `admin`-only AND drop arbitrary file reads.
- **Audit** at `<lightclawHome>/audit/secret-ops/<YYYY-MM-DD>.jsonl` (derives from `<home>`; §十 removed the per-subdir `paths.audit` / `LIGHTCLAW_AUDIT_DIR` overrides). Records `{ts, user, op, name, source}` — never values or masked previews.
- **What this does NOT prevent**: the model echoing `$TOKEN` into stdout (V1 mitigation is the `## Available Secrets` prompt warning; V2 may add stdout redaction); the model writing the value to a workspace file via Bash (same caveat). The threat model covers framework-controlled surfaces only.
- **Not for**: model API keys (those stay in `endpoints.*.apiKey`), Feishu app secret (`channels.feishu.appSecret`), Brave key (`tools.webSearch.braveApiKey`). Those are deployment-level, statically read at daemon start. Per-user runtime secrets are an orthogonal domain.

# LightClaw Feishu Reply Quote Context Notes (Phase 28)

- Feishu reply messages carry `message.parent_id`. Both WS and webhook transports must preserve it as `FeishuRawMessage.parentId`; `rootId` remains reply-chain metadata and must not affect session routing.
- `ParentMessageFetcher` is best-effort and channel-local. It calls `im.v1.message.get` for exactly one parent hop, parses `{ text, mediaKeys, senderOpenId }`, resolves sender name cosmetically through `fetchFeishuUserInfo`, truncates text, caps media keys, and caches both success and fail-soft null results in an in-memory LRU. Fetch failures never block the inbound turn: log one stderr line and proceed as if the message had no quote.

Do not add a second attachment registry or duplicate inline blocks just for quotes.

This is what enables the intended group flow: user sends a file, then replies to that file with `@LightClaw ...`, and the reply carries the file through `parent_id`.

Keep this shape so quoted mid-flight follow-ups use the same decision framework as plain interjections.
- V1 is depth=1 only. If the parent itself is a reply, do not recursively fetch ancestors. Future quote-chain work should add an explicit depth limit and cycle guard instead of changing this implicit one-hop contract.

# LightClaw Feishu Cloud Docs Notes (PR4)

- Tool names encode lifecycle, not transport. `FeishuCreateFile` creates a new cloud resource and therefore takes no source URL; `FeishuWriteDoc` / `FeishuWriteSheet` edit an existing resource and must receive either an explicit URL or a direct token input. Do not blur these paths into a generic verb bag: create tools allocate new Feishu resources, write tools mutate existing ones, and `FeishuRead` is the single read entry for pasted URLs / direct tokens.
- `FeishuCreateFile.kind` is intentionally V1-narrow: only `'doc'` is supported. If future sheet / bitable creation is added, follow the PR4 read-input style with nested discriminants (`sheet: { ... }`, `bitable: { ... }`) instead of widening the current flat `kind` switch into many unrelated optional fields.
- `FeishuWriteConfirm` is a virtual permission ask name. It is not in `builtinTools`, must not appear in the LLM-visible tool catalog, and exists only so the channel approver can render an approval card and the audit log can tag write decisions consistently. The ask is plain `riskLevel: 'write'` — users may grant `[a] 以后都允许` to skip future prompts for the same scope, matching how every other write tool (`Edit`, `Write`, `Bash(<head>:*)`) behaves. Only `FeishuDeleteConfirm` is forced to once-only; see Phase 34 notes.
- Feishu write audit records live at `<lightclawHome>/audit/feishu-writes/<YYYY-MM-DD>.jsonl`. This directory is a sibling of `sessions/`, `memory/`, and `identity/`, not part of any project workspace or per-cwd artifact store. Write tools must append `confirmed`, `denied`, and `failed` outcomes there before returning.
- Canonical resource routing stays centralized. `wiki` URLs resolve one hop through the wiki node API to `objType` and then route to docx or sheet readers; `bitable` and generic `file` URLs are parsed into canonical resource shapes but their capabilities are empty in V1, so tools return an early unsupported hint instead of attempting SDK read/write calls.
- Phase 29 V1.5 search uses `name`, `searchHint`, and `description` weighted scoring. The four Feishu cloud-doc tools carry search hints so users can discover them with natural Feishu/doc/sheet/link phrases; older Phase 29 tools keep their existing metadata and should not be churned just because PR4 added hints.
- Privacy decision for pasted cloud URLs matches reply quotes: an explicit URL in a user message is treated as explicit share intent for that turn, even if the URL was not attached via Feishu message media. `ParentMessageFetcher` does not get a second approval layer for this V1; future stricter policy should be documented as a new privacy model, not slipped into URL parsing.
- **`FeishuCreateFile` performs initial permission grants automatically and best-effort.** Bot is the doc owner; without these grants the link returned in tool_result is 403 for the very user who asked the bot to create it (Bug 9 from 2026-05-12 dogfood). Strategy:
  - **DM session** (`sessionId` parses to `{kind:'dm'}`) → grant sender `full_access` only. Chat-level grant is intentionally skipped — DM has exactly two members (bot + sender) and the user grant already covers the sole counterparty.
  - **Group session** (`sessionId` parses to `{kind:'group'}`) → grant `openchat` `view` AND grant sender `full_access`. Permissions are taken as a union by Feishu, so sender ends up with `full_access` (manager) while other group members hold `view`. Sender becomes the human approver for any subsequent `Request access` flow Feishu surfaces natively — bot does not intercept those notifications. `member_type='openchat'` (NOT the older `chatid` — that name now returns a field-validation error; full valid enum: `email / openid / unionid / openchat / opendepartmentid / userid / groupid / wikispaceid / appid`. Do not regress: `groupid` is for contact-management groups, not chats).
  - **Off-channel** (terminal admin / bg-task on a feishu DM transcript / branch / fresh) → resolve sender open_id via `identity.channels.feishu[0]`; no chat grant. Without binding, the grant is `skipped-no-binding` and the doc stays bot-only with a warn-level audit field.
  Grants are intentionally NOT gated by a second `FeishuWriteConfirm` ASK; the create-doc ASK already authorized the action and re-asking on each grant would be UX noise. The user `full_access` perm is the lowest tier that lets the human approve later collaborator requests (`view` and `edit` cannot approve), so do NOT downgrade.
- **Sender open_id resolution for DM cannot use `sessionId` alone.** `feishu:dm:<chatId>` only carries the chat_id, which is a P2P chat reference (`oc_…`), NOT the sender's `ou_…`. The implementation MUST go through `identity.channels.feishu[0]` for DM. Group session ids do encode `senderOpenId` directly (Phase 26 formula), so the group path takes it from `parseFeishuSessionId(sessionId).senderOpenId` and never invokes the binding fallback. Keep these two paths separate; do not unify them by always going through identity binding because that breaks group dogfood when the sender's binding is stale or missing.
- **Grant failures are non-fatal and surface to the model in `permission_grants`.** Both `permission_grants.chat` and `permission_grants.user` carry one of: `view` / `full_access` (success or already-exists), `failed` (API rejected — error string lives in `permission_grants.errors[]`), `skipped-not-group` (DM chat grant), or `skipped-no-binding` (no openId resolvable). The audit record gets the same `permissionGrants` block. The tool description tells the model to read `permission_grants.errors` as a hint to fall back to a "tell user to share manually" reply rather than asserting the link is ready.
- **Grant idempotency.** Feishu's collaborator-already-exists family means "this member already has access". `grantPermission` uses `classifyFeishuError(...).kind === 'already-exists'` and treats it as success-equivalent. This keeps re-fires under interjection / retry from confusing the model with a fake "failed" status on a doc that is in fact accessible.
- **Confirmed-audit chronology.** `requireFeishuWriteConfirmation({deferConfirmedAudit:true})` lets the create path delay the confirmed audit so the eventual record can include `permissionGrants`. The catch arm in `runFeishuCreateFile` writes a bare confirmed audit BEFORE `auditFailed` so the timeline still reads "user approved → SDK failed" rather than jumping straight to failed. Write paths (`append-doc` / `sheet`) keep the inline confirmed audit unchanged (no grant step to merge).
- **Feishu error classification.** Feishu error-code recognition must go through `classifyFeishuError`; do not add new `error.code === <number>` / `response.data.code === <number>` checks in channel or tool code. When a new Feishu code appears, add the dispatch in `src/channels/feishu/resources/errors.ts`, add an envelope sample in `errors.test.ts`, and update `info/wiki/lightclaw-feishu-error-codes.md` in the matching category. Write paths that should back off use `withFeishuRetry(() => callFeishu(...))`; read paths should stay direct so users can see rate-limit failures instead of waiting silently.
- **`drive:drive` scope is the minimum permission tier.** PR4 already requires it for `folder_token` / drive link parsing; the grant step uses the same scope. Self-build app may also expose a finer-grained `docs:permission.member:create` ("添加协作者") as a separate togglable item — operators should grep both names in the developer console and toggle whichever the tenant requires. Re-publish the app version for changes to take effect.

# LightClaw Feishu Cloud Workspace Notes (Phase 34)

- Topology: LightClaw owns one bot-drive root folder (`<lightclawHome>/feishu-cloud-root.json`) and one lazily-created user folder per canonical identity (`users/<canonical>/state/feishu-workspace.json`). Agent tools never receive or operate on the root token; the only root-level maintenance path is admin slash `/feishu-workspace`.
- `FeishuCreateFile` now defaults its parent to the current user's workspace root. `parent_folder` resolves a subfolder path inside that workspace; legacy `folder_token` is still accepted but must pass ancestry check under the same user folder. Pre-Phase-34 docs that landed in bot drive root are grandfathered and will not appear in `FeishuList`.
- Agent workspace tools are channel-scoped and deferred: `FeishuList`, `FeishuCreateFolder`, `FeishuMove`, and `FeishuDelete`. `FeishuRead` / `FeishuWriteDoc` / `FeishuWriteSheet` intentionally keep PR4 pasted-URL semantics; a user-provided URL is explicit share intent and is not ancestry-limited by Phase 34.
- The cloud boundary is token ancestry, not a path string. Implementation: a process-wide `ParentCache` (`workspace/ancestry.ts`) records `(child, parent)` edges every time `listFolder` runs — the Feishu SDK's metadata API (`drive.v1.meta.batchQuery`) does **not** include `parent_token`, so walk-up via that API is impossible; we infer the inverse direction (parent → children) from list responses opportunistically. `assertWithinWorkspace(target, workspaceToken)` walks up through the in-memory map synchronously; if the chain hits `workspaceToken` it passes, otherwise it writes a `boundary-violation` audit row and refuses. The Phase 34 invariant that makes this sufficient: agents only ever acquire tokens via name resolution that walks down from the user workspace, so legitimate tokens are always populated. Tokens injected via legacy escape hatches (e.g. `FeishuCreateFile.folder_token` typed by the model) are not in the cache and therefore get rejected. Write tools evict touched tokens after mutation so a stale parent edge can't survive a move / delete.
- Never auto-recreate root or user folder on probe failure. Earlier `getOrCreateWorkspaceRoot` / `getOrCreateUserWorkspace` probed via `listFolder({maxItems:1})` and treated any 4xx as "folder gone, recreate", which silently destroyed user data on a single transient 400 (orphaning the original folder + every share grant the user had attached to it). Persisted tokens are now trusted as canonical; recreation happens only on cold start (no on-disk record). If the folder is truly deleted, the next real `listFolder` surfaces the error to the agent / admin, and `/feishu-workspace status` / `delete` / config override is the explicit recovery path.
- `FeishuMove` uses Unix `mv` semantics as of Phase 7.5: `destination` relocates, `new_name` renames, and both fields together move first then rename. Source and destination stay inside the current user workspace, destination ancestry must not contain the source folder token, and same-parent name collisions are rejected before calling Feishu. If move succeeds but rename fails, the tool returns a `WorkerFailure` JSON envelope with `partial_result` so the caller can retry the rename alone. Audit rows still use `operation:'move'` and add optional `resource.mode`, `oldTitle`, `newTitle`, `moved`, and `renamed` fields. **Confirmation is grantable as "以后都允许" since 2026-05-19** — `FeishuMoveConfirm` was dropped from both `isHighRiskAsk` and `isOneShotFeishuOperation` because moves are bounded by the user workspace and reversible. The other one-shot virtual confirms (`FeishuDeleteConfirm`, `FeishuReplaceDocConfirm`, `FeishuSheetDestructiveConfirm`) remain forced once-only.
- `FeishuDelete` uses Feishu's native trash behavior (`drive.v1.file.delete`, `type=folder|docx|sheet|...`) and asks through virtual tool `FeishuDeleteConfirm`. Treat it as high-risk: no persistent "always allow" button, even in loose modes.
- User deletion and workspace deletion are deliberately separate. `/user remove` clears identity/runtime state only; it does not remove the Feishu user folder. Admin can later run `/feishu-workspace delete <canonical>` which requires a short-lived `--confirm <token>` and records `admin-delete-workspace`.
- Audit rows continue to live in `<lightclawHome>/audit/feishu-writes/<YYYY-MM-DD>.jsonl`. Phase 34 adds `create-folder`, `move`, `delete`, `boundary-violation`, and `admin-delete-workspace`, with ancestry chain snapshots on boundary-sensitive operations.

# LightClaw Pairing Card Notes (Phase 25)

- Unknown Feishu senders take the card path only when the canonical admin already has a Feishu binding. Otherwise `ChannelRunner.resolveMessageUser()` must keep the old text fallback, because an application card with no admin target is worse than a visible pairing code.
- The card path does not create `pending.json` entries until the user clicks `[确认申请]`. Cancel stays silent and does not consume the pairing rate-limit slot. If a pending code already exists, repeated user messages render the waiting card instead of sending another review card.
- `fetchFeishuUserInfo()` is cosmetic and best-effort: it uses `contact.v3.user.get` with `user_id_type=open_id`, returns `{ name, email, userId }`, and falls back to open_id on any failure. Do not make pairing depend on this API being healthy.
- `/user approve <code>` (no `--as`) and admin card approval both call `deriveCanonicalName({ name, email, openId, userId })`, so canonical names are deterministic (`<base>_<user_id>` when Feishu user_id is available). Terminal-only override: `/user approve <code> --as <name>` skips `deriveCanonicalName` and binds the sender into the supplied (existing or new) identity. The card path has no `--as` because there is no UI for picking a target name; admins who need to merge an IM sender into an existing identity (most commonly: their own admin) must use the terminal slash. `--as` validates the name with `isValidIdentityName` BEFORE `approveCode` consumes the pending entry, so a typo never burns a pairing code; in `runtime.backend = "local"` the `rejectNonAdminInLocal` gate still applies (only `--as <admin>` is accepted).
- Pairing card tokens are in-memory only. After a daemon restart, old card clicks resolve as expired or already handled; users can resend a message and `pending.json` remains the durable source of truth.
- Admin review card clicks must validate the operator through `lookupBySender(feishu:<open_id>)` + `isAdmin()`. Never trust the card payload alone for approval authority.
- **Applicant-facing pairing cards (application / waiting / cooldown) push to applicant DM**, never to the chat the applicant @-mentioned the bot in (group privacy: leaking applicant identity / pairing code to every group member is unacceptable). `PairingCardCoordinator.pushApplicantCard()` calls `sender.sendInteractiveCardToOpenId(applicantOpenId, card)` and only falls back to in-chat `sender.sendInteractiveCard(message, card)` if the DM push errors. Feishu's `im.message.create` with `receive_id_type=open_id` auto-creates the DM thread, so first-contact-in-group works without prior DM existence. Admin review cards already pushed to admin DM since Phase 25; applicant DM routing closed the symmetric leak in 2026-05-08.
- **Bootstrap text-fallback notices (welcome+code, rate-limited, cooldown-hook-missing) also push to applicant DM.** When admin has no Feishu binding `canRenderPairingCard` is false and `resolveMessageUser()` falls into the older text path that calls `sendNotice(message, …)`. Without DM routing those notices echo back to the inbound chat — including groups, leaking the same applicant identity / pairing code the card path was carefully avoiding. `ChannelRunnerStrategy.sendNoticeToOpenId({ message, applicantOpenId, kind, content })` (Feishu impl: `sender.sendInteractiveCardToOpenId(applicantOpenId, buildSystemNoticeCard({…}))`) is the DM-first path; runner's `sendApplicantNotice()` helper tries it first and falls back to in-chat `sendNotice` only when the hook is absent OR the DM push errors. All three bootstrap leak sites in `resolveMessageUser` (cooldown-hook-missing, welcome+code success, rate-limited catch) go through `sendApplicantNotice`. Fix landed 2026-05-08 dogfood when user-with-no-admin-Feishu-binding still saw cards in group.
- **No applicant-facing string mentions admin terminal commands.** `channel.pairing.adminCmd` (which read "管理员命令：/user approve <code>") was deleted; `channel.pairing.waiting.body` no longer carries the `/user approve {code}` fallback line; `channel.pairing.rateLimited` no longer references `/user pending`. Applicant-side messaging is purely user-actionable: code + waiting state + try-again-later. Admin discovers stuck pending entries through their own `/user pending` slash in DM or terminal.
- **Welcome card has admin / non-admin variants.** `buildApprovalWelcomeCard({ isAdmin })` branches on the recipient. Non-admin: legacy user-side slashes (`/help` `/status` `/feedback` `/stop`). Admin: separate body listing `/user` `/ceiling` `/cost` `/sandbox` plus the user-side basics (no `/feedback` since admin is the recipient, not the sender). `post-approve.runApprovalPreheat` resolves `isAdmin(name)` before pushing.
- **Pre-approval message replay.** `PendingEntry` carries `lastApplicantText` + `lastApplicantTextAt` + `lastApplicantChatId` + `lastApplicantChatType` (additive to the v1 shape; missing fields tolerated for backward-compat with old `pending.json`). Three independent `resolveMessageUser` paths must all stash routing fields (chatId + chatType) — and text when present — or replay silently dies / lands in the wrong chat: (a) the existing-pending card branch (`canRenderPairingCard && existing`) calls `updatePendingApplicantText(senderKey, message.text, message.chatId, message.chatType)` before rendering the waiting card; (b) the new-application card path stashes via `PairingCardCoordinator`'s in-memory `'pending'`/`'submitting'` state (which carries text+chatId+chatType) and promotes to pending.json the moment `applyConfirm` runs `generateOrReusePending` — call is unconditional, NOT gated on text being non-empty; (c) the bootstrap text-fallback path (admin has no Feishu binding so `canRenderPairingCard=false`) calls `updatePendingApplicantText` after `generateOrReusePending`. All three stash calls intentionally do NOT reset `createdAt` / `ttlMs` — TTL still measures from initial application time. **Empty applicantText is a valid case**: the user @-ed the bot in a group with no body (just `@LightClaw`). `updatePendingApplicantText` decouples text from routing — empty text still stashes chatId / chatType when present; the only fully-no-op case is text-AND-routing-all-absent. Post-approve then replays even with an empty applicantText so the LLM greets via the bare `[senderName] ` prefix per `9af7001`'s empty-mention-natural-reply design — replay's only hard requirement is now `replayChatId` (origin chat or welcome-card DM fallback) plus a registered channel runner. After `/user approve` (terminal or card) lands, `preheatAndWelcomeOnApproval(name, link, { applicantText, applicantChatId, applicantChatType })` pushes the welcome card and synthesizes a `NormalizedChannelMessage` whose chatId / chatType come from the **original chat** (group → group, DM → DM), not from the welcome card's DM chat_id. The welcome card's DM chat_id is only used as a degraded fallback when `applicantChatId` is missing on old pending.json shapes. The synthetic message is fed into `ChannelRunner.handleMessage` via `getChannelRunner()` from `runner-registry.ts` — chatType drives Phase 26 sessionId routing, so a group-origin replay lands in `feishu:group:<groupId>:<senderOpenId>` with `[senderName]` prefix from `formatChannelUserText`, and the agent's reply via `onAssistantTurn → sendReply(effectiveMessage, text)` goes back to the same group via `im.message.create` with `receive_id_type=chat_id`. **Cards (welcome / pairing / permission ask / permission resolution / BackgroundTask completion) stay on DM regardless** — that is a privacy boundary, distinct from the agent-conversation continuity boundary that this stash encodes. Replay is best-effort and skips silently if `replayChatId` or the channel runner is missing. Media attachments on the pre-approval message are intentionally dropped (Feishu media keys have a TTL that often outlasts admin's approval window; the user can resend).
- `sendInteractiveCardToOpenId` returns `{ chatId? }`. The chatId is the bot↔user DM chat_id reported by Feishu's `im.message.create` response. Capturing it from the welcome push is the whole reason the welcome push happens BEFORE the replay handleMessage call — the replay needs that chatId to route into `feishu:dm:<chatId>` so the replay turn and any future inbound DMs share one transcript.
- **Synthetic-message marker on replay path.** The replay `NormalizedChannelMessage` carries `synthetic: true`. The platform never saw `messageId`, so reply / reaction APIs return 400 on it. Channel adapters check the flag and short-circuit: Feishu sender's `replyTargetFor(message)` returns `undefined` for synthetic messages so `sendReplyOrCreate` skips `im.message.reply` and goes straight to `im.message.create` with `receive_id_type=chat_id`; Feishu typing strategy returns a null token immediately when `message.synthetic` is true, bypassing `messageReaction.create`. Without these short-circuits dogfood produces back-to-back `AxiosError 400` traces (typing add fail + send reply fail) and the user-visible bot reply never lands. Mention gating, pairing, transcript persistence, and the agent loop itself all still apply — synthetic messages are otherwise indistinguishable from real inbounds.

# LightClaw In-flight Interjection Notes (Phase 27)

- The channel session lock is no longer a hard barrier between turns for Feishu. When a main sessionId is mid-flight (`channelInterjectionQueue.hasInflightFor(sessionId)`), bare inbound messages route to the interjection queue and receive a one-line ack instead of stacking on the lock. `/stop` remains the explicit abort fast path.
- Interjections are delivered to the model at the next tool boundary inside `query.ts`. `interjectionDrain()` returns the queued entries, and `buildInterjectionBlock()` wraps them into a `<user-interjection>` text block alongside the existing `tool_result` blocks in the same user message. The block's hard rule is: the previous request MUST be completed UNLESS the user's interjection EXPLICITLY says to stop. Do not loosen the EXPLICITLY gate or shrink the reverse examples; the whole point is fighting the model's "latest message = new task" bias.
- The framework intentionally never references `/stop` in the prompt the model sees. `/stop` is a user-to-system meta command that aborts the in-flight query loop directly, not an agent action.
- Permission ASKs awaiting a click are auto-denied when an interjection arrives via `FeishuPermissionCoordinator.tryAutoDenyForInterjection(sessionId)`. The next `<user-interjection>` block carries an additional reminder so the model can re-issue the original tool call when appropriate, or skip it when the cancellation path applies. Do not send a separate "denied" notice on this auto-deny path; the ack notice is enough and the deny reason is structural, not a user choice.
- Feishu approval is card-only. There is no "type 1 / approve / yes / 批准 to approve" path anymore. `tryConsumePermissionMessage` and the `parseTextAction` family have been deleted. Do not reintroduce them; if card delivery fails, `notifyCardDeliveryFailureAndDeny` sends a plain text failure notice and resolves the pending as deny so the user can resend.
- After Phase 37 there is no terminal agent loop, so there is no terminal permission ASK either — the `permission/prompt.ts` readline approver was removed alongside `mode: 'interactive'` in query.ts. Approval UX is now channel-only (Feishu cards). The historical "Terminal in-flight interjection" follow-up was scoped to the readline ASK and is moot.
- Interjection metadata is stamped onto the injected user message as `metadata.interjectionEntries`. Audit and transcript replay can see which user words were injected at which tool boundary. Preserve this metadata in non-summarizing transcript rewrites, and on the messages compaction keeps verbatim (`toKeep` — copied by reference, so it survives automatically). The `toCompress` prefix is, by definition, collapsed into a text summary, so per-message metadata there does not survive a compact — that is expected, not a leak to fix. If a durable audit trail across compacts is ever needed, route it to a sidecar file rather than relying on transcript metadata.
- The interjection queue is for **bare chat only**. Any inbound text starting with `/` (after trim) is treated as a slash command and never enters the interjection queue — see `isLikelySlashCommand` in `runner.ts`. Wrapping a slash as `<user-interjection>` is silently destructive: the LLM treats `/mode auto` as natural language and `dispatchChannelSlash` never runs, so the command is dropped. Read-slash + `/stop` short-circuit pre-lock via `parseFastPathSlash`. Write slashes (`/mode <m>`, `/model <m>`, `/rules allow ...`, `/auth import ...`, `/user approve ...`, `/sandbox prefetch|reset`) and unknown slashes route by session liveness: idle → in-lock `dispatchChannelSlash` path unchanged; **in-flight → `channelPendingSlashQueue`** (`src/channels/feishu/pending-slash-queue.ts`), drained and applied at the in-flight turn's next tool-call boundary — see the mid-turn slash bullet in `# LightClaw Slash UX Notes`. Do not narrow the in-flight routing to a slash allowlist — unknown slashes should still queue so `dispatchChannelSlash` can produce its own usage notice at the boundary instead of being absorbed into the next interjection block.
- **Reply quote anchor follows the most recent drained interjection.** `runner.ts` keeps `let replyTargetMessage = effectiveMessage` per turn; every successful `interjectionDrain` advances it to the FIFO-last entry's messageId + senderOpenId, and both `onAssistantTurn` and the end-of-query single-shot fallback use this anchor (not the const `effectiveMessage`) when calling `sendReply`. Result in Feishu UI: a bot reply that's primarily about the user's latest interjection threads off that interjection, not the turn opener — closes the 2026-05-11 confusion where the bot's "GLM-5 摘要翻译" reply was UI-quoting the turn-start `[图片][图片][图片]`. This is a *timeline anchor*, not a strict semantic mapping: when one assistant turn covers BOTH original task and interjections, the UI still only quotes one message and we pick the most recent input as the natural reference (matches Slack / Discord bot conventions). The anchor resets to `effectiveMessage` at the start of each `attempt` in the retry loop because interjections drained in a failed attempt have already been consumed from the queue and the messages slice was rolled back.

# LightClaw Feishu Session Isolation Notes (Phase 26)

- Feishu sessionId formula is now `feishu:dm:<chatId>` for p2p/private chats, and `feishu:group:<chatId>[:<threadId>]:<senderOpenId>` for group/topic-group/unknown chat types. `threadId` comes from Feishu `message.thread_id` and is a topic-group sub-channel; `rootId` comes from `message.root_id` and is only reply-chain metadata. Do not merge them back into `parentId`, and do not make `rootId` influence sessionId.
- Same Feishu user in DM, each group, and each topic thread runs an independent transcript, `session-memory.md`, channel lock, and permission FIFO queue. Canonical identity, identity preferences, permission rules, and auto-memory stay per canonical user so long-term facts and user-level rules still cross sessions.
- Group mention gating is enforced in application code before pairing/session routing. With `channels.feishu.requireMention` (default `true`), group messages pass only when `mentions[]` contains the bot open_id or the parsed text contains `@<botName>`. The Feishu open-platform "only messages that mention bot" backend toggle is not enough; keep this gate as the safety net. `requireMention: false` is the explicit admin escape hatch.
- **Bot's own @-mention is erased from inbound text before runner-side parsing.** `parseMessageContent`/`stripMentions` accept a `botStripId` (bot's open_id, fetched at startup via `fetchBotSelfInfo` and threaded through both transports). Mentions whose `openId === botStripId` get replaced with empty string at *every* occurrence in the text (any position, any count); other mentions still render as `@<name>` so the LLM keeps user-of-interest context. Mention key (`@_user_<n>`) is the precise locator with `escapeRegex` defense — do not switch back to display-name string matching, that breaks if a user renames themselves to the bot's display name. Without this strip, group inbound `"@LightClaw /help"` keeps the leading `@<botName>` prefix and every `^/...` slash detector (`parseFastPathSlash`) silently fails — `/stop`, `/help`, `/mode`, `/rules`, write slashes all break.
- Bot self identity is probed once at startup via `/open-apis/bot/v3/info`. If it cannot be fetched, the gate falls back to "pass" with a stderr warning instead of killing the daemon, because a bot-info outage should not make the channel unusable.
- Group user messages are prefixed before the LLM sees them: `[<senderName>] <text>`. Sender name is best-effort contact lookup, then mention sidecar name, then open_id suffix. DM messages do not get this prefix. The Feishu system prompt tells the model that the prefix is sender metadata, not user words. **Framework synthetic turns (`message.frameworkText`) also skip the prefix** (2026-06-13): a bg-result / taskrun wake's text is a framework block, not user speech, so labeling it `[<senderName>]` reads as "the user pasted this block" — `formatChannelUserText` gates the prefix on `!message.frameworkText`, and `wakeOrInterject` sets `frameworkText:true`. This matches the in-flight interjection path, which already renders `source:'background-task'` entries as raw block text (no sender label). The post-approval replay synthetic does NOT set `frameworkText` — it carries the user's real words and keeps the prefix.
- Permission approval cards from group-triggered tool calls are pushed to the sender's DM via `sendInteractiveCardToOpenId(senderOpenId)`. The card button value carries `originSessionId`; callbacks validate it before resolving the pending ask. If DM push fails, fall back to the original chat and log stderr so the turn never hangs silently.
- Permission `ownerKey` is the sessionId. Same user in DM and group can have independent pending approval queues. Do not restore `chatId:senderOpenId`; that collapses unrelated session decisions back together.

# LightClaw Permission System Notes

- `Tool.suggestPermissionRules(input)` returns a *set of rules to install as a group* — not a precise→broad menu. For a chained Bash command the suggester emits one `Bash(<head>:*)` rule per subcommand (split on `;`/`&&`/`||`/`|`, max 5); for path tools a single `Tool(<dir>/**)` rule; for WebFetch a single `WebFetch(<hostname>)` rule; for MCP a single `MCP(<server>:<tool>)` rule. New tools should follow the same shape — return an empty array when no precise scope is derivable, and the approver will fall back to a single tool-wide allow rule.
- Approvers render a fixed three-option UX (Allow once / Allow <merged label> / Deny). The middle option installs every rule in the suggester's array in one go, and the merged label is built by `formatSuggestionLabel` (degrades to `N 类 …` past 50 chars). Faithful port of Claude Code's `bashToolUseOptions.tsx` + `generateShellSuggestionsLabel`. Do not add per-rule buttons or tier-selection UX back.
- `ask` outranks `allow` in `evaluatePermission`. Rules in `permissions.json`'s `ask: [...]` array force the ASK flow even under `bypassPermissions`; only `deny` outranks them. Use this to keep critical operations (`Bash(rm:*)`, `Edit(/etc/**)`) confirmable while running otherwise-permissive sessions.
- The "以后都允许" / `[a]` button writes a persisted rule to `<lightclawHome>/users/<canonical>/state/permissions.json`, not to in-memory state. Rules survive daemon restarts and are reloaded via `loadIdentityRules` on every initializeState / resetSessionContext. There is no "session-scoped" tier — `once / always / deny` collapses to a 3-option UX where `always` is unconditionally persisted.
- Dispatched workers share the requester's permission UX. The channel runner sets `state.permissionApprover` before each query() entry; the permission router prefers `ctx.permissionApprover` but falls back to `state.permissionApprover`, so Dispatch-spawned workers reach the same Feishu card as the main agent. Do NOT reintroduce the "isSubagent → auto-deny on ask" short-circuit; workers without an approver (test paths, unattended off-channel cases) still deny via the final fallback branch, which preserves the original safety property.
- Background fires also use the channel permission UX when the daemon has an active channel runner and the canonical user has a channel binding. `runBackgroundTaskFire()` gets the approver through `getChannelApproverFor(canonicalUser, sessionId)`. If no approver is available during startup/shutdown gaps or for an unbound user, `requestPermission()` keeps the bg fallback: non-high-risk asks auto-allow under the worker role's tool scope, high-risk asks deny with denial detail for the result block.
- Concurrent same-kind permission asks (e.g. parallel subagents both asking `Bash(curl:*)`) coalesce via the FIFO queue + reevaluate sweep: only the head renders a card; when the user picks "以后都允许", `FeishuPermissionCoordinator.reevaluateOwnerQueue` resolves every queued tail under the new rule set and silently allows / denies anything that now matches. Never render multiple cards for what is effectively one decision.
- **Phase 8 PR5 (2026-05-18) `MemoryWriteAudit.sourceTier`**: audit row at `<lightclawHome>/audit/memory-writes/<YYYY-MM-DD>.jsonl` carries optional `sourceTier: 'L1' | 'L2' | 'L3'`. Resolved by `resolveSourceTier(targetPath, memoryDir)` in `src/memory/scope.ts` — L1 = user root file, L2 = `_shared` tier, L3 = role-private dir. Omitted on boundary violations (target resolves outside memoryDir, denied path). Lets post-hoc audit attribute writes per memory tier without re-deriving from path strings.
- High-risk permission asks hide the "以后都允许" button — channel users have no shoulder-surfing safety net and `rm -rf /` permanently allowed is unrecoverable. The classifier is `permission/high-risk.ts:isHighRiskAsk`; chained Bash commands trigger as soon as any subcommand is high-risk (`cd /tmp && rm -rf foo` → high-risk via the `rm` segment). The Bash side (rewritten §1.4, 2026-05-14; relaxed 2026-05-19) is conservative — false positives only cost one extra "allow once" click, a false negative permanently allows arbitrary code execution. It flags: **destructive / priv-esc heads** (`rm` / `dd` / `mkfs.*` / `sudo` / `su` / `doas` / `pkexec` / `runuser`), **shells** (`bash` / `sh` / `zsh` / `fish` / `dash` / `ksh` / `eval` — `curl … | sh` install-from-internet), **command wrappers** (`env` / `xargs` / `find -exec` / `timeout` / `nohup` / `setsid` / `exec` / `command` / `nice` … — the real head is scanned out of their argument tokens; a persisted `Bash(<wrapper>:*)` rule is itself high-risk because the head-only rule syntax can't condition on the wrapped command), and **command substitution used as the command** (`$(curl …)` / backtick). Heads are normalized first so path / quote / backslash evasion (`/bin/rm`, `\rm`, `'rm'`) can't slip past. **Language interpreters (`python` / `node` / `perl` / `ruby` / …), ephemeral package runners (`npx` / `npm exec` / `pnpm dlx` / `yarn dlx` / `bunx` / `bun x` / `uvx` / `uv run` / `pipx run`), and `source` / `.` are deliberately NOT high-risk** — general-purpose, routine on this workload; the friction of always-allow being hidden does not buy real security since anyone who can run `python` / `npx` / `source x.sh` can write a script and `bash` it (and `bash` is already gated). The package-runner re-classification (2026-05-19) closed an inconsistency with the interpreter carve-out: the "fetch-and-run remote code" argument applies equally to `python -c "$(curl …)"`. Do not re-add interpreters / package runners / source without revisiting that decision. Edit/Write/Read on `/etc`, `/usr`, `/boot`, `/sys`, `/proc`, `**/.ssh`, `**/.gnupg`, `**/.aws`, `**/.kube` is high-risk. Feishu high-risk asks: `FeishuDeleteConfirm` (trash deletion), `FeishuReplaceDocConfirm` (whole-doc replace), `FeishuSheetDestructiveConfirm` (whole-sheet delete). Other Feishu writes (create-doc / create-folder / append-doc / sheet append+overwrite / table-edit / move / upload) are plain `write` and grantable as "always allow"; move was re-classified down on 2026-05-19 because moves stay inside the user workspace (PathPolicy + ancestry guard) and are reversible. Stale-card clicks that ask for "以后都允许" on a high-risk pending are silently downgraded to allow-once; never persist a rule that the current UX would not have offered.

# LightClaw Tool Catalog Notes (Phase 29)

- `Tool.channelScope?: ('feishu' | 'terminal')[]` filters tool visibility by channel. Omitted means visible everywhere, which preserves all pre-Phase-29 builtin tools without annotation churn. New tools that require Feishu sender/chat context should use `channelScope: ['feishu']`; terminal-only diagnostics should use `['terminal']`.
- `SessionContext.channel` is set at session creation (`'terminal'` in CLI, `'feishu'` in ChannelRunner / BackgroundTask). Query callers should pass `getAllTools(ctx.channel)` or the known channel-specific equivalent. Plain `getAllTools()` remains the backward-compatible full-catalog path for tests and startup probes.
- `Tool.alwaysLoad` and `Tool.shouldDefer` override `isDeferredTool()`. Default rules: builtin tools load inline, MCP tools defer, ToolSearch never defers. `shouldDefer` wins over `alwaysLoad` so an operator-marked deferred tool is not silently inlined.
- **Phase 31 split (2026-05-12)**: every builtin tool is explicitly tagged. The current **inline** set (`alwaysLoad: true`, 9 tools) is: `Bash` / `Read` / `Write` / `Edit` / `Grep` / `Glob` / `TodoWrite` / `ToolSearch` / `Dispatch`. Everything else is **deferred** (`shouldDefer: true`) — conversation / memory / web / skill / sleep / send-file tools, `AskUserQuestion`, the Dispatch management tools that remain model-visible (`Message` / `UpdateSchedule`), and `Notify`. (The Feishu cloud-doc / cloud-space tools added after Phase 31 are also deferred, behind their `channelScope` + role gates.) The split is by **per-turn use frequency**, not by capability: inline tools are what almost every turn reaches for; deferred tools are task-specific. **`Dispatch` was re-classified deferred → inline after the original Phase-31 8-tool set**: the orchestrator's core per-turn delegation verb; deferring it carried a ToolSearch round-trip the model routinely sidestepped by doing the work itself, *suppressing delegation*, so only post-hoc management tools + `Notify` stay deferred. This is the frequency-criterion exception: a tool whose whole value is being reached for at the decision point is defeated by burying it behind ToolSearch. (`AskUserQuestion` was briefly inlined 2026-06-02 on the same reasoning, then reverted to deferred the same day — a dogfood transcript showed the model plain-texting a blocker question with the tool *already inline*, so deferral was never the cause; the real fix was strengthening the brainpp-batch-job skill prompt's "ask via the card" instruction, and by the frequency criterion a structured question is task-specific, not every-turn. It stays `main`-only on `feishu` via BLOCKED_WORKER_TOOLS + `channelScope:['feishu']`.) New tools must explicitly tag `alwaysLoad` or `shouldDefer` — don't leave both unset and rely on "builtin → inline" default, because that bypasses the per-tool review for inline-vs-deferred placement. Original Phase-31 budget figures (8-tool inline baseline): inline ~1770 tokens, deferred ~3380 tokens; cold-start prompt saved ~66% of tool-description bytes.
- Deferred loading is controlled by `tools.deferredLoading` (`auto` / `always` / `off`) and `tools.deferredLoadingThreshold` (default 30). **Default flipped to `'always'` in Phase 31**: tool-count threshold is no longer the gate; the gate is the `alwaysLoad` / `shouldDefer` tag on each tool. `auto` mode preserves the old "≥ threshold → enable" behavior for operators who prefer it. `off` is the emergency rollback: no ToolSearch, all tools inline.
- `ToolSearch` is injected only when deferred loading is active. It supports `select:Name1,Name2` exact lookup and keyword search with multi-token AND plus `+keyword` required-name matching. Matches are added to `SessionContext.discoveredTools`; the next query-loop turn includes their full schemas in the provider tools array.
- `SessionContext.discoveredTools` is in-memory and per session. Do not persist it or share it across DM / group sessions. Dispatched workers intentionally get a fresh empty `Map<string, number>` plus `turnCounter: 0` so requester discovery state does not leak into worker prompts.
- **`discoveredTools` is a bounded LRU with turn-based TTL.** **Phase 31 upgraded the V1.5 `Set<string>` to `Map<string, lastUsedTurn>`** so steady-state token spend stays low under the new `deferredLoading: 'always'` default — without TTL, a long DM session walks through every deferred tool once and then carries all of them inline forever (defeating the inline/deferred split). `markDiscovered(map, name, turn, maxSize)` is the single mutation entry: it re-inserts existing names to the back of the Map (MRU), records the current turn as the value, and evicts the front entry once `map.size > maxSize`. `pruneStaleDiscoveredTools(map, currentTurn, ttl)` drops entries with `lastUsed < currentTurn - ttl`; `query.ts` calls it at the start of every turn before building the catalog. Settings: `tools.discoveredToolsMaxSize` (default 30, 0 disables cap), `tools.discoveredToolsTtlTurns` (default 20 ≈ one /compact cycle, 0 disables TTL → V1.5 behavior). `SessionContext.turnCounter` is the session-scoped counter feeding both APIs — incremented once per query-loop turn (subagent and custom-systemPrompt callers skip the bump because they don't use the deferred path). `query.ts` calls `markDiscovered` from BOTH the `discoverTool` callback inside the tool-call dispatch (handles ToolSearch matches) AND the post-permission step in `dispatchToolCall` when the dispatched tool is `isDeferredTool` (handles direct re-use of an already-promoted tool, so active tools don't slide toward eviction just because newer ToolSearch hits keep landing). Without the active-use refresh, a session that searches a tool at turn 5 and uses it every turn after would still evict it once the TTL fired.
- Deferred tool names live in an English `<system-reminder>` at the end of the system prompt. Do not mix deferred names into `formatToolCatalog()`; that catalog is only for tools whose schemas are already loaded and callable this turn.
- When a model directly calls a deferred tool before ToolSearch, `query.ts` returns a self-healing `tool_result` explaining that the tool is deferred and giving the exact `ToolSearch({query: "select:<name>"})` call. Do not let this fall through as a generic unknown-tool or provider API error.
- Custom `systemPrompt` callers, including forked subagents, keep their existing inline tool catalog shape; query disables deferred loading for those calls to avoid a mismatch between the fixed prompt text and the per-turn tools array.
- Anthropic `tool_reference` is intentionally not used in V1. Tools-array expansion is provider-agnostic across anthropic / openai / openai-auth; Anthropic-only transport optimization can be revisited later if schema size becomes a real token cost.

# LightClaw Terminal Console Notes

- The terminal does NOT run the agent loop. `repl.ts` is a slash-only admin console: it dispatches builtin slash commands, prints a banner, and keeps the daemon process in the foreground (cli.ts owns channel startup + the shutdown drains that fire when the loop exits). The agent is reached exclusively through channels (Feishu); the admin talks to the bot there like any other paired identity. # LightClaw Slash UX Notes (Phase 18)

- `/help` is a pure command list, role-rendered (admin sees an extra block). Do not put whoami / state info in `/help`; that goes to `/status`. State and operation surfaces are split: `/help` answers "what can I do", `/status` answers "who am I, where am I, what's running".
- Admin-only commands (`/user`, `/ceiling`, `/cost`, `/sandbox`) and user-only commands (`/feedback`) are gated in both `BUILTIN_COMMANDS.visibleTo` and `dispatchChannelSlash`. The role gate must reject with a clear message ("admin only" / "user-only"), not silent allow. `/sandbox` in particular is admin-only because its `status` subcommand leaks deployment internals (image / container / worker names), `prefetch` triggers a multi-GB pull, and `reset` rebuilds a per-user worker — none of which should be a user-facing button. Sandbox health surfaces to admin via channel notices, not via slash commands.
- Renamed commands (`/identity` → `/user`, `/permissions` → `/rules`) are intentionally NOT kept as compat aliases. The `RENAMED_COMMANDS` table in `src/commands/builtin.ts` only emits a hint ("Renamed to /user. See /help.") so the user can self-correct. New code must not register the old names.
- `/stop` aborts the in-flight turn for the **calling sessionId** and, since collab-phase2 PR9, sets running/blocked TaskRuns in that chat's rooted TaskRun trees waiting (`waiting {reason:'user-stop'}`) by aborting their `currentSessionId` controllers. Queued children remain queued, other chats are untouched, and worker-created standing service roots are excluded because their `callerSessionId` is not the calling chat. A stop notice is persisted per user and injected into the next normal user turn as a `<system-reminder>` so main can continue, cancel queued/waiting work via `TaskUpdate`, or ask the user. Slash commands do not consume the notice. `/stop` remains channel-only (`channelOnly: true`) — the terminal admin console never runs a query, so it has no in-flight turn to abort.
- `/stop` and a curated read-only slash whitelist take a **pre-lock fast path** in `ChannelRunner.handleMessage` via `parseFastPathSlash`. The channel lock is held for an entire LLM turn, so without this short-circuit `/stop` would queue behind the very query it is trying to abort and never fire mid-turn. Read fast-path runs the slash inside a fresh `SessionContext` populated from disk: preferences (mode / model), identity rules, and the persisted main-session transcript (so `ctx.messages.length` reflects the real message count). Live in-flight per-turn counters like `totalInputTokens` read 0, which is honest "between turns" semantics. Whitelist (`parseFastPathSlash` returns `'read'`): `/help`, `/status`, `/cost`, `/rules` (no args / `list`), `/mode` / `/model` (no args), `/auth list`, `/user` (no args / `list` / `pending` / `feedback`), `/sandbox` (no args / `status`), `/feedback`. `/sandbox status` is special — its handler needs a live `Runtime`, so the fast path acquires one from the per-canonical pool just for that slash (Map lookup if cached). `/feedback` writes `feedback.jsonl` on a path entirely separate from the channel session transcript, so no main-lock contention applies. Write variants (`/mode <m>` / `/model <m>` / `/rules allow ...` / `/auth import ...` / `/user approve ...` / `/sandbox prefetch` / `/sandbox reset`) take the in-lock `dispatchChannelSlash` path when the session is idle; when a turn is already in flight they route to the pending-slash queue instead (next bullet). When adding a new slash, default to in-lock; only opt into the whitelist after confirming the handler doesn't read live in-memory turn state (or, for runtime-touching slashes like /sandbox, after confirming a pool acquire is acceptable).
- **Mid-turn write slashes (`channelPendingSlashQueue` + `slashDrain`).** A write / unknown slash that lands while its sessionId's turn is in flight is NOT stacked on the session lock (it would only run after the whole turn finished). `ChannelRunner.handleMessage` pushes it to `channelPendingSlashQueue` (`src/channels/feishu/pending-slash-queue.ts`) keyed by sessionId, acks with `t('channel.slash.queued')`, and returns before `runExclusive`. The in-flight `query()` drains it via the `InvocationContext.slashDrain` callback at every tool-call boundary — the `finally` of the tool-dispatch loop AND the `toolUses.length === 0` final-turn branch — so a mid-turn `/mode auto` applies to the turn's remaining tool calls. `slashDrain` runs inside the turn's `SessionContext` scope, so `/mode` (`setPermissionMode`, read live per tool call) takes effect immediately; `/model` mutates `config.defaultModel` and `query.ts` re-resolves `roleModel` at the top of every turn so the switch lands too. Slashes still queued after the query returns (landed during the final turn past the last boundary, or during post-query sendReply / typing / background drain) are replayed by the runner's outer `finally` (`replayLeftoverSlashes` → `handleMessage`); the session is idle by then so they take the in-lock path. `slashDrain` / `replayLeftoverSlashes` are best-effort and never throw — a slash failure must not mask the turn's own outcome. `/stop` is unaffected (its own pre-lock abort fast path); routing to the pending-slash queue keys off `channelInterjectionQueue.hasInflightFor` and owns no in-flight flag of its own.
- **Phase 9 PR1 (2026-05-18) deleted `/b` / `/branch` / `/fresh`.** Parallel sub-task delegation now goes through `Dispatch` exclusively (user asks main in natural language, main decides whether to dispatch a background worker). The old spawn-pair / merge-back / trim-to-last-completed-turn / `branch-<canonical>-<uuid>` lock-key orchestration is fully removed; legacy transcript `branchPlaceholder` / `branchSpawn` metadata becomes inert text on new daemon (no recovery path runs). Do not reintroduce user-side parallel-spawn slashes — they break the agent-as-manager model.

# LightClaw Prompt Design Principle (Phase 2 PR6, 2026-05-16)

**Minimum + complete context.** Every prompt is written from the agent's own first-person perspective with the minimum information that agent needs to do its job — never from a system / overview perspective that enumerates surrounding architecture.
- **Do not** enumerate sibling agents, blocked tools, channel infrastructure, scheduling layers, or "the parent has X". That is 此地无银三百两 — listing what the agent does NOT have tells the model what the framework HAS, leaking attack surface and inviting the model to reason about hierarchy it should not see.
- **Do** name the agent's role + its own tools + its own delivery target. Refer to the consumer as "the requester" or "the reader", not "the parent" / "main agent" / "orchestrator".
- The framework wrapper (`buildSubagentPromptContent` in `src/prompt.ts`) no longer adds a generic opener such as "You are a focused LightClaw worker". It renders the role-owned prompt plus framework-derived sections only. Per-role bodies and wrapper are consistent — both use the requester/reader frame. Do not regress to "subagent" / "parent agent" without re-opening this audit.
- The 2026-05-16 sweep also rewrote the then-named `general-purpose.ts` / `explore.ts` / `extract-memories.ts` / `auto-dream.ts` / `web.ts` prompts to drop the "subagent" / "parent" / "user's message" hierarchy words and the `extract` / `auto-dream` negative-enumeration capability lines ("you have no shell / no skills / do NOT call UseSkill"). The no-skills / no-UseSkill constraints are still enforced by Role tools allowlists and internal runtime gates — prompt belt-and-suspenders was redundant with the runtime gate AND leaked framework structure. The Phase 6.5 ids for these roles are now `generalist`, `localExplorer`, `memoryExtractor`, `memoryCurator`, and `webSearcher`.

# LightClaw Memory Layers Notes (Phase 2, 2026-05-16)

- **Three-tier dir layout under `<memoryDir>/`**:
  - **L1 (user root)** — `<memoryDir>/*.md` + `<memoryDir>/MEMORY.md`. Written by `main` (orchestrator), `extract_memories`, and `auto_dream` (all kind ∈ `{orchestrator, internal}`). Pre-Phase-2 layout is byte-identical here, so old user memory dirs need no migration.
  - **L2 (cross-role workboard)** — `<memoryDir>/_shared/*.md` + `<memoryDir>/_shared/MEMORY.md`. **`auto_dream` is the only writer** (enforced physically — no other Role's tool list contains `MemoryWriteAt` / `MemoryMove` / `MemoryDelete`). Filename convention `<YYYY-MM-DD>-<topic-kebab>-by-<source-role>.md` is enforced by the autoDream prompt, not the filesystem. Read scope `'shared'` is what makes an entry visible from another Role.
  - **L3 (role-private)** — `<memoryDir>/<agentType>/*.md` + `<memoryDir>/<agentType>/MEMORY.md`. Written by a worker Role when `getCurrentRole()` is that worker. `resolveMemoryDirsForRole` (`src/memory/scope.ts`) puts worker `selfWriteDir` at `<root>/<agentType>`; orchestrator + internal `selfWriteDir` stay at `<root>`.
  - All three tiers are **lazy mkdir**: `auto-memory.writeMemoryFile` (`src/memory/auto-memory.ts`) `mkdir -p`s before the first write. An old user with only L1 files sees no new directories until a worker actually writes or autoDream promotes.

- **Read visibility is framework-derived, not role-authored.** `ContextPolicy` and `memoryScopes` are gone. `resolveMemoryDirsForRole` gives orchestrator roles L1 + L2, worker roles L1 + L2 + their own L3, and internal roles L1 + L2. `resolveReadableMemoryDirsForRole` appends every existing top-level worker L3 only for internal roles, so curators can see the full tree without giving normal workers cross-worker private memory.
  - `MemoryRead` still rejects explicit nested reads into another worker's L3. Workers can read root-level L1 files and `_shared`, but `web` cannot ask for `general-purpose/foo.md`.
  - Writing is independent of readable dirs — see next bullet.

- **`MemoryWrite` is path-bound by `SessionContext.currentRole`, not by tool input.** `src/tools/memory-write.ts:call()` reads `getCurrentRole() ?? getMainRole()`, computes `selfWriteDir` via `resolveMemoryDirsForRole(role, memoryDir)`, and writes there. The tool schema has **no `scope`, no `path`** parameter — agent has no language to ask for any other location.
  - Path-scoping enforcement: `memoryPathWithinDir(targetPath, selfWriteDir)` rejects any filename that resolves outside `selfWriteDir` (filename injection like `../foo` denies on every call).
  - Every call writes `<lightclawHome>/audit/memory-writes/<YYYY-MM-DD>.jsonl`. Schema: `{at, userId, role, filename, targetPath, status: 'written'|'denied', deniedReason?, operation?: 'write'|'read'}` (`src/audit/memory-writes.ts`).
  - `currentRole` is populated by `query.ts` for main turns and by `runDispatchedAgent` for dispatched workers, so each worker writes into its own L3 (or the user root for orchestrator / internal kinds). Do not bypass — manually constructing a `SessionContext` without `currentRole` falls back to `getMainRole()`, which lands writes in L1 even if the caller is logically a worker.

- **`MemoryWriteAt` / `MemoryMove` / `MemoryDelete` are `auto_dream`-Role-only.** Tagged `internalOnly: true`, hidden from `getAllTools()` / ToolSearch, and present **only** in `auto_dream.tools`. Never add them to any other Role's `tools` list without admin discussion — that would let extract / a worker / a future role write into another role's L3 or into `_shared/`, breaking the "autoDream is the sole curator" invariant.
  - All three paths must resolve under `<memoryDir>` via `joinAndAssertWithinMemoryDir` (`src/memory/tool-path.ts`) — absolute paths or `..`-escapes throw `MemoryToolPathError` and don't write.
  - All three **reject `basename === 'MEMORY.md'`** via `assertNotMemoryIndex`. `MEMORY.md` is framework-owned: every successful op calls `rebuildMemoryIndex(<affectedDir>)` (`src/memory/auto-memory.ts:322`) to regenerate the per-tier index from the surrounding `*.md` files. An agent-authored index would be silently overwritten on the next op, and a deleted index would reappear; refusing at the tool boundary is the clean failure mode.

- **autoDream is per-canonical-user single instance — never split by role.** Promotion is inherently a cross-role decision; per-role splits would lose the very signal autoDream exists to consume. `<memoryDir>/.consolidate-lock` + the per-user scan throttle + the extract/dream mutual-exclusion (`isExtractionInProgressFor(memoryDir)`) all run per canonical user. Phase 3 kept this invariant.

# LightClaw Per-Role Extract Notes (Phase 6, 2026-05-17)

- **Worker transcripts are persisted before role-owned extraction runs.** `runDispatchedAgent` writes completed worker messages to `<sessionsDir>/<parentSessionId>/forks/<roleAgentType>-<forkId>.jsonl` via `persistForkTranscript()`. The directory and helper names keep the historical "fork" label for on-disk compatibility; the runtime semantics are dispatch-only. The write is best-effort and returned as `forkTranscriptPersisted`; extraction waits for that promise, while the user-facing worker result is not blocked by a failed persistence write.
- **Per-role extraction runs for worker roles when auto-memory is enabled.** `runSubagent()` calls `triggerForkExtract()` for `kind:'worker'` roles. The extraction fork still runs as `extract_memories`, but `currentRoleOverride` points `MemoryWrite` at the owner role's L3, so a `web` extraction writes under `<memoryDir>/web/`, `explore` writes under `<memoryDir>/explore/`, and so on.
- **Fork transcript JSONL carries a meta marker as its first line.** New dispatch transcripts write `{"kind":"fork-transcript-meta","forkContextEndIndex":0}` because there is no inherited parent prefix. `parseForkTranscriptFile()` still supports older nonzero markers and marker-less files, so previous transcript files remain readable. Do not move the marker to a sidecar `.meta.json` or drop it — extraction slicing depends on it.

- **Existing-memory visibility follows the owner role's readable dirs.** `collectExistingMemoriesForRole()` uses `resolveMemoryDirsForRole(ownerRole, memoryDir).readableDirs`, so `web` compares against `<memoryDir>/web/` plus `_shared/`; `main` compares against L1 plus `_shared/`; internal curators keep their broader read visibility.
- **Fork transcript retention is opportunistic and throttled.** The extraction pipeline runs `maybeSweepForkTranscripts(config.sessionsDir)` after normal extraction cleanup. Default behavior deletes fork JSONL files older than 7 days and stamps `<sessionsDir>/.last-fork-sweep` so the sweep runs at most once per 24 hours. Session enumeration sites (`branch-merge.ts`, `background-task/session-resolve.ts`, `identity/store.ts`, `tools/_session-helpers.ts`) filter by `entry.isDirectory()`, so the stamp file (and any future hidden file alongside) never leaks into session-id enumeration.

  - `chain-abort-propagation` (process-wide): subscribes to `notification{kind:'abort', broadcast:'chain'}` and handles legacy in-memory chain aborts; TaskRun-ledger waiting owns durable background-fire stop semantics.

# LightClaw Dispatch Notes (Phase 10, 2026-05-19)

- There is one healthy LLM-visible execution stack since collab-phase3 PR16. # LightClaw TaskRun Notes (collab-phase1 PR1-PR7, 2026-06-10)

- `src/taskrun/store.ts` is the durable TaskRun ledger. Each run lives at `<lightclawHome>/users/<canonical>/taskruns/<id>/` with append-only `events.jsonl` plus derived `meta.json`; `meta` is only a snapshot of events and may gain derived fields later without migrating the event stream.
- PR1 wrote lifecycle events: `created`, `started`, and `finished`. PR2 adds `progress` and `artifact`. PR4 adds `delivered` / `accepted` / `rejected` / `cancelled`; PR6 adds `watchdog-report`; PR7 adds `escalated`; collab-phase2 PR9 adds `paused` (renamed `waiting` in the 2026-06-10 wait rename; readers accept both kinds); collab-phase3 PR12-PR16 adds `checkpoint`, `resumed`, `rebuilt`, and wake metadata on the waiting event. Future message and checkpoint data must still be added as new event kinds, not by changing the lifecycle schema.
- **Terminal states are two-phase since PR4 (delivered, then accepted).** A worker-side conclusion (success or failure report) lands the run at `status:'delivered'` — NOT terminal. Acceptance writes `accepted` + `finished` (done/failed per the delivered outcome). Since collab-phase3 PR12, rejection writes `rejected` but keeps the run `running` so the framework can resume the worker with feedback; only a later deliver/accept/cancel path finishes it. A delivered run counts as a root obligation, which is what keeps an undelivered background result visible instead of letting its root close over it.
- **Acceptance settles edge-by-edge up the tree (PR5).** Each parent settles its own direct children — a worker accepts/rejects the runs it dispatched (stack-like unwind), it is NOT all funneled to main. Transitional fallback until collab-phase3 re-animatable parents: the orchestrator may settle any delivered run inside its own rooted trees (a one-shot worker that already returned cannot settle its children); free-forest runs (top-level non-rooted) are out of its reach and wait for the watchdog.
- **`TaskUpdate` is the single state-machine tool** (deferred / host / safe, visible to workers): `action:'deliver'` has ONE meaning for every caller — conclude a run you own — and forks mechanics on the TARGET's structure, not the caller's role (2026-06-10 structural-refactor ruling: a tool verb must mean the same thing for every role; role differences are only visibility gating and permission scope, the legacy-tool pattern). A non-root target must be the caller's `currentTaskRunId` (records `ok` + `summary`, parks at delivered); a `kind:'root'` target closes through the settled-ledger gate (orchestrator-scoped, refused with an itemized obligation list until each is settled). `action:'accept'|'reject'` targets a `delivered` run on a parent edge per the rule above; reject requires `feedback` and now resumes rather than closes the child. `action:'wait'` without `runId` sets the caller's own run waiting with a checkpoint plus `wake` (`child-join`, `timer`, or parent-reply/awaiting-reply); `wait` with a direct-child `runId` asks a currently running child to stop and stores `requester-hold`. `action:'cancel'` cancels queued/waiting/running work by TaskRun runId: main can cancel runs inside any of this user's rooted trees, while a worker can cancel direct children. Running cancellation aborts the run's `currentSessionId` before marking it cancelled. A standing service root runId shuts down the whole service (remove entry, cancel/abort current child, close the standing root). Cancelling the queued current child of a standing service is refused with routing guidance — the entry would re-fire or recreate that slot, silently undoing the cancel; stop the service via its root or suspend it via `UpdateSchedule enabled:false`. A dispatch entry id is accepted for one compatibility window and resolved to the backing runId. The orchestrator scope for accept/reject/cancel is **user-scoped, not chat-scoped** — the watchdog batches findings per owner and may wake main in any chat, so the disposition verbs must reach every root of the user (chat isolation applies to `/stop` execution, not ledger settlement). `TaskAccept` / `TaskClose` were retired into it. Workers still cannot create roots (`TaskCreate` stays in BLOCKED_WORKER_TOOLS).
- **`markDelivered` is idempotent** (only queued/running/blocked → delivered; since collab-phase2 PR9 `waiting` is NOT overwritten — a late completion path must not flip a user-stop): a worker that explicitly delivered via TaskUpdate keeps its self-reported outcome — the framework's settle-on-return / fire-terminal markDelivered becomes a no-op instead of overwriting it. **`markStarted` likewise never resurrects a terminal run** — a late fire path against a cancelled/done/failed run is a no-op that keeps the terminal state, instead of the unconditional started reducer flipping it back to running.
- **The `<background-task-result>` envelope carries `taskRunId`** (threaded scheduler → deliverCompletion → notification payload → block render; omitted when the best-effort store write failed) so the receiver — main or a live spawner worker — can settle the run via TaskUpdate. Template prose is untouched; model-facing wording is finalized in the dedicated end-of-project prompt PR.
- `latestProgress` and `artifactPaths` are derived meta pointers only. The source of truth remains `events.jsonl`.
- PR3 adds `TaskRunMeta.kind?: 'root' | 'dispatch'`. Missing `kind` means legacy dispatch. A root is a management container created by `TaskCreate` or by the framework for a standing recurring/interval service; a dispatch node is a worker/background execution unit. Standing service roots carry `standing:true`.
- TaskRun persistence is best-effort. Dispatch and scheduler callers catch store failures, write one stderr diagnostic, and keep the original dispatch/background behavior unchanged.
- `TaskCreate` is main-only, deferred, safe, and create-only. It creates a running root TaskRun and returns the root `runId`; it does not dispatch workers or encode workflow judgment.
- A root reaches terminal state ONLY through the orchestrator's `TaskUpdate {action:'deliver', runId:<root>}` — there is no automatic close. The close is gated on a settled ledger: open obligations (running/queued runs, delivered runs awaiting acceptance, legacy pending oneshot entries) cause a structured rejection listing each item. `finalizeSettledRoots` (PR3's main end-turn auto-close) is deleted — it could close a root as done while a failed-delivery result sat unconsumed, permanently masking the orphan from the watchdog.
- Main finite Dispatch (`schedule:'now'`, `after`, `oneshot`) must pass `task` pointing at an open root TaskRun for the current user. Missing or invalid `task` is rejected before signal publication / TaskRun creation, with a self-heal hint to call `TaskCreate`.
- Worker Dispatch ignores `task` and continues to inherit `parentRunId` from `SessionContext.currentTaskRunId`.
- `recurring` / `interval` Dispatch entries are standing top-level services **for any caller**. The framework creates one `standing:true` root plus one current queued child at dispatch time; each fire starts that child, delivers it for acceptance, then completion handling creates the next queued child under the same root. The standing root never attaches under the caller's current work root, so a worker-created recurring service cannot keep an unrelated root from draining. Stopping the service is `TaskUpdate { action:'cancel', runId:<standing-root-run-id> }`: remove the bg entry, cancel/abort the current child, then close the standing root once obligations are clear.
- Background Dispatch uses the existing `bg-tasks.json` scheduler plane. **Oneshot (and now/after-normalized) entries create their durable run at dispatch time** (`status:'queued'`, persisted as `BackgroundTaskEntry.taskRunId`) so scheduled-but-not-fired work is visible in the tree and counts as a root obligation; the scheduler marks it `started` at fire time and retries reuse the same run. The fire's terminal conclusion (success or failure) lands at `delivered` and awaits explicit acceptance. Recurring / interval entries persist `standingRootRunId` plus current-child `taskRunId`; legacy entries without `standingRootRunId` keep the old per-fire `finished` behavior until recreated.
- **Resume is TaskRun-ledger driven (collab-phase3 PR12-PR16).** `resumeRunWithBlock()` reopens a running/waiting worker by its last recorded session transcript, injects a `<taskrun-resume>` block, and records `resumed`; when the session gap is too large or the transcript cannot be loaded, it may rebuild from the stored checkpoint and record `rebuilt`. `Message { to:<runId> }` routes running children as interjections and waiting children through this resume primitive; a no-target Message is an ask-to-parent path and must include `default` so the worker can time out and continue.
- **Resumes execute DETACHED through `scheduleResumeRunWithBlock` (`src/taskrun/resume-schedule.ts`), never inline.** A resumed shift can run for minutes; awaiting it inside the triggering call (TaskUpdate reject, Message to a waiting run, a child-join wake at delivery time) would freeze the caller inside a tool call — the exact shape retiring blocking dispatch removed. The scheduler serializes per run, captures the ambient SessionContext when one exists, and otherwise builds an owner context mirroring `runBackgroundTaskFire`'s resolution. `resumeRunWithBlock` itself carries the awake-already guard: if the run's last session still has a turn in flight, the block joins that live turn as an interjection and the ledger flips back to `running` — never a second agent loop racing the live one on a single transcript. The ask parent-unavailable fallback settles in place for the same reason (answered(auto) + markResumed on the current session + default handed back through the tool result); it must not resume its own session mid-turn.
- **The child-join wake fires at the child's TURN-END, carrying its full final reply** (2026-06-13). `wakeParentForChildJoinBestEffort` (in `resume.ts`) takes an optional `resultText` and is called from the two places a run's turn actually ends: the scheduler's settle-on-return `markBackgroundTaskRunTerminalBestEffort` for a fire (passes `outcome.summary` = the worker's uncapped final reply), and `resume.ts` after a resumed run's query (passes `result.assistantText`). It is **no longer called from TaskUpdate explicit deliver** — mid-turn a self-delivering worker has no final reply yet, only the capped `summary` label, and waking from there fed a parent that explicitly waited a 500-char label instead of the result it was owed. The ledger `outcome.summary` (capped) is now only the cold-backstop fallback inside `wakeParentForChildJoinBestEffort` for the watchdog reconcile. Blocking dispatch is retired, so a fire ends in exactly one of those two turn-end paths (never both); the parent's `consumed` guard still backstops a watchdog wake racing the live one. `wakeParentForChildJoinBestEffort` returns whether it woke a parent so `onFireComplete` can **suppress the now-redundant bg-result notification** to that same parent (the explicit wait already delivered the full result inline; pushing it again via `deliverCompletion` would deliver it twice). Do not re-add an inline wake at the TaskUpdate deliver site — that reintroduces both the label-truncation and the double-delivery.
- **Due declared wakes are executed by the watchdog reconcile, not reported to main**: a fired `timer`, an ask past `wake.timeoutAt` (append `answered(auto, timeout)` and continue with the declared default), or an awaited child that already settled without the deliver-hook landing. This is also the restart re-arm — the in-process `setTimeout`s for timer/ask die with the daemon, the ledger does not. A wake surfaces as a `dead-wake-source` finding only after its resume attempt failed (`getLastResumeFailure`).
- `TaskUpdate cancel` of a run with a finite backing entry removes that entry, marks queued/waiting runs `cancelled`, and hard-aborts a running fire's `currentSessionId` before marking the run `cancelled`. The scheduler treats abort-like fire outcomes as `aborted` terminal scheduler outcomes: no retry, no completion notification, and no delivered overwrite of the cancellation/waiting state. Standing services should be stopped by cancelling the standing root. `TaskUpdate` retries gated close after each accept/reject verdict whose settled run sits under a `standing:true` root with no live dispatch entry backing it — the verdict on the last open obligation is what actually closes an orphaned standing root.
- `BackgroundTaskEntry.parentTaskRunId` is optional lineage metadata captured at schedule time for finite root-attached main dispatches, worker-created background dispatches, and the standing root parent of recurring/interval current children. It does not change scheduling, list/update/cancel semantics, or the v2 store shape for older entries. `getRootObligations`' bg-tasks scan only backstops legacy entries without `taskRunId`.
- `TodoWrite` remains the real-time progress publisher. PR2 only appends a durable `progress` event at the existing progress bus emission point when `SessionContext.currentTaskRunId` is present; channel forwarding still consumes the signal bus, not TaskRun reads.
- `TaskInspect` is a deferred, read-only host tool over the current user's TaskRuns. Main can inspect any run for the current user; workers can inspect only their current TaskRun and descendants. Inspecting one run returns recent events, direct `children`, and a full recursive `tree`. Runs backed by a live background entry include schedule metadata (`schedule`, `nextRunAt`, `enabled`, `label`, `dispatchId`) on the inspected run and tree/list summaries.
- Artifact recording is deliberately narrow in PR2: worker finish paths may declare handles found in final text / successful background outcomes, but Write / Feishu tool internals are not hooked. If artifact capture needs a broader producer protocol, move that whole step to PR3 instead of adding an in-between PR.
- Crashes are intentionally honest: if a process dies after `started` but before a delivered/terminal mark, the run remains `status:'running'` with `currentSessionId` set.
- **TaskRun watchdog (PR6 + collab-phase2 PR9/PR11)** is level-triggered and read-only over run state: it reports `queued`/`running` dispatch nodes when there is no active session, no bg-task entry still pointing at the run (enabled or suspended), and no in-memory scheduler claim; it reports `delivered` nodes only after `taskrun.watchdog.deliveredGraceMs` and only when the receiver session is not in-flight; and it reports non-root `waiting` nodes after `taskrun.watchdog.waitingGraceMs` (0 disables). Roots that are merely open are not stranded. Delivery is **parent-first since collab-phase3 PR15**: findings are grouped by direct parent; a live parent gets the `<taskrun-reconcile>` block as an interjection, a non-live but still-actionable parent (not queued/terminal, no failed resume) gets a revived shift via the detached resume scheduler, and only the leftovers batch into one wake for main through `wakeOrInterject`. Each reported run then gets `watchdog-report { fingerprint }` appended. The fingerprint ignores prior watchdog/escalation events so the report marker does not make itself re-fire; a later real run event changes the fingerprint and naturally re-arms reporting.
- **TaskRun watchdog escalation (PR7, layered per 2026-06-10 review)** bounds recovery loops and escalates UP ONE LEVEL at a time — interfaces are layered (user↔main, child↔parent), the framework never bypasses main while main is reachable. Three same-fingerprint watchdog reports inside `taskrun.watchdog.budgetWindowMinutes` → one final **escalation-marked reconcile wake to main** (`<taskrun-reconcile ... escalation="stalled-reconcile">`) so main decides: change approach, cancel, or report to the user through its own channel; then `escalated { fingerprint, reason }` is appended to the root (or the finding run if the root is missing) and waking stops for that fingerprint. The direct owner-DM system notice is reserved for the genuine bypass case — **main itself is unreachable**: `taskrun.watchdog.deliveryRetryMaxAttempts` failed reconcile deliveries, or the escalation wake itself failing to deliver. Any later non-watchdog/non-escalation event changes the fingerprint, clearing the stop condition without a manual reset.
- Terminal TaskRun directories may be swept after the default 7 day TTL, **but never while their tree still has any non-terminal run** — sweeping a terminal mid-tree node breaks `parentRunId` reachability and would silently drop live descendants from obligations / TaskInspect under an open root. Non-terminal directories are never swept.

# LightClaw User-Defined Role Notes (Phase 7.5, 2026-05-18)

In-flight dispatches keep their spawn-time role definition.

# LightClaw Agent-Centric Notification Notes (Phase 4, 2026-05-16)

- User-visible background results follow the manager model: a bg-dispatch fire's output flows back as a `<background-task-result>` block injected into the receiver's prompt (in-flight via interjection queue, idle main via synthetic Feishu turn). **Receiver = spawner when the spawner is still alive in the chain registry; main otherwise (the historical default).** `scheduler.deliverCompletion` resolves the receiver via `resolveLiveWorkerSpawner(task.chainState, liveSessions)` (2026-05-18) — walks `path[length-2]` down to `path[1]`, skipping main at index 0 since main never registers itself in `chainRegistry`. First live worker ancestor wins; all-dead returns null and the legacy main origin/DM resolution path takes over. Receiver-aware delivery makes worker→bg→worker dispatch lifecycles coherent (the spawning worker, when still mid-turn, sees the result via interjection at its next tool boundary) without changing the main-receiver path.
- `<background-task-result>` is formatted by `src/signal-bus/background-result-block.ts`, which ships **two prose templates** (split 2026-05-18, both rewritten 2026-05-19). `BACKGROUND_TASK_RESULT_BLOCK_MAIN_TEMPLATE` carries the "you, the manager" framing and now has three options (plain reply / autonomous next step / Notify) under an explicit "unattended agent" default: every result is surfaced to the user via plain reply, autonomous follow-up taken when the path forward is reasonably clear, Notify reserved for three narrow triggers (user input required to unblock / major must-not-miss information / user-only intervention). The pre-2026-05-19 "continue silently" option was deleted — silent swallow on the main tier leaves the user blind to delegated work in flooded-info channels, which defeats the point of background dispatch. The XML envelope still includes `aborted` in the outcome enum for wire-format stability; collab-phase2 PR9/PR10 abort paths intentionally suppress completion delivery before this block is rendered, so if `aborted` ever surfaces from a legacy/internal path the model-facing fallback is enough. `BACKGROUND_TASK_RESULT_BLOCK_WORKER_TEMPLATE` mirrors the unattended-agent posture inside the worker's narrower channel: final-text is the only output, autonomous follow-up taken when the path is clear, surface in final-text when the requester needs it, silent absorption legitimate for genuinely irrelevant exploratory checks. The worker template has no Notify equivalent since workers do not own that capability. Both templates now name `UpdateSchedule` / `TaskUpdate cancel` as the self-healing actions, matching the PR17 six-verb surface. `formatBackgroundTaskResultBlock` takes `receiverRole` and selects the template; the hook supplies `signal.to.id` so the prose at each receiver matches that receiver's actual capabilities.
- `Notify` is the strong user-facing card tool. It takes `{title, body, severity, target}` where `severity = info | warning | urgent` and `target = this-chat | user-dm`. It emits a `notification(kind:'card', fromTool:'Notify')` signal and then uses the active Feishu sender to push an interactive card to the current chat or the user's DM.
- The old wake-mode binary (`notify_user` / `stay_silent`) and `src/background-task/wake.ts` are gone. Background fires still run in isolated `bg-<canonical>-<task>-<fire>` sessions, but completion delivery no longer starts a separate wake query loop.
- Permission asks from background fires are handled at tool-call time through the active channel approver when one exists. Completion delivery does not own a special permission-card side path; permission denial, tool failure, and success outcomes all flow back through the same background-result signal path.
- `TodoWrite` emits a transparent `progress` signal when a todo flips to `completed`, rate-limited per session. The tool description is unchanged; progress emission is framework behavior, not prompt-visible motivation.
- **Phase 8 PR4 (2026-05-18) `scheduler.deliverCompletion` is emit-only**: removed direct `channelInterjectionQueue.push` / `runner.handleMessage` calls; now publishes `notification{kind:'background-result'}` and the `background-result-to-interjection` hook reproduces the prior direct-push behavior. For main receivers, collab-phase2 PR11 centralizes that reproduction in `wakeOrInterject`: in-flight push, idle synthetic turn, origin-aware/admin-only delivery guard, and pending synthetic merge all live in one helper. Hook is registered process-wide at `init.ts` startup via `registerBusSubscribers()`. Future scheduler additions go through publish, not direct call. 2026-05-18 extended this with spawner-aware delivery (see top of this section) and a broadened subscription to `{role:'*'}` so worker receivers are reachable. 2026-06-13: `onFireComplete` skips the `deliverCompletion` emission entirely when the fire just woke a child-join parent — that parent received the full result inline via its resume, so the bg-result would be a duplicate (see the child-join turn-end bullet above).
- **Phase 8 PR4 (2026-05-18) `/stop` became signal-bus emit-only for chain propagation**, but collab-phase2 PR9 adds a second local responsibility in the channel runner/command handler: pause the calling chat's active TaskRun tree and abort any associated `currentSessionId`, including `bg-*` running fires owned by that tree. The TaskRun ledger owns background fire pause/cancel semantics.
- **TodoWrite `progress` signal has a real subscriber as of Phase 8 PR3**: the `forward-progress-to-channel` hook (per-turn lifecycle for main role) subscribes and forwards milestones to the channel as plain text replies with 5s per-session rate-limit. Without the hook the signal still emits but goes nowhere — keep the rate-limit on the publish side (`todo-write.ts:88-92`) even if the subscriber is later replaced.
- **`progress` signal carries `chainPath` for attribution (2026-05-19)**: dispatched workers were silently published as `from/to.id:'main'` with `sessionId = main sessionId` because (a) `todo-write.ts` hardcoded `'main'` instead of reading `getCurrentRole()` and (b) `childCtx` in `dispatched-agent.ts` shallow-copied the parent ALS sessionId so `getSessionId()` inside the worker still returned the main sessionId. Net effect: a webSearcher TodoWrite completion landed in the channel as `Progress: 1/3 - <worker todo>` with no role tag, indistinguishable from main's own todos. Two coordinated fixes: (1) `todo-write.ts` reads `getCurrentRole()` + `getCurrentChainState()` and emits `from = {role: triggerRole, sessionId: triggerSessionId}`, `to = {role:'main', sessionId: chainRoot.sessionId}`, with `payload.chainPath = chainState.path.map(p=>p.role)` (defaults to `[currentRole]` when no chain). (2) `forward-progress-to-channel` reads `payload.chainPath` and prefixes worker progress with the same `[main → webSearcher]` breadcrumb shape used by `worker-activity-stream.ts`, leaving main-only chainPath bare. Subscription stays `role:'main'` because `to.id` is always `'main'`; the hook still indexes `activeMainSessions` by main sessionId so the lookup works after the sessionId-alignment change below. See also `# LightClaw Dispatched Worker SessionId Notes` for the ALS sessionId change that the publisher fix coordinates with.

# LightClaw Dispatched Worker SessionId Notes (2026-05-19)

- Dispatched worker ALS `getSessionId()` now returns the chain path's last node sessionId (`dispatched-<dispatchId>` for blocking, `dispatchId` for bg), not the parent main sessionId. `dispatched-agent.ts` assigns `childCtx.sessionId = chainSessionId ?? currentCtx.sessionId` so per-sessionId state (api-logger directory, todos persist, session-memory file, auto-extract/auto-compact hooks, abort controller registration) splits cleanly between main and each worker fork. The fork-transcript path `<parentSessionId>/forks/<role>-<forkId>.jsonl` still uses `currentCtx.sessionId` directly (captured before runWithSessionContext enters the worker scope) so on-disk "which main session spawned this fork" stays unchanged.
- `SessionContext.chainState?: ChainState` rides on the context so role-aware publishers (`todo-write.ts → progress`, future events) can resolve the chain path and chain-root sessionId without re-reading invocation state. `getCurrentChainState()` in `state.ts` is the read API. main turn entries leave the field undefined; dispatched-agent populates it from `params.chainState`. Do not mutate `chainState` mid-turn — it is a snapshot of the dispatch graph at spawn time.
- Pre-2026-05-19 the ALS sessionId fallthrough was a shallow-copy oversight, not a designed sharing channel. Framework code that needed a "worker-specific sessionId" already had one — `chainState.path.at(-1).sessionId` — used by interjection queue, scheduler bg-result routing, and chain registry. The two sessionIds being out of sync silently broke per-fork isolation for everything that called `getSessionId()` directly: e.g. `abortInFlightForSession(workerSessionId)` after a chain-abort signal couldn't find the worker's controller because `beginQuery()` had registered the controller under the main sessionId (overwriting main's own controller in the process). Worker ALS state is now aligned with the chain leaf.
- Test fixture guidance: any new test that constructs a worker SessionContext should set `sessionId` to the chain path's last node and populate `chainState`.
- **Internal roles do NOT write `session-memory.md` (2026-06-08).** `kind:'internal'` maintenance roles (`memoryExtractor` / `memoryCurator` / `skillCurator` / `skillConsolidator`) carry no `chainState`, so their `childCtx.sessionId` falls back to `currentCtx.sessionId` — the triggering turn's id (often a dispatched worker like a background job watcher). `query.ts`' `maybeUpdateSessionMemory` early-returns on `rolePolicy.kind === 'internal'`, the single chokepoint for both the mid-turn kick and the end-of-turn flush. Without it, an auto-dream curator pass that crossed the session-memory thresholds wrote its working memory to the *triggering* session's `session-memory.md` and clobbered it (dogfood: a `skillCurator` pass overwrote a still-monitoring watcher's job-monitoring memory with "Skill Discovery …"). These runs are one-shot / fresh-context / never resumed, so they have no durable working memory worth persisting; a rare mid-run compaction falls back to the compaction summary itself. The fork-transcript still lands under the triggering session (provenance, non-destructive) — only the session-memory write is suppressed. Do NOT re-enable session-memory for internal roles without first giving them an isolated sessionId (note: `listSessionsTouchedSince`/`gatherDreamSessions` do not filter ephemeral prefixes, so a new internal session dir would leak into the dream's own scan).

# LightClaw BackgroundTask Notes

- BackgroundTask is now the internal scheduler/storage plane behind background-only `Dispatch({ schedule:... })`. The LLM-visible scheduling surface is `Dispatch` + `UpdateSchedule`; inspection and cancellation are TaskRun-owned via `TaskInspect` / `TaskUpdate cancel`. Scheduled jobs still run later in an isolated `bg-<canonical>-<task>-<fire>` session and still use the existing background-task store/scheduler/runner modules.
- Schedule shapes accepted at the Dispatch boundary: `oneshot { at: ISO8601 }`, `after { afterMinutes }` (one-time, normalized to oneshot at spawn / update time — never persisted as `'after'`), `recurring { daysOfWeek, hour, minute }`, `interval { everyMinutes, anchorAt? }`. The `'after'` shorthand exists specifically because LLMs reliably mishandle "1 minute test" / "remind me in 5 minutes" — they tend to either miscompute an ISO8601 timestamp for `oneshot` or, worse, silently fall through to `interval { everyMinutes: 1 }` and create a recurring task. Dispatch create and `UpdateSchedule` rewrite `'after'` into `'oneshot'` with `at = now + afterMinutes * 60_000` before storage; `schedule-calc.computeNextRunAt` also has a defensive `'after'` branch but stored entries should never carry that kind.
- Current surface: `src/signal-bus/*`, `src/tools/dispatch.ts`, `src/tools/notify.ts`, `src/audit/dispatch.ts`, `src/signal-bus/chain-state.ts`, `src/signal-bus/chain-guard.ts`, and the existing background-task store/scheduler/runner. `src/background-task/wake.ts` and the wake-only tools were removed in Phase 4; wrapper tools were removed in Phase 7 PR5.
- The cron/background agent is isolated but not a separate query implementation. `runBackgroundTaskFire()` builds a fresh bg SessionContext, resolves the task role, and delegates execution to `runDispatchedAgent({mode:'bg'})` with `subagentLabel: 'background_task'`. The fire writes its own `bg-<canonical>-<task>-<fire>` transcript and fork transcript through the dispatched-worker path.
- BLOCK matrix:
  - Worker roles are blocked from recursive delegation unless their Role explicitly includes `Dispatch` and `reachableRoles`. `TodoWrite`, `MemoryWrite`, `MemoryRead`, and role-visible task tools are allowed when present in the role's `tools` list.
  - BackgroundTask isolated agents are allowed normal tools by role/policy and are still bounded by Dispatch chain guards when they dispatch.
  - Main agent normal/wake mode no longer has special wake-only tools; `Notify` is the explicit escalation tool.
- Store shape is per canonical user at `<lightclawHome>/users/<canonical>/state/bg-tasks.json`, versioned as `{ version: 2, tasks: [...] }`. Required task fields include `id`, `ownerCanonicalUser`, `prompt`, `role`, `schedule`, `label`, `notifyOn`, `notifyTo`, `enabled`, and `createdAt`; optional fields include `lastFiredAt`, `pendingPriorPromptNotice`, `originSessionId`, `chainState`, `parentTaskRunId`, `standingRootRunId`, and `taskRunId`. Version 1 files lazy-migrate on read, and old v2 failure-state fields are discarded before schema parse. Successful oneshot tasks are removed after completion; failed oneshots stay in the store with `lastFiredAt` for visibility through `TaskInspect` and schedule management through `UpdateSchedule`.
- **Phase 8 PR5 (2026-05-18) `BackgroundTaskEntry.role`**: store entry now carries the worker `agentType` (`generalist` / `webSearcher` / etc., or a user-defined role name) populated by `executeDispatch` from `input.role`. `TaskInspect` surfaces that role via the backing TaskRun and schedule metadata; loader injects `role: 'generalist'` for pre-PR5 entries lacking the field so on-disk v2 stores migrate without dropping tasks. Required field in zod schema.
- The scheduler's resource cap is per canonical user (`backgroundTask.maxConcurrentRunsPerUser`, default 3), not global. One user filling their three fire slots must not block another user's three slots. Overflow fires queue FIFO under that user.
- Startup catchup compensates missed oneshot tasks with stagger; recurring catchup is intentionally not retroactive (next run computed forward from now). Phase 9 PR1 removed `recoverOrphanedBranchPlaceholders` — legacy `branchPlaceholder` user messages in old transcripts become inert text on the new daemon (no recovery sweep runs since `/b` `/branch` `/fresh` are gone).
- Fire delivery path (`scheduler.deliverCompletion`) publishes a `background-result` signal. Successful fires, ordinary failures, and permission-denied failures are delivered as `<background-task-result>` blocks to the spawner when it is a live worker (see `# LightClaw Agent-Centric Notification Notes` for spawner-aware delivery), otherwise to the main agent via origin/DM resolution. If no delivery target can be resolved, the result is logged and left out of the agent loop.
- **Main-session result resolution (origin-aware).** `scheduler.deliverCompletion` prefers `task.originSessionId` (captured at BackgroundTask/Dispatch create time from `getSessionId()`) when it parses to a Feishu DM or group session id AND its transcript directory exists on disk. Resolved via `resolveOriginWakeSessionId(originSessionId, sessionsDir)` in `session-resolve.ts`. Fallback to `resolveWakeSessionId(canonicalUser, sessionsDir)` picks the most-recent active DM for legacy entries or deleted origins. When neither resolver works, the result is logged and left out of the agent loop rather than fabricating the old pre-Phase-26 `feishu-<canonical>` orphan session id.
- **Agent-centric delivery follows origin.** In-flight origin sessions receive the formatted background-result as an `InterjectionEntry` with `source:'background-task'`. Idle origin sessions get a synthetic Feishu message with the block as user text, so the normal ChannelRunner path starts a continuation turn under the same sessionId. Group-origin results therefore return to the group slice that created the task; DM-origin returns to the DM. The main agent then decides whether to stay silent, reply, adjust, or call `Notify`.
- **Admin-only gate.** Mirroring `runner.ts:56-66`, `scheduler.deliverCompletion` refuses agent-centric result delivery when `runtime.backend === 'local'` and `getAdmin() !== canonicalUser`. That prevents a paired non-admin's background result from re-entering LocalRuntime through the synthetic main-session turn.
- Shutdown paths must drain in this order: memory extraction, autoDream, then BackgroundTask. The CLI already calls `drainPendingBackgroundTasks(60_000)` and stops the scheduler; new daemon exits should keep that drain.
- Background result block prose lives in `src/signal-bus/background-result-block.ts`; user-visible scheduler/system strings go through `t()` (`bg.card.*` / related keys). Keep LLM-facing fire envelopes in English and user-facing notices in i18n.
- Background fire permission asks use `getChannelApproverFor(task.ownerCanonicalUser, sessionId)` so high-risk operations can reach the same Feishu card UX as foreground turns. If the active runner or channel binding is absent, the background fallback in `requestPermission()` auto-allows only non-high-risk asks under the role's tool scope and denies high-risk asks with detail captured in `FireOutcome.permissionDenials`.
- `matchBashCommand` is chain-aware: it splits top-level `;` / `&&` / `||` / `|` / `&` and any segment can match a `Bash(<head>:*)` pattern. This closes the old `cd /tmp && rm -rf foo` gap for deny rules and also keeps allow behavior consistent for pipelines such as `grep foo | wc`.
- **`UpdateSchedule` accepts `prompt`** (alongside `schedule` / `label` / `enabled`) for queued one-shots and future recurring/interval fires only — a one-shot whose fire is in flight (running OR waiting mid-shift) is refused with routing guidance, since the fire already consumed the prompt and a one-shot has no future fires. When a new prompt differs from the existing one, the prior prompt is stashed in `task.pendingPriorPromptNotice` and consumed once by `scheduler.deliverCompletion`. A second prompt update before the next fire overwrites the field; the first prior prompt is intentionally lost rather than chained, to avoid unbounded growth and noisy repeated notices.

# LightClaw Skill Dispatch Brief Notes (dispatch-brief track, 2026-06-16)

- **`dispatch_brief` is a skill's manager-facing pre-dispatch contract**, distinct from the two existing skill faces: `when_to_use` answers *when to route here*, the body answers *how to execute* (worker-only), and `dispatch_brief` answers *what a delegator must settle before handing the work off, and what to leave to the worker*. It exists to close the 2026-06 dogfood failure where main (a read-only manager) directed a worker on work whose intake requirement lived only in the worker's skill body — main never saw "ask the user for the image", so it sent the worker probing. Knowing-nothing → misdirect; knowing-the-whole-procedure → main does it itself. The brief is the middle: the contract main needs, not the procedure it would overreach with.
- **Parsed in `loader.ts` (`dispatch_brief` → `SkillMeta.dispatchBrief`, trimmed, omitted when blank) and codegen `build-bundled-skills.ts`; both must stay in sync** (same shape as `when_to_use` → `whenToUse`). It is frontmatter, never body — so it is stripped from the body the worker loads.
- **Rendering is all-tool: a brief surfaces ONLY through `ListRoleSkill`, never inlined into the static prompt.** The PR2.1 decision: inlining every reachable worker's brief into `## Reachable Workers` grows main's per-turn prompt unboundedly with skill/worker count. So Reachable Workers stays names-only; `ListRoleSkill(role)` is the one-stop pre-dispatch briefing. `formatDispatchBriefForDelegation` prefixes the brief with `Before you delegate:`; an empty/absent brief renders nothing (no `dispatch_brief: None` line — `list-role-skill.ts` filters blank, the on-demand path guards `if (skill.dispatchBrief)`).
- **The brief reaches only the dispatching manager, never the worker running the skill.** Worker-facing paths render no brief: the auto-loaded workflow body comes from `loadRegisteredSkill().body` (frontmatter already stripped), and the worker's own `## Available Skills` listing (`formatSkillsSection`) renders only `description | when_to_use`. A worker never reads "Before you delegate: …" about its own skill — that would be a role-confused instruction.
- **`a37b563` boundary holds**: always-on workflow skills (`<role>-workflow`) are NOT routable capabilities — they are never named/listed as on-demand skills (`visibleOnDemandSkillsForRole` excludes `autoLoad`). But their brief still surfaces *unnamed* as the worker's "standing contract" in `ListRoleSkill` output (`visibleAutoLoadDispatchBriefsForRole`). Surface the contract, never the procedure.
- **`delivery-orchestration` is the brief's consumer, not a carrier.** It is main's own auto-load procedure (how main front-loads intake, settles requester-held inputs, hands a complete instruction). It has no `dispatch_brief` — main is not dispatched to.
- **Author a brief on intrinsic merit, not current routing topology.** A skill gets a `dispatch_brief` iff delegating its work would force the delegator to settle something a worker can't discover on its own — an external / costly / irreversible resource to pin (image, compile target, mountable data path), an unrecoverable step (a delete that can be refused), or a requester-owned judgment axis (review focus + acceptance signal). Pure read-only exploration / "the input is the whole task" → omit. Do NOT gate authoring on "is this skill dispatched-to today" — skills may be pushed down to workers later (e.g. `skillify` is on every non-internal worker). Bundled inventory result: `brainpp-batch-job` (rich), `build-environment` / `archive-workflow` / `feishu-doc-workflow` / `pre-delivery-review-workflow` / `skillify` (light) carry briefs; `coding-workflow` / `local-exploration-workflow` / `web-research-workflow` / `remember` / `delivery-orchestration` carry none.
- **The write/maintain chain is self-sustaining** so user-authored skills don't reopen the gap: `skillify` (Step 3 teaches when/how to author a brief — manager-facing, what-to-settle not how, only the four needs in the requester's domain, conditional sink for cross-dispatch capture), `skillCurator` (drafts new skills with the same NEEDED judgment), `skillConsolidator` (carries a brief through a merge, rewrites for the merged contract, never silently drops one), and `SkillWrite`'s description lists `dispatch_brief` as a supported frontmatter field. PR1 parse + round-trip already persists it for user skills.
- **`stampFrontmatterRoles` (loader.ts) must stay block-scalar-safe.** It rewrites `roles:` on every non-internal role-stamped save (a worker self-saving via `skillify`). Do NOT reintroduce a global `\n{2,}` → `\n` collapse there — it silently eats intentional blank lines inside a multi-line `dispatch_brief: |` literal block scalar, rewriting the field's content. The `d1cc662` fix removes the existing `roles:` block plus only the single line break it left, mirroring the single-line in-place edits in `recordSkillUsage` / `stampArchivedAt`.
- **Role input to `ListRoleSkill` / `Dispatch` is leniently resolved** via `resolveAgentLenient` (`role-resolver.ts`): exact match first, else trim + lowercase + strip `-_\s`. No fuzzy / typo matching — only human-shaped spelling variants of a real role.

# LightClaw Test Determinism Notes

- **`pnpm test` runs at `--test-concurrency=16` on an 8-core box (2× oversubscription).** This is a deliberate throughput choice, but it means any individual test process can be descheduled by the OS for seconds while wall-clock time keeps advancing. Tests must therefore be deterministic under starvation — never rely on "enough wall-clock has passed for the async work to finish".
- **Never poll a wall-clock deadline to wait for in-process async completion.** The anti-pattern `const deadline = Date.now() + N; while (cond && Date.now() < deadline) { await sleep(5) }` false-fails when the process is starved past the deadline before the awaited effect lands (the 2026-06-22 `query-session-memory.test.ts` flake: it failed ~1/6 of full-suite runs). Instead, await the **actual** completion signal — a deferred `Promise` the code-under-test resolves. It can only "hang" if the feature is genuinely broken, which the node:test per-test timeout then converts into an honest failure rather than a flaky false one. (A wall-clock poll is acceptable ONLY when waiting on genuinely external I/O with no in-process signal — e.g. a subprocess writing a pidfile in `runtime/process.test.ts` — and even then keep the timeout generous.)
- **Do not assert on a fire-and-forget side-effect immediately after the call that triggers it.** `query.ts` intentionally runs session-memory updates / compaction / extraction non-blocking (the turn must not stall on a slow post-turn LLM write), so `await query(...)` resolving does NOT mean those side-effects have fired. A test that reads a counter right after the await is racing the side-effect. Thread a deterministic "started" / "finished" signal out of the stubbed updater and `await` it before the assertion.
