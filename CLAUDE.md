# LightClaw Runtime Safety Notes

- LocalRuntime is admin-only. When `runtime.backend = "local"`, paired non-admin users must not acquire a runtime; multi-user service must use DockerRuntime or RjobRuntime.
- Do not add path-string workspace guards to tools or permission policy. Runtime safety comes from the LocalRuntime admin-only gate, Docker/Rjob isolation, read-only mounts, and the Phase 5 permission system.
- RlaunchRuntime never uses `brainctl exec -i`. The cluster's brainctl exec drops stdin payloads silently (the `9cafbdc` writeFile incident: ~16% silent corruption) and also suppresses stdout when `-i` is opened with no real stdin. Every `ExecInput.stdin` is folded into the bash command body via `composeExecScript` (base64 inline + brace group so the pipe feeds the whole `&&` chain). Per-call cap is 32 KB raw — empirically the brainctl ws frame fails above ~57 KB total script. `fs.writeFile` chunks transparently above the cap; new tools that hand large payloads to a helper should chunk via `fs.writeFile` + read-from-disk rather than growing the cap.
- **Daemon-only fast IO (`writeFileViaHostMount` / `readFileViaHostMount`)**. RuntimeFs exposes optional methods that skip brainctl exec by going through the host-side bind mount directly (`fsp.writeFile` / `fsp.readFile` on the gpfs/virtiofs path that the worker mounts at `/workspace`). They are **harness-internal** — only call them from channel encoders, pairing materialize, future webfetch staging, or other code where the bytes have to flow into / out of the daemon Node process anyway. Tool implementations (`Read`, `Edit`, `Write`, `Bash` subroutines, etc.) MUST stay on `runtime.fs.readFile` / `runtime.fs.writeFile` so sandbox boundaries (path translation, perm narrowing, audit, future overlay rules) are preserved. The fall-through contract is explicit: both fast methods return `null` when the path falls outside `mountTable` or the host fs syscall fails (sticky-disabled per-runtime instance after first failure, log on flip), and the caller transparently falls back to the brainctl path. The two flags (read disabled / write disabled) are independent so a write outage does not also disable read. Tool-side `runtime.fs.readFile` is single-hop (`base64 -w 0 path`, capped at `READ_FILE_BUFFER_BYTES = 256 MB`) — the prior 512 KB dd-chunked protocol was retired after a 2026-05-10 byte-mismatch on a 4.5 MB PDF.
- **Provider content drop reporting via static probe**. Each provider exposes `detectStaticDropKinds()`, which probes its own message-shape translator (`convertMessages*`) with a synthetic message containing one block of every `AttachmentKind` and returns the kinds that fall out as dropped. `getProviderFor()` runs the probe ONCE per (endpoint, upstreamModel) on first lookup and writes `recordCapability(... false)` for every dropped kind so the channel-runner's `encodeAttachmentsForInline` short-circuits before any real upload — no waste read+base64+landing-in-transcript on the very first PDF turn. The probe is pure local computation: same convertMessages function streamChat would call, run on synthetic empty-base64 input. Single source of truth — `streamChat` and `detectStaticDropKinds` cannot drift apart because the latter literally runs the former's translator. Wire-side errors that ARE context-sensitive (proxy strips an `image_url` and returns 400, newer model variant rejects a previously-accepted shape) are caught by the reactive autopilot in `channels/runner.ts` via `isCapabilityMissingError`. There is intentionally no per-streamChat runtime drop event — for the schemas we have today (anthropic / openai / openai-auth), drops are deterministic schema-level facts that the static probe captures fully; a runtime event would just rewrite the same cache bit. New provider authors implement `detectStaticDropKinds()` by calling their convertMessages with a synthetic probe and returning what populated the optional `dropped: Set<AttachmentKind>` out-param.
- **Adding a new `AttachmentKind` requires three coordinated edits.** The static probe is single-source-of-truth ONLY when these stay in sync — otherwise the new kind silently bypasses precharge and you pay first-turn waste forever (the runtime `content_dropped` event was retired 2026-05-10, no other backstop precedes the wire). When extending `AttachmentKind` in `provider/types.ts` to add e.g. `'archive'` / `'mesh'` / whatever future modality:
  1. Add a probe block of that kind to **every** provider's `detectStaticDropKinds()` synthetic message (`anthropic.ts` / `openai.ts` / `openai-auth.ts` and any future provider). Empty base64 is fine — the probe doesn't care about content.
  2. Add a corresponding case in **every** provider's local `classifyUnsupportedBlock(blockType)` mapping (e.g. `if (blockType === 'archive') return 'archive'`). Forgetting this means the probe sees the block, but the classifier returns `null`, and the kind never enters the dropped Set even when the wire schema doesn't accept it.
  3. Add the matching declared default in each provider's `capabilities.attachments.<kind>` (typically `false` if unsupported, `'unknown'` if uncertain), and update encoder paths in `channels/attachment-encoding.ts` to emit and gate blocks of that kind.

  The reactive 4xx catch in `channels/runner.ts` will still flip the cache when a wire 4xx error message names the new kind (`isCapabilityMissingError` already pattern-matches a wide set of keywords) — but only after a first wasted upload. Static probe is the one that prevents the waste; #1 + #2 must stay in sync to preserve that property.

# LightClaw Cwd Layout Notes (Phase 24)

- `<cwd>/.lightclaw/` is a data write area, never a code discovery root. LightClaw writes inside this namespace fall into two categories:
  - **Persistent, agent-readable**: `inbox/<chatId>/<fileName>` for incoming channel media (`runtime.fs.writeFile`); `downloads/<fileName>` for WebFetch binary responses (PDF / images / archives / office docs — written from inside the sandbox by `scripts/sandbox-helpers/webfetch.py`, no chat-namespace because WebFetch has no natural namespace key). The agent can `Read` / `AnalyzeVisuals` / `Bash` these via `<workspaceRoot>/.lightclaw/<inbox|downloads>/...`. Both are aged out by the per-canonical-user `inbox-aging` sweep (Hermes-style hourly mtime scan, default ttl 7 days, configurable via `channels.feishu.inboxAging`); `inbox/` is two-deep and `downloads/` is flat, but they share the same TTL since they are the same class of cache. WebFetch always appends a 6-char random suffix to the URL-derived basename so repeated fetches of the same URL never silently overwrite, and the mime-derived extension is authoritative (URL paths like `arxiv.org/pdf/2509.25721` would otherwise confuse `os.path.splitext` into treating `.25721` as an extension).
  - **Ephemeral, tool-internal**: `tmp/pdf-pages/<uuid>/page-N.jpg` (AnalyzeVisuals' pdftoppm output) and `tmp/resize/<uuid>.jpg` (vision resize subroutine output). Both are deleted by the producing tool's `finally` block; inbox-aging will pick up stragglers only on a process crash mid-tool-call. Never agent-readable as artifacts — they exist for the duration of a single tool call.
- Hook / MCP / Skill discovery is admin-side only: `<lightclawHome>/hooks/`, `<lightclawHome>/mcp.json`, and `<lightclawHome>/skills/`. Do not reintroduce a project-layer scan path under `<cwd>/.lightclaw/` even if Claude Code does.
- Channel attachments sink in two phases: Feishu `onMessage` attaches `pendingAttachment` metadata to `NormalizedChannelMessage`; `ChannelRunner` materializes it after pairing and runtime acquire via `ChannelRunnerStrategy.materializeAttachment`. New channel adapters should follow the same shape: channel code does not touch identity or runtime pools directly.
- LightClaw deliberately does NOT register persistent attachments in any sidecar registry / index. Path-as-handle is sufficient for local files; cloud documents (PR4 Feishu collab) will pass tokens directly as tool arguments. This matches Claude Code / OpenClaw / Hermes — none ship an artifact registry. If a future feature genuinely needs cross-session lookup or token-as-handle, scope the abstraction narrowly to that feature instead of resurrecting a global registry.

# LightClaw Feishu Reply Quote Context Notes (Phase 28)

- Feishu reply messages carry `message.parent_id`. Both WS and webhook transports must preserve it as `FeishuRawMessage.parentId`; `rootId` remains reply-chain metadata and must not affect session routing.
- `ParentMessageFetcher` is best-effort and channel-local. It calls `im.v1.message.get` for exactly one parent hop, parses `{ text, mediaKeys, senderOpenId }`, resolves sender name cosmetically through `fetchFeishuUserInfo`, truncates text, caps media keys, and caches both success and fail-soft null results in an in-memory LRU. Fetch failures never block the inbound turn: log one stderr line and proceed as if the message had no quote.
- Quoted parent media reuses the normal pending-attachment path. The parent messageId, not the new reply messageId, is used for `PendingAttachment.messageId` and `fileNameFor(parentId, mediaKey)`, with `quotedFromMessageId` set so `formatChannelUserText` can append `(via quoted message)` to the path breadcrumb. Do not add a second attachment registry or duplicate inline blocks just for quotes.
- The LLM-facing contract is a `<quoted-message author="...">` block before the current user text. It may include `<text>...</text>` and one `<attached>fileName</attached>` line per quoted media key. Escape quote text and author attributes; self-quotes from the bot render `author="LightClaw"` so the model does not confuse old assistant text with the current user's words.
- Mention gating is unchanged. A group message still needs to @ the bot unless `requireMention=false`; quote context only enriches messages that already passed the normal gate. This is what enables the intended group flow: user sends a file, then replies to that file with `@LightClaw ...`, and the reply carries the file through `parent_id`.
- Interjection compatibility is by pre-rendering the same `<quoted-message>` block into `InterjectionEntry.quotedSummary`; `buildInterjectionBlock()` prepends it inside `<user-interjection>` before the interjection text. Keep this shape so quoted mid-flight follow-ups use the same decision framework as plain interjections.
- V1 is depth=1 only. If the parent itself is a reply, do not recursively fetch ancestors. Future quote-chain work should add an explicit depth limit and cycle guard instead of changing this implicit one-hop contract.

# LightClaw Pairing Card Notes (Phase 25)

- Unknown Feishu senders take the card path only when the canonical admin already has a Feishu binding. Otherwise `ChannelRunner.resolveMessageUser()` must keep the old text fallback, because an application card with no admin target is worse than a visible pairing code.
- The card path does not create `pending.json` entries until the user clicks `[确认申请]`. Cancel stays silent and does not consume the pairing rate-limit slot. If a pending code already exists, repeated user messages render the waiting card instead of sending another review card.
- `fetchFeishuUserInfo()` is cosmetic and best-effort: it uses `contact.v3.user.get` with `user_id_type=open_id`, returns `{ name, email, userId }`, and falls back to open_id on any failure. Do not make pairing depend on this API being healthy.
- `/user approve <code>` (no `--as`) and admin card approval both call `deriveCanonicalName({ name, email, openId, userId })`, so canonical names are deterministic (`<base>_<user_id>` when Feishu user_id is available). Terminal-only override: `/user approve <code> --as <name>` skips `deriveCanonicalName` and binds the sender into the supplied (existing or new) identity. The card path has no `--as` because there is no UI for picking a target name; admins who need to merge an IM sender into an existing identity (most commonly: their own admin) must use the terminal slash. `--as` validates the name with `isValidIdentityName` BEFORE `approveCode` consumes the pending entry, so a typo never burns a pairing code; in `runtime.backend = "local"` the `rejectNonAdminInLocal` gate still applies (only `--as <admin>` is accepted).
- Pairing card tokens are in-memory only. After a daemon restart, old card clicks resolve as expired or already handled; users can resend a message and `pending.json` remains the durable source of truth.
- Admin review card clicks must validate the operator through `lookupBySender(feishu:<open_id>)` + `isAdmin()`. Never trust the card payload alone for approval authority.
- **Applicant-facing pairing cards (application / waiting / cooldown) push to applicant DM**, never to the chat the applicant @-mentioned the bot in (group privacy: leaking applicant identity / pairing code to every group member is unacceptable). `PairingCardCoordinator.pushApplicantCard()` calls `sender.sendInteractiveCardToOpenId(applicantOpenId, card)` and only falls back to in-chat `sender.sendInteractiveCard(message, card)` if the DM push errors. Feishu's `im.message.create` with `receive_id_type=open_id` auto-creates the DM thread, so first-contact-in-group works without prior DM existence. Admin review cards already pushed to admin DM since Phase 25; applicant DM routing closed the symmetric leak in 2026-05-08.
- **Bootstrap text-fallback notices (welcome+code, rate-limited, cooldown-hook-missing) also push to applicant DM.** When admin has no Feishu binding `canRenderPairingCard` is false and `resolveMessageUser()` falls into the older text path that calls `sendNotice(message, …)`. Without DM routing those notices echo back to the inbound chat — including groups, leaking the same applicant identity / pairing code the card path was carefully avoiding. `ChannelRunnerStrategy.sendNoticeToOpenId({ message, applicantOpenId, kind, content })` (Feishu impl: `sender.sendInteractiveCardToOpenId(applicantOpenId, buildSystemNoticeCard({…}))`) is the DM-first path; runner's `sendApplicantNotice()` helper tries it first and falls back to in-chat `sendNotice` only when the hook is absent OR the DM push errors. All three bootstrap leak sites in `resolveMessageUser` (cooldown-hook-missing, welcome+code success, rate-limited catch) go through `sendApplicantNotice`. Fix landed 2026-05-08 dogfood when user-with-no-admin-Feishu-binding still saw cards in group.
- **No applicant-facing string mentions admin terminal commands.** `channel.pairing.adminCmd` (which read "管理员命令：/user approve <code>") was deleted; `channel.pairing.waiting.body` no longer carries the `/user approve {code}` fallback line; `channel.pairing.rateLimited` no longer references `/user pending`. Applicant-side messaging is purely user-actionable: code + waiting state + try-again-later. Admin discovers stuck pending entries through their own `/user pending` slash in DM or terminal.
- **Welcome card has admin / non-admin variants.** `buildApprovalWelcomeCard({ isAdmin })` branches on the recipient. Non-admin: legacy user-side slashes (`/help` `/status` `/fresh` `/feedback` `/stop`). Admin: separate body listing `/user` `/ceiling` `/cost` `/sandbox` plus the user-side basics (no `/feedback` since admin is the recipient, not the sender). `post-approve.runApprovalPreheat` resolves `isAdmin(name)` before pushing.
- **Pre-approval message replay.** `PendingEntry` carries `lastApplicantText` + `lastApplicantTextAt` + `lastApplicantChatId` + `lastApplicantChatType` (additive to the v1 shape; missing fields tolerated for backward-compat with old `pending.json`). Three independent `resolveMessageUser` paths must all stash routing fields (chatId + chatType) — and text when present — or replay silently dies / lands in the wrong chat: (a) the existing-pending card branch (`canRenderPairingCard && existing`) calls `updatePendingApplicantText(senderKey, message.text, message.chatId, message.chatType)` before rendering the waiting card; (b) the new-application card path stashes via `PairingCardCoordinator`'s in-memory `'pending'`/`'submitting'` state (which carries text+chatId+chatType) and promotes to pending.json the moment `applyConfirm` runs `generateOrReusePending` — call is unconditional, NOT gated on text being non-empty; (c) the bootstrap text-fallback path (admin has no Feishu binding so `canRenderPairingCard=false`) calls `updatePendingApplicantText` after `generateOrReusePending`. All three stash calls intentionally do NOT reset `createdAt` / `ttlMs` — TTL still measures from initial application time. **Empty applicantText is a valid case**: the user @-ed the bot in a group with no body (just `@LightClaw`). `updatePendingApplicantText` decouples text from routing — empty text still stashes chatId / chatType when present; the only fully-no-op case is text-AND-routing-all-absent. Post-approve then replays even with an empty applicantText so the LLM greets via the bare `[senderName] ` prefix per `9af7001`'s empty-mention-natural-reply design — replay's only hard requirement is now `replayChatId` (origin chat or welcome-card DM fallback) plus a registered channel runner. After `/user approve` (terminal or card) lands, `preheatAndWelcomeOnApproval(name, link, { applicantText, applicantChatId, applicantChatType })` pushes the welcome card and synthesizes a `NormalizedChannelMessage` whose chatId / chatType come from the **original chat** (group → group, DM → DM), not from the welcome card's DM chat_id. The welcome card's DM chat_id is only used as a degraded fallback when `applicantChatId` is missing on old pending.json shapes. The synthetic message is fed into `ChannelRunner.handleMessage` via `getChannelRunner()` from `runner-registry.ts` — chatType drives Phase 26 sessionId routing, so a group-origin replay lands in `feishu:group:<groupId>:<senderOpenId>` with `[senderName]` prefix from `formatChannelUserText`, and the agent's reply via `onAssistantTurn → sendReply(effectiveMessage, text)` goes back to the same group via `im.message.create` with `receive_id_type=chat_id`. **Cards (welcome / pairing / permission ask / permission resolution / BackgroundTask completion) stay on DM regardless** — that is a privacy boundary, distinct from the agent-conversation continuity boundary that this stash encodes. Replay is best-effort and skips silently if `replayChatId` or the channel runner is missing. Media attachments on the pre-approval message are intentionally dropped (Feishu media keys have a TTL that often outlasts admin's approval window; the user can resend).
- `sendInteractiveCardToOpenId` returns `{ chatId? }`. The chatId is the bot↔user DM chat_id reported by Feishu's `im.message.create` response. Capturing it from the welcome push is the whole reason the welcome push happens BEFORE the replay handleMessage call — the replay needs that chatId to route into `feishu:dm:<chatId>` so the replay turn and any future inbound DMs share one transcript.
- **Synthetic-message marker on replay path.** The replay `NormalizedChannelMessage` carries `synthetic: true`. The platform never saw `messageId`, so reply / reaction APIs return 400 on it. Channel adapters check the flag and short-circuit: Feishu sender's `replyTargetFor(message)` returns `undefined` for synthetic messages so `sendReplyOrCreate` skips `im.message.reply` and goes straight to `im.message.create` with `receive_id_type=chat_id`; Feishu typing strategy returns a null token immediately when `message.synthetic` is true, bypassing `messageReaction.create`. Without these short-circuits dogfood produces back-to-back `AxiosError 400` traces (typing add fail + send reply fail) and the user-visible bot reply never lands. Mention gating, pairing, transcript persistence, and the agent loop itself all still apply — synthetic messages are otherwise indistinguishable from real inbounds.

# LightClaw In-flight Interjection Notes (Phase 27)

- The channel session lock is no longer a hard barrier between turns for Feishu. When a main sessionId is mid-flight (`channelInterjectionQueue.hasInflightFor(sessionId)`), bare inbound messages route to the interjection queue and receive a one-line ack instead of stacking on the lock. `/stop` remains the explicit abort fast path; `/b` and `/fresh` always run on independent session ids and never become interjections.
- Interjections are delivered to the model at the next tool boundary inside `query.ts`. `interjectionDrain()` returns the queued entries, and `buildInterjectionBlock()` wraps them into a `<user-interjection>` text block alongside the existing `tool_result` blocks in the same user message. The block's hard rule is: the previous request MUST be completed UNLESS the user's interjection EXPLICITLY says to stop. Do not loosen the EXPLICITLY gate or shrink the reverse examples; the whole point is fighting the model's "latest message = new task" bias.
- The framework intentionally never references `/stop` in the prompt the model sees. `/stop` is a user-to-system meta command that aborts the in-flight query loop directly, not an agent action.
- Permission ASKs awaiting a click are auto-denied when an interjection arrives via `FeishuPermissionCoordinator.tryAutoDenyForInterjection(sessionId)`. The next `<user-interjection>` block carries an additional reminder so the model can re-issue the original tool call when appropriate, or skip it when the cancellation path applies. Do not send a separate "denied" notice on this auto-deny path; the ack notice is enough and the deny reason is structural, not a user choice.
- Feishu approval is card-only. There is no "type 1 / approve / yes / 批准 to approve" path anymore. `tryConsumePermissionMessage` and the `parseTextAction` family have been deleted. Do not reintroduce them; if card delivery fails, `notifyCardDeliveryFailureAndDeny` sends a plain text failure notice and resolves the pending as deny so the user can resend.
- Terminal ASK (`src/permission/prompt.ts`) remains strict-options (`1/y/2/a/3/n`, default deny). Terminal in-flight interjection is a separate future project because readline sync mode needs a side channel before users can type while tools run.
- Interjection metadata is stamped onto the injected user message as `metadata.interjectionEntries`. Audit and transcript replay can see which user words were injected at which tool boundary; do not strip that metadata in compaction or transcript rewrites.
- The interjection queue is for **bare chat only**. Any inbound text starting with `/` (after trim) is treated as a slash command and falls through to the in-lock `dispatchChannelSlash` path even when the session is in-flight — see `isLikelySlashCommand` in `runner.ts`. Read-slash + `/stop` already short-circuit via `parseFastPathSlash`; `/b` and `/fresh` route via their own parsers; the slash-bypass guard is what catches write slashes (`/mode <m>`, `/rules allow ...`, `/auth import ...`, `/user approve ...`, `/sandbox prefetch|reset`). Wrapping a slash as `<user-interjection>` is silently destructive: the LLM treats `/mode auto` as natural language and `dispatchChannelSlash` never runs, so the command is dropped. Do not narrow the guard to a slash allowlist — unknown slashes should still skip the queue so `dispatchChannelSlash` can produce its own usage notice instead of being absorbed into the next interjection block.
- **branch / fresh forks never drain the main session's interjection queue.** The push side already only ever writes to `mainSessionId` (the queue is keyed by the main session that's in-flight); the drain side in `runner.ts`'s `interjectionDrain` callback shorts out with `if (branchRequest || freshSessionId) return []`. Without this, a `/b` or `/fresh` running concurrently with a busy main DM/group steals queued entries off the main and silently injects them into the fork's prompt — the 2026-05-11 dogfood symptom was a `/b 查一下上海的天气` turn that pulled the DM's `"这个图你能看见吗"` interjection mid-flight, then the branch model started talking about images the user never sent it AND the main DM lost that user input forever (drain is consumptive). Push semantics stay unchanged: bare messages still go to `mainSessionId`; the fork-side guard is the surgical patch.
- **Reply quote anchor follows the most recent drained interjection.** `runner.ts` keeps `let replyTargetMessage = effectiveMessage` per turn; every successful `interjectionDrain` advances it to the FIFO-last entry's messageId + senderOpenId, and both `onAssistantTurn` and the end-of-query single-shot fallback use this anchor (not the const `effectiveMessage`) when calling `sendReply`. Result in Feishu UI: a bot reply that's primarily about the user's latest interjection threads off that interjection, not the turn opener — closes the 2026-05-11 confusion where the bot's "GLM-5 摘要翻译" reply was UI-quoting the turn-start `[图片][图片][图片]`. This is a *timeline anchor*, not a strict semantic mapping: when one assistant turn covers BOTH original task and interjections, the UI still only quotes one message and we pick the most recent input as the natural reference (matches Slack / Discord bot conventions). The anchor resets to `effectiveMessage` at the start of each `attempt` in the retry loop because interjections drained in a failed attempt have already been consumed from the queue and the messages slice was rolled back.

# LightClaw Feishu Session Isolation Notes (Phase 26)

- Feishu sessionId formula is now `feishu:dm:<chatId>` for p2p/private chats, and `feishu:group:<chatId>[:<threadId>]:<senderOpenId>` for group/topic-group/unknown chat types. `threadId` comes from Feishu `message.thread_id` and is a topic-group sub-channel; `rootId` comes from `message.root_id` and is only reply-chain metadata. Do not merge them back into `parentId`, and do not make `rootId` influence sessionId.
- Same Feishu user in DM, each group, and each topic thread runs an independent transcript, `session-memory.md`, channel lock, and permission FIFO queue. Canonical identity, identity preferences, permission rules, and auto-memory stay per canonical user so long-term facts and user-level rules still cross sessions.
- Group mention gating is enforced in application code before pairing/session routing. With `channels.feishu.requireMention` (default `true`), group messages pass only when `mentions[]` contains the bot open_id or the parsed text contains `@<botName>`. The Feishu open-platform "only messages that mention bot" backend toggle is not enough; keep this gate as the safety net. `requireMention: false` is the explicit admin escape hatch.
- **Bot's own @-mention is erased from inbound text before runner-side parsing.** `parseMessageContent`/`stripMentions` accept a `botStripId` (bot's open_id, fetched at startup via `fetchBotSelfInfo` and threaded through both transports). Mentions whose `openId === botStripId` get replaced with empty string at *every* occurrence in the text (any position, any count); other mentions still render as `@<name>` so the LLM keeps user-of-interest context. Mention key (`@_user_<n>`) is the precise locator with `escapeRegex` defense — do not switch back to display-name string matching, that breaks if a user renames themselves to the bot's display name. Without this strip, group inbound `"@LightClaw /b foo"` keeps the leading `@<botName>` prefix and every `^/...` slash detector (`parseFastPathSlash`, `parseBranchRequest`, `parseFreshRequest`) silently fails — `/stop`, `/help`, `/b`, write slashes all break. The 2026-05-08 dogfood incident with `/b` packed into `<user-interjection>` was caused by this exact gap; OpenClaw shipped the same shape of fix as their issue #35994 (`bot.stripBotMention.test.ts`).
- Bot self identity is probed once at startup via `/open-apis/bot/v3/info`. If it cannot be fetched, the gate falls back to "pass" with a stderr warning instead of killing the daemon, because a bot-info outage should not make the channel unusable.
- Group user messages are prefixed before the LLM sees them: `[<senderName>] <text>`. Sender name is best-effort contact lookup, then mention sidecar name, then open_id suffix. DM messages do not get this prefix. The Feishu system prompt tells the model that the prefix is sender metadata, not user words.
- Permission approval cards from group-triggered tool calls are pushed to the sender's DM via `sendInteractiveCardToOpenId(senderOpenId)`. The card button value carries `originSessionId`; callbacks validate it before resolving the pending ask. If DM push fails, fall back to the original chat and log stderr so the turn never hangs silently.
- Permission `ownerKey` is the sessionId. Same user in DM and group can have independent pending approval queues. Do not restore `chatId:senderOpenId`; that collapses unrelated session decisions back together.

# LightClaw Permission System Notes

- `Tool.suggestPermissionRules(input)` returns a *set of rules to install as a group* — not a precise→broad menu. For a chained Bash command the suggester emits one `Bash(<head>:*)` rule per subcommand (split on `;`/`&&`/`||`/`|`, max 5); for path tools a single `Tool(<dir>/**)` rule; for WebFetch a single `WebFetch(<hostname>)` rule; for MCP a single `MCP(<server>:<tool>)` rule. New tools should follow the same shape — return an empty array when no precise scope is derivable, and the approver will fall back to a single tool-wide allow rule.
- Approvers render a fixed three-option UX (Allow once / Allow <merged label> / Deny). The middle option installs every rule in the suggester's array in one go, and the merged label is built by `formatSuggestionLabel` (degrades to `N 类 …` past 50 chars). Faithful port of Claude Code's `bashToolUseOptions.tsx` + `generateShellSuggestionsLabel`. Do not add per-rule buttons or tier-selection UX back.
- `ask` outranks `allow` in `evaluatePermission`. Rules in `permissions.json`'s `ask: [...]` array force the ASK flow even under `bypassPermissions`; only `deny` outranks them. Use this to keep critical operations (`Bash(rm:*)`, `Edit(/etc/**)`) confirmable while running otherwise-permissive sessions.
- The "以后都允许" / `[a]` button writes a persisted rule to `<lightclawHome>/identity/per-user/<canonical>/permissions.json`, not to in-memory state. Rules survive daemon restarts and are reloaded via `loadIdentityRules` on every initializeState / resetSessionContext. There is no "session-scoped" tier — `once / always / deny` collapses to a 3-option UX where `always` is unconditionally persisted.
- Subagents share the parent's permission UX. The channel runner sets `state.permissionApprover` before each query() entry; the permission router prefers `ctx.permissionApprover` but falls back to `state.permissionApprover`, so AgentTool-spawned forks reach the same Feishu card / readline prompt as the main agent. Do NOT reintroduce the "isSubagent → auto-deny on ask" short-circuit; terminal forks without an approver still deny via the final fallback branch, which preserves the original safety property.
- Concurrent same-kind permission asks (e.g. parallel subagents both asking `Bash(curl:*)`) coalesce via the FIFO queue + reevaluate sweep: only the head renders a card; when the user picks "以后都允许", `FeishuPermissionCoordinator.reevaluateOwnerQueue` resolves every queued tail under the new rule set and silently allows / denies anything that now matches. Never render multiple cards for what is effectively one decision.
- High-risk permission asks (anything that contains a `Bash(rm/dd/sudo/su/sh/bash/zsh/eval/mkfs.*:*)` rule, OR an Edit/Write/Read on `/etc`, `/usr`, `/boot`, `/sys`, `/proc`, `**/.ssh`, `**/.gnupg`, `**/.aws`, `**/.kube`) hide the "以后都允许" button — channel users have no shoulder-surfing safety net and `rm -rf /` permanently allowed is unrecoverable. The classifier is `permission/high-risk.ts:isHighRiskAsk`; chained Bash commands trigger as soon as any subcommand is high-risk (`cd /tmp && rm -rf foo` → high-risk via the `rm` segment). Stale-card clicks that ask for "以后都允许" on a high-risk pending are silently downgraded to allow-once; never persist a rule that the current UX would not have offered.

# LightClaw Tool Catalog Notes (Phase 29)

- `Tool.channelScope?: ('feishu' | 'terminal')[]` filters tool visibility by channel. Omitted means visible everywhere, which preserves all pre-Phase-29 builtin tools without annotation churn. New tools that require Feishu sender/chat context should use `channelScope: ['feishu']`; terminal-only diagnostics should use `['terminal']`.
- `SessionContext.channel` is set at session creation (`'terminal'` in CLI, `'feishu'` in ChannelRunner / wake / BackgroundTask). Query callers should pass `getAllTools(ctx.channel)` or the known channel-specific equivalent. Plain `getAllTools()` remains the backward-compatible full-catalog path for tests and startup probes.
- `Tool.alwaysLoad` and `Tool.shouldDefer` override `isDeferredTool()`. Default rules: builtin tools load inline, MCP tools defer, ToolSearch never defers. `shouldDefer` wins over `alwaysLoad` so an operator-marked deferred tool is not silently inlined.
- **Phase 31 split (2026-05-12)**: every builtin tool is explicitly tagged. **8 inline** (`alwaysLoad: true`): `Bash` / `Read` / `Write` / `Edit` / `Grep` / `Glob` / `TodoWrite` / `ToolSearch`. **15 deferred** (`shouldDefer: true`): all conversation / memory / web / skill / agent / sleep / send-file / background-task tools. The split is by **per-turn use frequency**, not by capability: inline tools are what almost every turn reaches for; deferred tools are task-specific. New tools must explicitly tag `alwaysLoad` or `shouldDefer` — don't leave both unset and rely on "builtin → inline" default, because that bypasses the per-tool review for inline-vs-deferred placement. Description token budget: inline 8 = ~1770 tokens, deferred 15 = ~3380 tokens; cold-start prompt saves ~66% of tool-description bytes.
- Deferred loading is controlled by `tools.deferredLoading` (`auto` / `always` / `off`) and `tools.deferredLoadingThreshold` (default 30). **Default flipped to `'always'` in Phase 31**: tool-count threshold is no longer the gate; the gate is the `alwaysLoad` / `shouldDefer` tag on each tool. `auto` mode preserves the old "≥ threshold → enable" behavior for operators who prefer it. `off` is the emergency rollback: no ToolSearch, all tools inline.
- `ToolSearch` is injected only when deferred loading is active. It supports `select:Name1,Name2` exact lookup and keyword search with multi-token AND plus `+keyword` required-name matching. Matches are added to `SessionContext.discoveredTools`; the next query-loop turn includes their full schemas in the provider tools array.
- `SessionContext.discoveredTools` is in-memory and per session. Do not persist it or share it across DM / group / branch / fresh sessions. Forked agents intentionally get a fresh empty `Map<string, number>` plus `turnCounter: 0` so parent discovery state does not leak into child prompts. `/fresh` mirrors the same isolation: `runFresh` rewraps the parent SessionContext with `discoveredTools: new Map<string, number>()` and `turnCounter: 0` before calling `query()`, so an ephemeral fresh turn never sees the parent main session's promoted MCP tools.
- **`discoveredTools` is a bounded LRU with turn-based TTL.** **Phase 31 upgraded the V1.5 `Set<string>` to `Map<string, lastUsedTurn>`** so steady-state token spend stays low under the new `deferredLoading: 'always'` default — without TTL, a long DM session walks through every deferred tool once and then carries all of them inline forever (defeating the inline/deferred split). `markDiscovered(map, name, turn, maxSize)` is the single mutation entry: it re-inserts existing names to the back of the Map (MRU), records the current turn as the value, and evicts the front entry once `map.size > maxSize`. `pruneStaleDiscoveredTools(map, currentTurn, ttl)` drops entries with `lastUsed < currentTurn - ttl`; `query.ts` calls it at the start of every turn before building the catalog. Settings: `tools.discoveredToolsMaxSize` (default 30, 0 disables cap), `tools.discoveredToolsTtlTurns` (default 20 ≈ one /compact cycle, 0 disables TTL → V1.5 behavior). `SessionContext.turnCounter` is the session-scoped counter feeding both APIs — incremented once per query-loop turn (subagent and custom-systemPrompt callers skip the bump because they don't use the deferred path). `query.ts` calls `markDiscovered` from BOTH the `discoverTool` callback inside the tool-call dispatch (handles ToolSearch matches) AND the post-permission step in `dispatchToolCall` when the dispatched tool is `isDeferredTool` (handles direct re-use of an already-promoted tool, so active tools don't slide toward eviction just because newer ToolSearch hits keep landing). Without the active-use refresh, a session that searches a tool at turn 5 and uses it every turn after would still evict it once the TTL fired.
- Deferred tool names live in an English `<system-reminder>` at the end of the system prompt. Do not mix deferred names into `formatToolCatalog()`; that catalog is only for tools whose schemas are already loaded and callable this turn.
- When a model directly calls a deferred tool before ToolSearch, `query.ts` returns a self-healing `tool_result` explaining that the tool is deferred and giving the exact `ToolSearch({query: "select:<name>"})` call. Do not let this fall through as a generic unknown-tool or provider API error.
- Custom `systemPrompt` callers, including forked subagents, keep their existing inline tool catalog shape; query disables deferred loading for those calls to avoid a mismatch between the fixed prompt text and the per-turn tools array.
- Anthropic `tool_reference` is intentionally not used in V1. Tools-array expansion is provider-agnostic across anthropic / openai / openai-auth; Anthropic-only transport optimization can be revisited later if schema size becomes a real token cost.

# LightClaw Slash UX Notes (Phase 18)

- `/help` is a pure command list, role-rendered (admin sees an extra block). Do not put whoami / state info in `/help`; that goes to `/status`. State and operation surfaces are split: `/help` answers "what can I do", `/status` answers "who am I, where am I, what's running".
- Admin-only commands (`/user`, `/ceiling`, `/cost`, `/sandbox`) and user-only commands (`/feedback`) are gated in both `BUILTIN_COMMANDS.visibleTo` and `dispatchChannelSlash`. The role gate must reject with a clear message ("admin only" / "user-only"), not silent allow. `/sandbox` in particular is admin-only because its `status` subcommand leaks deployment internals (image / container / worker names), `prefetch` triggers a multi-GB pull, and `reset` rebuilds a per-user worker — none of which should be a user-facing button. Sandbox health surfaces to admin via channel notices, not via slash commands.
- Renamed commands (`/identity` → `/user`, `/permissions` → `/rules`) are intentionally NOT kept as compat aliases. The `RENAMED_COMMANDS` table in `src/commands/builtin.ts` only emits a hint ("Renamed to /user. See /help.") so the user can self-correct. New code must not register the old names.
- `/fresh <prompt>` runs an ephemeral one-shot session: new sessionId (`fresh-<uuid>`), no memory recall, no transcript persistence, mode forced to `default`. The output is prefixed with `[fresh] `. Do not couple `/fresh` to the forked-agent runner — it goes through the main `query()` path with `persistTranscript: false / includeMemory: false / forcedMode: 'default'` flags.
- `/stop` aborts the in-flight turn for the **calling sessionId only** (Phase 32). The state tracks abort controllers per sessionId (`abortControllerBySession`), keyed by the Phase 26 formula (`feishu:dm:<chatId>` / `feishu:group:<chatId>[:<threadId>]:<senderOpenId>` for channel sessions; the terminal session id for REPL). The channel fast-path resolves the inbound message's sessionId via `strategy.resolveSessionId(message, userId)` before aborting; the terminal handler reads `ctx.sessionId`. Same canonical admin running a long DM task while a quick group turn errors out can `/stop` in the group without killing the DM session and vice versa. Two intentional non-goals: `/branch` and `/fresh` sub-sessions (`branch-<canonical>-<uuid>` / `fresh-<uuid>`) run on their own sessionIds, so a parent-chat `/stop` does NOT stop them — both are designed as fire-and-forget / one-shot work. Never abort the global controller from a channel handler — that would also kill an admin's terminal session running concurrently.
- `/stop` and a curated read-only slash whitelist take a **pre-lock fast path** in `ChannelRunner.handleMessage` via `parseFastPathSlash`. The channel lock is held for an entire LLM turn, so without this short-circuit `/stop` would queue behind the very query it is trying to abort and never fire mid-turn. Read fast-path runs the slash inside a fresh `SessionContext` populated from disk: preferences (mode / model), identity rules, and the persisted main-session transcript (so `ctx.messages.length` reflects the real message count). Live in-flight per-turn counters like `totalInputTokens` read 0, which is honest "between turns" semantics. Whitelist (`parseFastPathSlash` returns `'read'`): `/help`, `/status`, `/cost`, `/rules` (no args / `list`), `/mode` / `/model` (no args), `/auth list`, `/user` (no args / `list` / `pending` / `feedback`), `/sandbox` (no args / `status`), `/feedback`. `/sandbox status` is special — its handler needs a live `Runtime`, so the fast path acquires one from the per-canonical pool just for that slash (Map lookup if cached). `/feedback` writes `feedback.jsonl` on a path entirely separate from the channel session transcript, so no main-lock contention applies. Write variants (`/mode <m>` / `/model <m>` / `/rules allow ...` / `/auth import ...` / `/user approve ...` / `/sandbox prefetch` / `/sandbox reset`) intentionally fall through to the lock so they serialize with any in-flight turn. When adding a new slash, default to in-lock; only opt into the whitelist after confirming the handler doesn't read live in-memory turn state (or, for runtime-touching slashes like /sandbox, after confirming a pool acquire is acceptable).
- `/branch`'s spawn-pair write to the main transcript is fire-and-forget at the runner level. `appendBranchSpawnPair` itself still acquires `channelSessionLock(mainSessionId)` (because lining up the (user, placeholder) pair at a between-turn boundary is what keeps the API contract — interleaving the placeholder mid-turn would split a tool_use from its tool_result), but the runner does NOT `await` it before kicking off the branch query. The merge-back path awaits the deferred promise before its own `rewriteTranscript`, and FIFO on `channelSessionLock(mainSessionId)` keeps spawn-pair-write strictly before merge-back. Net effect: `/b X` typed during a long main turn starts running immediately; the spawn placeholder lands in the main transcript at the next safe boundary (when the main turn finishes); merge-back replaces that placeholder with the branch's final text. Do not "fix" this by re-awaiting `appendBranchSpawnPair` at spawn time — that defeats `/branch` entirely (the symptom: branch starts only after the main turn it was meant to side-step finishes).
- `/branch` snapshots the main transcript via `trimToLastCompletedTurn(loadTranscript(mainSessionId))`, NOT raw `loadTranscript`. The trim walks back from the end and stops at the last `assistant` message with no `tool_use` block (or the last `system` compact_boundary). This is the fix for the 2026-05-07 `feishu-zouyicheng` / `branch-zouyicheng-5fce2af1` incident: when `/b` fires during an in-flight main turn, the main user message is already on disk but the assistant response is not, so a raw load returns a transcript ending in a dangling user message. Without trim, the branch then appends its own user query and the LLM sees two consecutive user messages — gpt-5-codex tolerates this by treating it as a batch and answering BOTH (branch ends up solving the main session's question alongside its own). Trim also keeps the inherited transcript small, which keeps the branch's auto-memory extraction (which blocks `awaitBackgroundTasks` at the end of the branch's runner block) fast — on a 60-message inherited transcript extraction can outlast the next main turn, producing the visible "branch done last in tmux" symptom from the same incident. Wake mode and other consumers of `loadTranscript(mainSessionId)` do NOT need trim because they acquire `channelSessionLock(mainSessionId)` first and therefore by definition see a between-turn snapshot.
- `mergeBranchResultBack` returns `MergeBranchResult` (`'replaced' | 'fallback-appended' | 'skipped'`). The fallback path handles the compact-erased-placeholder edge case: if a long-running branch finishes after main turns have triggered auto-compact (which collapses the prefix into a `system` summary message that no longer carries `branchPlaceholder` metadata), the placeholder cannot be located by branchId. Without the fallback, the branch result would be silently dropped from the main transcript. With the fallback (passed as `input.fallback = { userQuery, branchSessionId, startedAt }` from the channel runner), merge-back appends a synthetic (user, assistant) pair at the end of the transcript carrying the same `branchSpawn` / `branchPlaceholder` metadata an in-place replacement would have used. The transcript stays user/assistant-alternating, so the next main turn sees the branch outcome as a normal Q+A pair. Both replace and fallback paths log to stderr so admin can grep `branch <id> merge-back ...`. Do not remove the fallback — it is the only path that keeps long branches recoverable across compact boundaries.

Do not regress to passing the parent's cacheSafeParams.systemPrompt verbatim.

Defense-in-depth; the AgentDefinition's tools list already narrows the catalog to the same five plus omitting Bash, so the gate exists only to back-stop a future code change that adds Bash to the definition.
- `inProgressByDir + pendingContextByDir` coalescing (keyed by `memoryDir`) prevents high-frequency turns from spawning many extraction forks for the same user, while still allowing concurrent extractions for different users. Do not bypass it by calling the extraction inner loop directly, and do not collapse it back to a single global flag.
- `drainPendingExtraction(60_000)` must run from process exit paths. New daemon or shutdown paths need to wire the same drain.
- **Module-load cycle:** `tools.ts → tools/background-task.ts → background-task/runner.ts → query.ts → memory/extract.ts → agents/run-subagent.ts` would form a static-import TDZ cycle if run-subagent.ts pulled in `getAllTools` / `getEnabledTools` at the top of file. It uses `await import('../tools.js')` inside `runSubagent()` body to break the cycle at module-load time while still seeing the fully-initialized tools.ts when the subagent actually runs. # LightClaw BackgroundTask Notes

- BackgroundTask vs AgentTool: AgentTool is immediate and returns a tool_result to the current turn; BackgroundTask is scheduled future work that returns immediately and runs later in an isolated `bg-<canonical>-<task>-<fire>` session. Do not add `schedule: now` to BackgroundTask, because that blurs the tool-choice boundary and can make the user wait for a result that will never enter the current turn.
- Schedule shapes accepted at the tool boundary: `oneshot { at: ISO8601 }`, `after { afterMinutes }` (one-time, normalized to oneshot at spawn / update time — never persisted as `'after'`), `recurring { daysOfWeek, hour, minute }`, `interval { everyMinutes, anchorAt? }`. The `'after'` shorthand exists specifically because LLMs reliably mishandle "1 minute test" / "remind me in 5 minutes" — they tend to either miscompute an ISO8601 timestamp for `oneshot` or, worse, silently fall through to `interval { everyMinutes: 1 }` and create a recurring task. Both `BackgroundTask.call` and `UpdateBackgroundTask.call` rewrite `'after'` into `'oneshot'` with `at = now + afterMinutes * 60_000` before storage; `schedule-calc.computeNextRunAt` also has a defensive `'after'` branch but stored entries should never carry that kind.
- Phase 22 surface (Iter 0–5 wired): `src/background-task/{types,store,schedule-calc,runner,scheduler,wake}.ts`, `src/agents/main-agent-can-use-tool.ts`, `src/session/branch-merge.ts`, `src/channels/feishu/bg-{completion-card,card-coordinator}.ts`, the four main-agent tools `BackgroundTask`/`ListBackgroundTasks`/`CancelBackgroundTask`/`UpdateBackgroundTask`, the wake-only tools `notify_user`/`stay_silent` (only injected via wake.ts; not in `builtinTools`), and `/branch` (alias `/b`) at the channel runner level.
- The cron/background agent is intentionally stateless. `runBackgroundTaskFire()` builds a fresh SessionContext, writes its own transcript, runs `query()` as `mode: 'subagent'` with `subagentLabel: 'background_task'`, and does not inherit parent cacheSafeParams or inject fireHistory into the prompt.
- BLOCK matrix:
  - AgentTool subagents are blocked from `BackgroundTask`, `notify_user`, and `stay_silent` (`BLOCKED_SUBAGENT_TOOLS`).
  - BackgroundTask isolated agents are blocked from recursive `BackgroundTask` and from wake-only tools (`createBackgroundTaskCanUseTool`).
  - Main agent in normal mode is blocked from `notify_user` / `stay_silent` (`createMainAgentCanUseTool('normal')`); wake mode (only path that enters via `wakeMainAgent`) flips them on.
  - AgentTool is allowed inside a BackgroundTask fire so a scheduled job can fork subagents while it runs.
- Store shape is per canonical user at `<lightclawHome>/identity/per-user/<canonical>/bg-tasks.json`, versioned as `{ version: 2, tasks: [...] }`. Each task can carry `allowedTools?: string[]`, using the same pattern syntax as `/rules allow` (`Bash(rsync:*)`, `WebFetch(api.example.com)`, `Edit(/tmp/**)`, `MCP(server:tool)`). Version 1 files lazy-migrate on read by treating missing `allowedTools` as undefined. Successful oneshot tasks are removed after completion; failed oneshots stay in the store with `lastFiredAt` so approval paths can update `allowedTools` and retry immediately. Recurring and interval tasks keep `lastFiredAt`, `consecutiveFailures`, and FIFO `fireHistory` capped to 20.
- The scheduler's resource cap is per canonical user (`backgroundTask.maxConcurrentRunsPerUser`, default 3), not global. One user filling their three fire slots must not block another user's three slots. Overflow fires queue FIFO under that user.
- Startup catchup compensates missed oneshot tasks with stagger; recurring catchup is intentionally not retroactive (next run computed forward from now). Init also calls `recoverOrphanedBranchPlaceholders(sessionsDir)` so any `/branch` placeholders left in `running` after a crash flip to `interrupted` content + status. **The directory filter accepts both `feishu:` (Phase 26 sessionId formula `feishu:dm:<chatId>` / `feishu:group:<chatId>[:<threadId>]:<senderOpenId>`) AND `feishu-` (legacy Phase 20 `feishu-<canonical>`) prefixes.** Pre-fix the sweep guarded only on `feishu-` and skipped every modern session; daemon-crash recovery silently failed for all Feishu DM / group / topic-group sessions, leaving the next user turn poisoned by a `running` placeholder. Do not narrow the filter back to a single prefix without first confirming no on-disk session uses the other shape — both prefixes are accepted indefinitely (zero cost, single startsWith pair).
- Fire delivery path (`scheduler.deliverCompletion`) reads the user's `identity.channels.feishu[0]` open_id; with no Feishu binding the fire still runs but completion is logged to stderr only. `notifyTo: 'user'` pushes a card via `BackgroundTaskCardCoordinator` (success card has no buttons; ordinary failure card has `[Retry now]`; permission failure card has `[Approve & Retry]`, which merges the suggested rules into this task's `allowedTools` only, never identity-global `/rules`, and immediately queues a new fire). `notifyTo: 'agent'` instead acquires the user's main session `channelSessionLock`, runs a wake `query()` with `notify_user`/`stay_silent` injected, and pushes `🔔 ${label}\n\n${text}` only when the model picks `notify_user`. Permission-denied wake prompts include denial details and tell the main agent to either `UpdateBackgroundTask({allowed_tools:[...]})` then `stay_silent`, `notify_user`, or cancel the task.
- **Wake target sessionId resolution.** The wake path is **DM-only**. `scheduler.deliverCompletion` calls `resolveWakeSessionId(canonicalUser, sessionsDir)` (in `wake.ts`) to pick the most-recently-active `feishu:dm:<chatId>` directory whose `meta.userId` matches the canonical user. Group sessions (Phase 26 `feishu:group:<chatId>[:<threadId>]:<senderOpenId>`) are intentionally excluded — wake is a 1-on-1 reminder; surfacing a BackgroundTask completion in a group leaks task content to other group members, and group sessions can be silent for days. **Never re-introduce the pre-Phase-26 hard-coded `feishu-<canonical>` session id.** That form predates `routing.ts` and creates an orphan transcript that does NOT lock against the user's actual DM session, breaking turn-level FIFO and silently writing to a directory no other path reads. `wakeMainAgent` defends with a `mainSessionId.startsWith('feishu:dm:')` precondition that returns `{kind:'silent', reason:'wake-refused-bad-session-id'}` if violated. When `resolveWakeSessionId` returns null (no DM session yet, e.g. user paired but never DM'd), scheduler falls back to the user-card path so the fire result is never lost. Cards continue to push to DM via `sendInteractiveCardToOpenId(openId, ...)` regardless — the privacy boundary is unchanged.
- **Wake admin-only gate.** Mirroring `runner.ts:56-66`, `scheduler.deliverCompletion` rejects the wake path when `runtime.backend === 'local'` and `getAdmin() !== canonicalUser`, falling back to the user card. `wakeMainAgent` defends in depth: even if a future caller bypasses the scheduler gate, wake refuses to acquire the runtime pool for a non-admin under local backend (returns `{kind:'silent', reason:'wake-refused-admin-only'}`). Without the gate, a paired non-admin's BackgroundTask failure outcome (e.g. a recurring task that fired before the runner-side admin gate triggered) could re-enter LocalRuntime in the wake path — the runner-side gate is a fire-time guard, not a wake-time guard.
- `/branch` and `/fresh` get separate lock keys: `branch-<canonical>-<uuid>` and `fresh-<uuid>`. Both share the singleton `channelSessionLock`, so neither blocks the main session, but `appendBranchSpawnPair` and `mergeBranchResultBack` re-acquire the main `feishu-<canonical>` lock to keep main-transcript writes serialized with any in-flight main turn. Branch result text is merged back full (no truncation) — `sessionMemory.md` absorbs it as a structured finding next turn and survives compact.
- Shutdown paths must drain in this order: memory extraction, autoDream, then BackgroundTask. The CLI already calls `drainPendingBackgroundTasks(60_000)` and stops the scheduler; new daemon exits should keep that drain.
- All BackgroundTask completion-card and `/branch` placeholder strings go through `t()` (`bg.card.*`, `branch.placeholder.*`). Wake `buildWakePrompt` stays English on purpose — it's an LLM system instruction, not user-facing display.
- Cron fires and wake-mode turns construct `SessionContext` with `permissionApprover: null` ON PURPOSE. Do not attach the channel runner's Feishu approver to fire / wake contexts; a 03:00 cron fire must not hang on an orphaned approval card. Phase 23 adds the unattended fallback instead: when `requestPermission()` reaches verdict `'ask'` with no approver and `ctx.isBackgroundTask`, it allows only `BG_BUILTIN_SAFE_TOOLS` (`Read`, `Glob`, `Grep`, `TodoWrite`, `MemoryRead`, `ListBackgroundTasks`) plus `ctx.taskAllowedTools`. Everything else denies with `background-task-not-in-allowlist` and is collected into `FireOutcome.permissionDenials` with `Tool.suggestPermissionRules()`.
- High-risk permission denial rules (`Bash(rm/dd/sudo/su/sh/bash/zsh/fish/eval/mkfs.*:*)`, sensitive Edit/Write/Read paths) never go to wake mode. `scheduler.deliverCompletion()` forces them to the user permission-failure card even when `task.notifyTo === 'agent'`. The card button remains enabled because it writes only this task's `allowedTools`; it shows a warning and does not modify global `/rules`.
- `matchBashCommand` is chain-aware: it splits top-level `;` / `&&` / `||` / `|` / `&` and any segment can match a `Bash(<head>:*)` pattern. This closes the old `cd /tmp && rm -rf foo` gap for deny rules and also keeps allow behavior consistent for pipelines such as `grep foo | wc`.
